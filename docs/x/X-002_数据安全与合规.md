## 2. 详细设计

### 2.1 数据分类与敏感度分级（v2.0 新写）

> v1.3 完全缺失本节。**没有分类，就无法论证脱敏是否充分**——"我们做了脱敏"不是一个可评审的陈述，"C3 类数据不落盘、C2 类默认加密且限制访问"才是。

可观测性数据的特殊之处在于：**平台不控制其内容**。客户可以把任何东西写进日志正文。因此分类必须按"**可能出现什么**"而不是"我们放了什么"来做。

| 级别 | 内容 | 处理要求 |
|------|------|---------|
| **C0** 无敏感 | 指标名与低基数 label、服务名、span 名、时间戳、HTTP 状态码 | 无特殊要求 |
| **C1** 内部运维 | 主机名、内网 IP、K8s 元数据、`trace_id`、堆栈、SQL 结构（不含字面量） | 静态加密；租户边界隔离 |
| **C2** **可能含个人数据** | **日志正文、span 自由属性、HTTP header 与 URL query、SQL 字面量、用户 ID 类字段** | 静态加密；租户边界隔离；**默认按含 PII 对待**；内部人员访问需审批；进入脱敏扫描范围 |
| **C3** 高敏 | 凭证与密钥、身份证/银行卡/手机号、健康与生物特征 | **目标是永不落盘**——必须在摄入侧、进入 Kafka 之前被 `redact` / `hash` / `drop` |

两条判断直接决定后续所有设计：

- **C2 是默认假设，不是检测结论。** 日志正文必须无条件按 C2 处理，因为平台没有任何手段保证客户不往里写 PII，而"我们扫过了没发现"在合规场景下不构成抗辩。这条决定了加密、访问控制与留存的基线适用于**全部日志与 span**，而不是"命中脱敏规则的那部分"。
- **C3 的处理目标是"不落盘"而不是"落盘后保护"**，这直接推出脱敏必须在 Kafka 之前执行（§2.2）。一旦进了 Kafka，它就已经落在至少三个 broker 的磁盘上了。

### 2.2 PII 脱敏

#### 2.2.1 为什么必须在摄入侧、进入存储前

查询侧遮蔽（查询时才隐藏）看起来更灵活，但它防不住四类泄露：存储层直接访问、**备份文件**、**归档层（开放 Iceberg 格式，客户可 BYO-bucket 自助读取）**、以及运维人员的排障访问。数据只要落了盘，遮蔽就只是 UI 行为。

因此脱敏点位固定在**摄入网关，早于 Kafka**。执行细节属于 DD-001。

#### 2.2.2 规则形态

- **内置规则集**：手机号、身份证、银行卡、邮箱、IP、JWT、常见云厂商密钥格式；
- **租户自定义规则**：正则 + 动作三选一——`redact`（掩码）/ `hash`（保留可关联性，用于仍需按该值聚合的场景）/ `drop`（整条丢弃）；
- **规则命中数按租户暴露为指标**，供合规审计与客户自查。

#### 2.2.3 性能预算

正则扫描在 10.5 万 EPS 峰值下是实打实的 CPU 成本。**M1 压测必须包含开启脱敏后的吞吐衰减实测**，规则数上限按实测结果设为配额（进 DD-006 的配额矩阵）。没有这个实测，租户加规则就是在无声地消耗平台摄入容量。

#### 2.2.4 漏脱敏的补救路径与其代价

必须诚实地写清楚，因为这决定合同措辞：

> **存储层是不可变的。** 漏脱敏的数据一旦进入 Doris，补救手段是**重写受影响的分区**（读出、清洗、覆写、验证），期间该分区查询不一致；若已归档，还需重写 Iceberg 快照；若已进备份，见 §2.5.3。代价随发现时间线性上升。

由此得出一条**合同措辞要求**：

> **脱敏是尽力而为（best-effort）的风险降低措施，不是完备性保证。** 基于正则的检测不可能覆盖所有 PII 形态，合同与 DPA 中不得表述为"平台保证不存储个人数据"。正确的表述是平台提供脱敏能力、客户对写入内容负责、双方按 §2.1 的分级共担责任。**这一条需法务确认措辞。**

### 2.3 访问控制

#### 2.3.1 租户边界

- **摄入侧注入**：客户只持有 Token，`tenant_id` / `project_id` / `cluster_id` 由网关解析注入，覆盖客户端自报值；
- **查询侧强制过滤**：查询网关注入租户谓词（DD-005 §3.1 的 AST 改写）+ Doris Row Policy 兜底；
- **两端都不信任客户端自报值**；
- 有效性的证明方法见 DD-006 §3.2.4 的串扰测试套件。**本文档要求该套件的通过记录作为合规证据留存**，而不只是 CI 的一个绿灯。

#### 2.3.2 底层引擎凭证

用户与租户**永远不直接接触** Doris / VM 的凭证。所有访问经查询网关，网关持有引擎凭证并置于密钥管理服务中。

#### 2.3.3 内部人员访问生产数据

这是审计中最常被追问、而 v1.3 完全未覆盖的一项：

| 场景 | 要求 |
|------|------|
| 排障需要查看客户数据 | **需审批（工单 + 客户侧知情或合同预授权）**，授予时限性只读权限，全程审计 |
| 直连 Doris / VM 的运维操作 | 限于 SRE 角色，堡垒机 + 录屏，**禁止导出到本地** |
| 数据库层面的批量读取 | 禁止。确有需要走审批后的导出流程，导出行为本身进审计 |
| 审计日志本身 | **平台运维人员不可删除、不可修改**（§2.4） |

### 2.4 审计

| 审计范围 | 记录内容 |
|---------|---------|
| **查询审计** | 谁、何时、用什么条件、查了哪个租户的多少数据（含 `query_id`，与 DD-005 §3.7 的返回字段对应） |
| **管理面操作审计** | 租户/Token 的创建与吊销、留存策略变更、配额调整、采样率下发、**分区删除**、大租户迁移——记录操作者、时间、变更前后值 |
| **AI 会话审计** | 会话、调用的工具、生成并执行的查询（带 `source=ai` 标记）、证据链 |
| **配置变更审计** | 控制面每次配置版本递增的内容与操作者（IF-9） |
| **内部人员访问审计** | §2.3.3 的全部审批与访问记录 |

**存储要求**：独立存储（不与遥测数据同库）、**平台运维人员不可删除**、留存 **365 天**、可导出给客户。

### 2.5 留存与删除

#### 2.5.1 留存

per-tenant 留存策略的合规含义是"客户可以要求更短的留存"，这是数据最小化原则的落地。**但其技术可行性目前受限**——共享表分区粒度是「天 × 全体租户」，无法按单租户删分区（SD-000 Q-9 / DD-006 OQ-2）。

> **合规影响**：在 Q-9 落地前，**不得向客户承诺任意自定义留存**。销售话术与合同模板需按"平台统一留存 + 有限档位"表述。这一条要在 GA 前同步给销售。

#### 2.5.2 退租删除的范围

v1.3 只写了"Doris 数据、Iceberg 归档、VM series、Kafka 残留与备份副本"。实际范围更大，**漏掉的部分正是审计会查的部分**：

| 类别 | 载体 | 删除方式 |
|------|------|---------|
| 热/温数据 | Doris logs / spans / exemplars | dedicated 租户直接 DROP；shared 租户 `DELETE WHERE tenant_id` + compaction |
| 冷数据 | Iceberg 归档（含客户 BYO-bucket） | 重写快照 + 过期旧快照。**BYO-bucket 场景需客户配合** |
| 指标 | VM series | 按 accountID 删除 |
| 消息队列 | Kafka | 随 12 小时保留期自然过期（**无需主动删，但需在证明中说明**） |
| **派生数据**（v2.0 补） | Traces 产品：`entity_registry`、`entity_topo`、`service_metrics_1m`；Logs 产品：日志侧 rollup | 按**所属产品**逐表 `tenant_id` 删除。**这是最容易漏的一类**——它们由管线自动产生，不在任何人的"数据清单"直觉里 |
| **计量与用量数据**（v2.1 修订） | **控制面账本库**的用量表、`metering` topic 聚合结果（**不在 Doris**） | 见 §2.5.4 的冲突。退租是否保留账单由法务裁决，与遥测删除解耦 |
| **备份** | Doris 备份、元数据备份 | 见 §2.5.3 |
| **审计日志** | 独立审计存储 | 见 §2.5.4 的冲突 |
| 凭证与配置 | 控制面库 | 删除租户记录与 Token 哈希 |

**时限承诺**：合同终止后 N 天（默认 30）内完成，并出具删除证明。

#### 2.5.3 备份中的残留（v1.3 最明显的合规缺口）

备份是**时间点快照**，无法从中精确删除单个租户的数据——这不是实现难度问题，是备份这一形态的固有属性。强行做（恢复、删除、重新备份）会破坏备份链的完整性，得不偿失。

**因此删除承诺必须分两段表述**：

> 平台在合同终止后 N 天内从**生产系统**彻底删除租户数据；**备份副本中的残留随备份轮转周期自然消除，最长不超过 M 天**（M = 备份保留期）。备份在此期间保持加密且仅在灾难恢复场景下可访问，不用于任何其他用途。

`M` 的值取决于备份保留策略，需与 X-001 共同确定并写入合同。**把这段话写进合同，比声称"立即彻底删除"然后被审计发现残留要安全得多。**

#### 2.5.4 两处删除冲突（需法务裁决）

**冲突一：审计日志 vs 退租删除。** 审计日志留存 365 天且不可删除（§2.4），但退租要求删除该租户的全部数据。两条要求直接矛盾。

- 倾向方案：**审计日志不在退租删除范围内**，理由是它记录的是"平台的操作行为"而非"客户的业务数据"，且平台自身有留存义务。但审计日志中包含 `tenant_id` 与查询条件（后者可能含 C2 内容）。
- 候选缓解：退租时对审计日志中的查询条件字段做不可逆脱敏，仅保留 `tenant_id` 哈希与操作元数据。
- **需法务裁决**，这是合同条款问题不是技术问题。

**冲突二：归档校验门禁 vs 退租删除，方向相反。** SD-000 分层原则 5 规定"校验未过不得删除"，退租则要求"必须删干净"。

- 解法是**两者不复用同一条路径**：门禁防的是**自动化误删**，退租是**人工审慎删除**。退租删除走独立路径，以**人工双签 + 全程审计**替代自动校验门禁，而不是绕过它。
- 这条必须在实现时明确，否则工程师面对"门禁不让删"的报错，最可能的做法是加一个绕过开关——那个开关一旦存在，分层原则 5 就名存实亡。

#### 2.5.5 单主体删除权（PIPL 第 47 条）

从 DUPLICATE 模型的日志表中精确删除某个自然人的数据近乎不可行。**一期的诚实做法是不承诺**：在合同中声明可观测性数据为运维日志、客户为个人信息处理者而平台为受托处理方，以短留存（180 天）与摄入侧脱敏作为补偿性措施。

> **§2.6.3 的 per-tenant 密钥不解决这个问题。** 加密擦除的粒度是租户，不是自然人——销毁租户密钥会毁掉该租户的全部数据。两者容易被混为一谈，但它们应对的是不同的删除请求。

真正的单主体删除需要按 subject-key 分区或 per-subject 加密，是独立的设计课题，留待二期按实际合规压力评估。

#### 2.5.6 数据可携带

归档层为开放 Iceberg 格式，支持 BYO-bucket 与客户自助导出。

### 2.6 加密（v2.0 新写，v1.3 几乎完全缺失）

#### 2.6.1 传输

| 链路 | 要求 |
|------|------|
| 客户集群 → 平台摄入网关 | TLS 1.2+ |
| 平台内部组件之间 | TLS；**跨 AZ 链路强制**。同 AZ 内部是否强制 mTLS 见 OQ |
| 平台 → 对象存储 / Doris / VM | TLS |
| 查询网关 → 外部模型提供方（BYOM） | TLS，且见 §2.7 |

#### 2.6.2 静态

| 载体 | 要求 |
|------|------|
| Doris 主存储（对象存储） | SSE-KMS |
| Iceberg 归档 | SSE-KMS |
| 元数据备份文件 | 加密（**与数据 bucket 使用不同的密钥**——同密钥会让一次密钥泄露同时打穿数据与元数据） |
| Kafka 分层存储（若启用） | SSE-KMS |
| 控制面库中的租户 Token | **哈希存储，仅创建时明文展示一次** |

#### 2.6.3 密钥管理与轮换

**决策（已定）：采用 per-tenant 密钥。** 理由是它能做**加密擦除**——销毁租户密钥即可使其全部数据（含备份与归档中的残留）不可解密，这比物理删除容易得多，也更容易向审计方证明。而加密方案在数据写入时即固化，事后从全局密钥改为 per-tenant 需要重写全部历史数据，所以必须现在定。

| 选项 | 加密擦除能力 | 代价 |
|------|-------------|------|
| 全局/按 bucket 单密钥 | 无。删除某租户只能靠物理删数据 | 简单，KMS 调用少 |
| **per-tenant 密钥（已采纳）** | 有 | KMS 集成复杂度上升，密钥数量随租户数增长 |

##### 这个决策与共享大表架构存在冲突，适用范围必须限定

> **SSE-KMS 的加密粒度是对象级，而共享表的一个 rowset 文件里混有全部租户的数据。** DD-002 采用 `DISTRIBUTED BY RANDOM`，每个 tablet 都包含所有租户的行（这正是 DD-002 §3.3 所说跨租户类型冲突会污染同 tablet 全部租户的同一个原因）。**你无法用租户 A 的密钥去加密一个同时含有 A 和 B 数据的文件。**

因此 per-tenant 密钥的适用范围是：

| 租户档位 | 密钥粒度 | 加密擦除 |
|---------|---------|---------|
| **dedicated**（独立库表 → 独立存储路径） | **per-tenant 密钥** | ✅ 可用 |
| **shared**（共享大表） | 平台级密钥（按 bucket / 按存储路径前缀） | ❌ 不可用，删除仍须物理删数据 |

对 shared 档位，理论上的替代方案是应用层字段级加密（每租户一个密钥加密各自的行），但它会**摧毁倒排索引与半结构化列的全部查询能力**——加密后的值无法分词、无法建索引、无法做 Facet 聚合，等于放弃平台的核心能力。**不可行，不作为候选。**

##### 由此产生的下游影响

1. **§2.5.3 的备份残留问题只对 dedicated 租户被解决。** shared 租户的删除承诺仍须按"生产系统 N 天 + 备份随轮转自然消除最长 M 天"表述；
2. **§2.5.5 的单主体删除对两个档位都仍不可行**——per-tenant 不是 per-subject，销毁租户密钥会同时毁掉该租户全部数据，不是删掉某个自然人的数据；
3. **这给了 DD-006 大租户双轨策略一个新的触发理由**：有强删除合规要求的客户应当直接定级为 dedicated，而不只是按数据量定级。这是对 DD-006 §3.5 大租户定义线的新增维度，需 DD-006 会签。

**轮换**：KMS 密钥按年轮换，采用信封加密使轮换不需重写数据。租户 Token 支持随时吊销与重新签发。

### 2.7 AI 场景的数据边界

#### 2.7.1 基线

- 送入模型的遥测内容**已经过摄入侧脱敏**（§2.2）——注意这继承了 §2.2.4 的 best-effort 属性，不是保证；
- AI 的每次数据访问经查询网关，继承租户谓词注入、配额与审计（IF-8）；
- AI 会话审计见 §2.4。

#### 2.7.2 BYOM 的告知与开关

- **必须在租户配置中明确告知"数据将发送至所选模型提供方"**，并记录客户的确认；
- 支持租户**禁用外部模型、仅使用私有化部署模型**；
- **默认值：默认禁用外部模型**（opt-in 而非 opt-out）。把遥测数据发往第三方是一项实质性的数据处理行为，默认开启会让客户在不知情下产生数据外发。

##### 境外模型提供方须单独准入（v2.0 补，源自 §2.8.2）

目标市场确定为国内后，这一条从"合规偏好"升级为**法定要求**：调用境外模型提供方处理客户遥测数据构成**个人信息出境**（PIPL 第 38 条），需通过安全评估、标准合同或认证之一。

因此 BYOM 的模型清单必须分两类管理：

| 类别 | 准入 |
|------|------|
| 境内模型服务 / 客户私有化部署 | 走常规 BYOM 流程（告知 + 确认） |
| **境外模型服务** | **默认不可用。** 需完成出境合规路径后方可对特定客户开放，且须逐租户授权与留痕 |

> 这同时**缩小了 DD-007 的 MVP 范围**：AI 层一期的模型路由只需覆盖境内服务与私有化部署，境外模型的接入可以推到合规路径完成之后。这是个好消息——它减少了 M4 的工作量，而不是增加。

#### 2.7.3 对内挂载外部 MCP（回应 DD-007 OQ-5 与 SD-000 §7.4）

DD-007 支持挂载外部 MCP 作为虚拟数据源参与诊断。**这条路径上的数据不经查询网关**，因而不继承租户注入、限流与审计。它不违反 IF-8 的字面（IF-8 约束的是访问平台存储），但产生三个本文档无法接受的缺口：

1. 外部 MCP 返回的数据与平台数据在诊断报告中混合，**证据链中出现无审计记录的片段**；
2. 平台向外部 MCP **发出的请求**可能携带 C1/C2 内容（服务名、错误信息、时间窗），这是一次未被告知的数据外发；
3. 若外部 MCP 由租户自行配置，平台成为数据传输的通道，**责任归属未定义**。

**结论：在以下三项落地前，不排进 MVP。**

- 外部 MCP 的调用（出参与入参）纳入 §2.4 审计范围；
- 向外部 MCP 发出的内容明确分级上限（倾向仅允许 C0/C1）；
- 租户配置外部 MCP 时的告知与责任条款，同 BYOM（§2.7.2）。

### 2.8 合规矩阵与数据驻留（v2.0 新写）

#### 2.8.1 矩阵

> 本表是**框架**，具体适用范围取决于目标市场，需产品与法务共同填实。这里给出的是本设计已具备的对应能力，以便评审时快速定位缺口。

| 要求类别 | 本设计的对应 | 状态 |
|---------|-------------|------|
| 数据最小化 | 摄入侧脱敏、短留存（180 天）、per-tenant 留存 | **受限**（§2.5.1） |
| 访问控制与最小权限 | §2.3 | 就绪 |
| 审计可追溯 | §2.4，留存 365 天不可删 | 就绪 |
| 传输与静态加密 | §2.6 | 就绪 |
| 删除权 | §2.5，单主体删除不承诺 | **部分**（§2.5.5） |
| 数据可携带 | 开放 Iceberg 格式 + BYO-bucket | 就绪 |
| 子处理方披露 | 云厂商 + BYOM 提供方 | **待补**（需 DPA 附录） |
| 数据驻留 | 单 Region | **见下** |
| 泄露通知 | — | **缺失**，需定义事件响应与通知时限 |

#### 2.8.2 数据驻留与目标市场（已澄清）

**决策（已定）：无强制数据驻留要求；前期 PoC 仅面向国内市场。**

因此：

- **SD-000 的非目标 N5「一期不做跨 Region」确认保留**，不再是风险项。跨 Region 能力按原计划留在 M5，且其驱动因素是容灾而非合规；
- 合同中仍需明确数据存储地域（这是披露义务，与驻留强制无关）。

##### 但"只做国内"不等于合规要求变少，只是换了一套

适用法规从 GDPR 切换为**《网络安全法》《数据安全法》《个人信息保护法》（PIPL）**，可能另有等级保护（等保）要求。两件事必须点出来，因为它们容易被"我们只做国内"一句话带过：

1. **PIPL 同样规定了删除权**（第 47 条）与个人信息处理的告知—同意要求。§2.5.5 关于单主体删除的"一期不承诺"立场依然成立，但抗辩理由要改写：不再援引 GDPR 语境，而是依据"可观测性数据属运维日志、采用短留存与摄入侧脱敏作为补偿措施"，并在合同中明确客户为个人信息处理者、平台为受托处理方。**具体条款需法务按 PIPL 口径重写**；
2. **数据出境是强监管项**（PIPL 第 38 条）。这直接影响 §2.7.2 的 BYOM：调用境外模型提供方（OpenAI 等）处理客户遥测数据构成个人信息出境，需通过安全评估、标准合同或认证之一。见 §2.7.2。

等保定级与合规差距分析不在本文档范围，需单独立项——但**它应在 GA 前完成，不是 GA 后**。
