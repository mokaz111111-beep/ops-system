## 2. 详细设计

### 2.1 故障矩阵

按影响严重度排序。最右列标明该故障消耗**哪个域**的错误预算——没有这一列，故障复盘时各域会互相推诿。

| 故障 | 影响 | 应对 | 预算域 |
|------|------|------|--------|
| ★ **元数据后端集群不可用 / 元数据损坏** | **最高等级：整个 Doris 集群数据不可读**（对象存储上有数据，但没有 rowset 元数据就无法定位） | 见 §2.2 | 存储（全额） |
| 整 AZ 失效 | 摄入容量减 1/3；元数据降级但可用 | 跨 AZ 部署 + 自动摘除 | 摄入 + 存储 |
| Doris FE 主节点 | 分钟级不可写新任务 | FE 三节点选举 | 存储 |
| Doris BE 节点 | 该 BE 缓存的数据需从对象存储重新加载，**查询延迟 spike 但数据不丢**（FE 把 tablet 重新分配给其他 BE） | 4 台 BE（N+1），单台故障损失 25% 缓存与算力；写入由 loader 重试、查询由网关重试兜底 | 存储 + 查询 |
| VM vmstorage 节点 | 查询该分片降级 | 副本因子 2 接管；vminsert 自动 re-route | 存储 |
| Kafka 单 broker | 无 | 3 副本，`min.insync.replicas=2` | — |
| 摄入网关单点 | 无 | 无状态多副本 + LB | — |
| `otlp-loader` 单副本 | 无 | 无状态，consumer group rebalance，offset 在 Kafka | — |
| 查询网关 | 无 | 无状态多副本 | — |
| Doris Meta Service 单副本 | 无 | 无状态，3 副本 + LB | — |
| 元数据后端单节点 | 无（`double` 冗余） | 3 节点每 AZ 一台，自动恢复 | — |
| Doris Recycler 停摆 | 对象存储上过期 rowset 不被回收，存储成本缓慢上升 | 2 副本；停摆超 24h 告警（非紧急，但不能长期无人管） | —（成本问题，非可用性） |
| 控制面整体不可用 | 新配置无法下发；**归档调度器停摆 → 分区堆积**（由「已过期未归档分区数」SLI 告警） | 数据面 fail-static 继续运行（DD-006 §3.6.3） | 控制面 |
| 客户集群 cluster-gateway 故障 | 该集群 trace 采样中断 | 2+ 副本；`file_storage` 持久队列缓冲；node-agent 的 loadbalancing exporter 自动重新路由 | 摄入 |
| **客户集群 vmagent 侧中断**<br>（v2.0 更正） | 该集群 metrics 上报中断 | **兜底是 vmagent 自身的磁盘队列，不是 cluster-gateway 的 `file_storage`**——metrics 不经 Collector 与 Kafka（DD-001 OQ-4） | 摄入 |

两点需要点出来：

- **cluster-gateway rebalance 期间同一 trace 可能落到不同副本**，造成短时采样不一致（同一 trace 的部分 span 被采、部分被弃）。这属于可接受降级，但排障时看到"trace 不完整"要能想到这个成因，不要误判为丢数据。
- **Recycler 停摆不消耗任何错误预算**，因为它既不影响可用性也不影响正确性，只影响成本。把它放进故障矩阵是为了它不被遗忘，不是为了让它参与 SLO 核算。**成本类故障需要独立的跟踪机制**，否则它永远排在可用性故障后面直到账单出问题。

### 2.2 最高等级单点：元数据后端

#### 2.2.1 为什么它比任何数据节点都严重

存算分离把数据主副本放到对象存储，代价是**数据的可定位性被完全外置到元数据**。对象存储上的 rowset 文件在没有元数据时是一堆无法解释的字节——不是"恢复慢"，是"恢复不了"。这与存算一体架构有本质区别：后者即使元数据损坏，数据文件与表结构仍在同一节点上，理论上可以逐节点扫描重建。

因此元数据后端的重要性**高于任何数据节点，也高于 FE**。FE 挂了是分钟级不可写，元数据没了是全量数据永久不可读。

#### 2.2.2 保护措施

| 措施 | 要求 |
|------|------|
| 持续增量备份 | `fdbbackup` 至**独立的对象存储 bucket**（与 Doris 数据 bucket 物理分离，避免同一 bucket 的误删或策略错误一次带走两者），**RPO ≤ 5 分钟** |
| **季度恢复演练** | 每季度必须执行一次从备份完整恢复的演练。**演练时间本身是被监控的 SLI**——"最近一次恢复演练距今天数"超过 100 天即告警 |
| 版本升级 | 灰度，且必须先在演练环境验证 |
| 备份新鲜度监控 | 备份落后 > 15 分钟即 P1 |

> **"有备份"和"验证过能恢复"是两件事，中间隔着一次真实演练。** 未经演练的备份在统计上接近于没有备份——这不是谨慎，是行业反复验证过的经验。演练时间作为 SLI 而非 checklist 项，就是为了让它无法被"这季度太忙"跳过。

#### 2.2.3 退路

若元数据后端的运维就绪度评估不通过（团队无相应经验、无法承诺季度演练），**唯一退路是改走存算一体架构**。这会推翻 SD-000 §4 的部署模式决策，连带影响 DD-002 的计算组隔离方案（DD-006 §3.2.2 依赖计算组做大租户物理隔离）和 X-003 的成本模型。

**因此这个评估必须在 M1 完成，不能拖。** 越晚推翻，代价越大——这是 SD-000 Q-3，本架构最大的单一风险。

### 2.3 过载降级预案

按序执行，每一级都必须可单独触发、可单独回滚：

| 级 | 触发条件 | 动作 | 用户可感知影响 | 决策权 |
|----|---------|------|---------------|--------|
| 1 | 热路径查询 p95 突破 SLO 且缓存命中率下降 | 归档与回源查询排队加深，保护热路径 | 冷查询变慢 | **自动** |
| 2 | 摄入侧持续背压 | 非核心租户日志摄入限流收紧 | 被限流租户收到 429 | **自动** |
| 3 | 摄入背压持续且级 2 无效 | Trace 采样率全局下调（控制面一键下发到各集群 gateway 的 `probabilistic` 策略） | trace 覆盖率下降 | **值班确认** |
| 4 | 级 3 无效 | 低 severity（DEBUG/INFO）日志按比例丢弃（平台 Collector 层），**丢前记录丢弃计量** | 日志缺失 | **值班确认** |
| 5 | 极端 | "骨架模式"：只保 metrics + ERROR 日志，事后从客户侧 agent 缓冲部分回补 | 大面积数据缺失 | **值班负责人 + 通知客户** |

三条约束：

1. **级 3 中错误与慢 trace 的保留策略不下调。** 只下调 `probabilistic` 部分。理由是系统正在过载时，错误与慢请求恰恰是最需要的排障依据——这时候丢掉它们，等于在最需要可观测性的时刻关掉可观测性。
2. **级 4 的丢弃必须先计量后丢弃**，计入 DD-006 §3.4.1 的"服务质量事件"（可能触发 SLA 赔付）。**不计量的丢弃是不可接受的**：客户事后问"我那条日志呢"，答不上来。
3. **级 3 及以上需值班确认，不自动执行**，因为它们直接损害产品承诺。级 1、2 可自动是因为它们在配额与 SLA 的约定范围内。

### 2.4 容灾

- 全部数据的主副本在对象存储（存算分离），天然跨 AZ、可开跨 Region 复制；归档层同理。**但元数据必须与数据同等对待**（§2.2）；
- **一期不承诺跨 Region 容灾**（最佳努力）。

| 指标 | 构成 | 量级 |
|------|------|------|
| **RPO** | Kafka 未消费窗口 + 元数据备份间隔（≤ 5 分钟） | 分钟级 |
| **RTO** | 新 Region 重建 Doris 集群 + 恢复元数据 + 指向同一对象存储 bucket + Kafka 回放追平 | 小时级 |

> **RTO 的最后一项有硬约束**：Kafka 保留期只有 12 小时（G7）。如果重建 + 元数据恢复耗时超过 12 小时，回放源已经过期，这部分数据永久丢失。**所以 RTO 不只是"多久能恢复服务"，它同时是"多久之内不会永久丢数据"的期限。** 演练必须实测这个总时长，若逼近 12 小时，要么优化重建流程，要么重新评估 Kafka 保留期。

跨区复制、元数据备份自动化与容灾演练整体列入 M5。

### 2.5 错误预算治理（v2.0 完整新写）

> v1.3 只有一句"SLO 错误预算消耗接入值班告警"。**一个不会导致任何人改变行为的预算不是预算，是一个仪表盘数字。** 本节定义它如何真正产生约束力。

#### 2.5.1 分域与不可挪用

SD-000 §8.3 把 43 分钟月度预算分配为：摄入 15 / 存储 15 / 查询 10 / 控制面 3。

**四个域的预算不可互相挪用。** 这条看似死板，但没有它，分域就失去意义：查询域的 10 分钟会被摄入域的事故悄悄吃掉，最后所有人都说"总量还没超"，而查询体验已经烂了。每个域的预算由对应 DD owner 负责，超支由该 owner 解释。

#### 2.5.2 燃尽率告警（多窗口多燃尽率）

不对"预算剩余百分比"告警，而对**燃尽速率**告警——前者在月初永远不触发，在月末永远太晚。

| 窗口 | 燃尽率 | 含义 | 分级 |
|------|--------|------|------|
| 1 小时 | 14.4× | 按此速率 2 天耗尽整月预算 | **P1** |
| 6 小时 | 6× | 按此速率 5 天耗尽 | **P1** |
| 3 天 | 1× | 按此速率月末刚好耗尽 | **P2** |

短窗口配高倍率抓突发故障，长窗口配低倍率抓慢性劣化。只有短窗口会漏掉"每天慢性掉一点"，只有长窗口则对突发反应太迟。

#### 2.5.3 预算耗尽的后果

这是让预算有牙齿的唯一机制：

- **某域预算耗尽 → 冻结该域的功能发布**，只允许可靠性相关变更，直至下个预算周期或预算通过改进回补；
- 冻结由 **SRE owner 宣布**，不由该域 owner 自行判断；
- **连续两个月超支 → 触发架构复盘**，复盘的产出必须是架构或容量层面的变更提案，而不是又一轮"加强监控"。

> 判定口径基于元集群采集的 SLI，**不基于人工事故认定**。人工认定必然带来"这次不算故障"的争论，而争论的结果总是倾向于不算。

#### 2.5.4 与控制面 3 分钟预算的特殊说明

控制面预算最紧（3 分钟），但控制面故障因 fail-static 而"看不见"。DD-006 §3.6.4 已说明理由。对 SRE 的实际含义是：**控制面的告警不能因为"数据面没事"而降级处理**，它的 P1 门槛反而应该比数据面更低。

### 2.6 平台自监控（Dogfooding）

平台用自身监控自身：所有组件暴露 metrics 进独立的**元集群**（小规模 VM + Doris，与生产数据物理隔离）。

> **物理隔离是硬要求，不是洁癖。** 生产集群故障时，如果监控数据也存在生产集群，就会同时失去故障现场——"瞎子修灯"。元集群规模可以很小，但必须独立部署、独立元数据后端、独立告警通道。

#### 2.6.1 核心 SLI 看板

★ 标记为一级 SLI（进值班主面板）。

| 类别 | SLI |
|------|-----|
| **摄入** | 端到端延迟 p50/p99、Kafka 消费 lag、★ **Kafka 最老未消费消息年龄**、★ `otlp-loader` Stream Load 成功率与 `-235` 错误率、批次大小分布、★ 客户侧 cluster-gateway 持久队列水位、★ **vmagent 磁盘队列水位**（metrics 路径的兜底，与上一项是两条独立链路） |
| **存储** | ★ **BE 本地缓存命中率（一级，直接决定热查询 p95）**、tablet 数与单 tablet 大小分布、compaction 积压、VARIANT 子列数水位、倒排索引膨胀率 |
| **半结构化建模健康度** | ★ **`variant_type_conflict_total{tenant,path}`——零容忍**、★ **Compaction Score 趋势**（VARIANT 宽列的首要预警信号）、★ **热点路径子列化状态**（schema 漂移探针）、JSON key 长度超限截断数、DOC 原始 JSON 存储占比 |
| **归档** | ★ 归档校验失败率（阈值 0.1%）、★ **已过期但未归档的分区数（阈值 > 2）**、归档层快照新鲜度 |
| **元数据** | ★ 事务延迟 p99、★ 备份新鲜度、★ **最近一次恢复演练距今天数**（季度合规项） |
| **查询** | 各类查询 p95/p99、每租户扫描量与并发水位、查询排队时长 |
| **指标链路** | vmstorage 拒绝率、series 基数水位、★ metrics 链路端到端背压事件数 |
| **采样** | 各集群 tail sampling 保留率、丢弃 span 数（计费折扣依据）、★ exemplar 跳转有效命中率 |
| **控制面** | ★ 落后于最新配置版本的实例数、★ 最大版本滞后时长、★ **快照陈旧实例数与陈旧时长**、下发成功率（源：DD-006 §3.7） |
| **计量** | ★ 三项对账偏差（DD-006 §3.4.2）、metering topic 积压 |
| **隔离** | ★ 金丝雀租户串扰断言的连续通过时长（源：DD-006 §3.2.4） |
| **租户** | 每租户五维配额水位、attributes 字段数水位 |
| **错误预算** | ★ 四个域各自的燃尽率（1h / 6h / 3d 三窗口） |

#### 2.6.2 自监控自身的可靠性

元集群失效时平台处于"无监控运行"状态，这是比大多数单组件故障更危险的状态（故障发生了但没人知道）。因此：

- 元集群本身由**外部拨测 + 独立告警通道**（不经平台自身）监控；
- **"元集群不可用"本身是 P0**，与生产数据面不可用同级。

### 2.7 告警分级与值班（v2.0 新写）

#### 2.7.1 分级的两个维度

通常告警只按影响面分级。本平台需要**两个维度**，因为存在一类"不影响任何 SLO 但造成不可逆损害"的故障：

| | 可逆 | **不可逆** |
|---|------|-----------|
| **影响面大** | P0 | P0 |
| **影响面小 / 无即时影响** | P2 | **P1（即使无 SLO 影响）** |

右下格是关键。典型成员：

- **VARIANT 跨租户类型冲突**：不影响可用性，不消耗任何错误预算，但一旦发生，该路径被提升为 JSONB、索引静默丢失，**污染该 tablet 内全部租户且无法事后修复，只能重建分区**；
- **Kafka 最老未消费消息年龄 > 2 小时**：此刻没有任何数据丢失，SLO 完好，但保留期只有 12 小时，**这是数据永久丢失前的最后预警窗口**；
- **已过期未归档分区堆积**：不影响查询，但归档管线卡住会一路堆到磁盘水位，且 SD-000 分层原则 5 禁止自动 DROP 兜底。

> **把这三类按"当前影响"评级，都会落到 P2 或更低，然后在工单队列里躺到损害不可挽回。** 这就是为什么需要可逆性这一维。

#### 2.7.2 分级定义

| 级别 | 定义 | 响应时限 | 通知方式 |
|------|------|---------|---------|
| **P0** | 数据面全域不可用；数据永久丢失正在发生；元集群不可用；安全事件（转 X-002 流程） | **5 分钟** | 电话呼叫，自动升级 |
| **P1** | 单域降级；错误预算快速燃尽（1h/14.4× 或 6h/6×）；**不可逆损害的预警**（§2.7.1 右下格） | **15 分钟** | 电话呼叫 |
| **P2** | 慢性劣化；容量水位触及（动作见 X-003）；成本类异常（如 Recycler 停摆） | 下个工作日 | 工单 |

#### 2.7.3 从水位到告警的映射

X-003 定义"信号 / 水位 / 扩容动作"，本文档定义同一批信号的"告警级别 / 值班动作"。两份表共用信号名，但**回答不同问题**——X-003 回答"该加多少机器"，X-001 回答"现在要不要叫人起床"。

| 信号 | 级别 | 值班动作 |
|------|------|---------|
