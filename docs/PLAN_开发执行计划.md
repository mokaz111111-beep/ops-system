## 0. 制定这份计划的三条判断

**① M1 不是一条流水线，是五条并行轨道。** 把 M1 排成"先验证存储、再打通摄入、再做查询"会让前端 2 人空转两个月，也会让 FoundationDB 的就绪度判定（失败就要推翻架构）拖到最后才出结论。五条轨道必须同时起步。

**② 有三件事是全局门闩，它们不出结论下游就只能返工。** 分别是半结构化建模基线（Q-2）、IF-7 查询 API 规格、FoundationDB 运维就绪度（Q-3）。三者分属三条不同轨道，所以更要并行。

**③ 现在最该抢的不是进度，是"不可逆的错误"。** M1 里有三项一旦做错就无法事后修补：VARIANT 跨租户类型冲突的建模决策（污染后只能重建分区）、静态加密的密钥粒度（改一次要重写全部历史数据）、Stream Load 幂等 label 的批次边界（定错了丢数且不报错）。这三项的优先级高于任何功能进度。

## 2. M1 内部的关键时序约束

这五条约束不是建议，违反其中任何一条都会产生返工。

### 2.1 B3 必须在 B4 之前

幂等 label 的批次边界规则（B3）决定了 `otlp-loader` 如何切批。先写 loader 再补规则，意味着攒批逻辑、offset 管理、label 生成三处都要改。而这个 bug 的特征是**不报错、只丢数**——`-235` 之类的错误会在监控里尖叫，重复消费导致的 label 不一致则完全静默，直到有人发现某天的数据少了一截。

**B3 已于 2026-10-04 由 Owner 双签关闭**（DD-001 §2.1 第 1–5 条 + DD-002 Q2-10）。B4 编码必须按已签口径落地，不得另选切批函数。同日一并关闭：生产 `acks=all` + `min.insync.replicas=2`（OQ-5）、身份只认消息头、限流按 Cluster、单批超突发额度走 E4（默认 4MiB）。OQ-6 的 M1 分区键偏离已签，二期必改回 `trace_id`。

### 2.2 D1 必须在第 1~2 周完成

前端 2 人的全部工作都挂在 IF-7 上。规格没定，他们只能写脚手架。IF-7 的草案已经在 DD-005 §3.7，补全它是文档工作而不是研发工作，没有理由排到后面。

**补全的验收口径是对照 DD-008 §3.9 的 FE-01~FE-31 逐条勾**，其中 10 条被标为 M2 阻塞项。不要靠"看起来够了"判断。

### 2.3 A5 必须做，哪怕 A4 通过

引擎定稿（Q-1 关闭）之后，稀疏列退路是**唯一退路**，不再有"换 ClickHouse"兜底。只验证主方案的风险是：如果 A4 在第 7 周给出否定结论，而退路从未验证过，那时你距离 M1 结束只剩一周，手上没有任何已验证的可行方案。

A5 的增量成本很小（同一套仿真数据换一个建表配置重跑一遍），买到的是"主方案失败时立刻有已验证的 Plan B"。

### 2.4 B6 的五段必须分别打点

§8.1 的分段预算（Collector 1.0s / 网关 0.5s / Kafka 0.5s / loader 2.0s / Stream Load 2.0s + 4.0s 余量）是用来定位超支模块的。只测端到端总和的话，超支时无法判断该优化谁，而 4.0s 的余量会掩盖某一段的严重超支直到它吃掉全部缓冲。

注意 DD-001 OQ-1 记录的口径差异：v1.3 的"3~5 秒"是典型值估算，§8.1 的 6.0 秒是分段预算上限。**验收按预算，不要拿 3~5 秒的合计值交差。**

### 2.5 A3 与 E2 必须联合评估

这两项表面无关，实际耦合：

- **A3** 若结论是"必须放弃 RANDOM 分桶、改按租户隔离 tablet"（以消除跨租户类型冲突的爆炸半径），那么每个数据文件就不再混有多个租户的数据；
- **而这恰好解除了 E2 的限制**——Q-14 说 per-tenant 密钥只对 dedicated 可用，根因正是 RANDOM 分桶让每个 rowset 文件都混有全部租户数据。

换句话说，**按租户隔离 tablet 这个决策同时解决类型冲突污染和共享表加密擦除两个问题**，但它的代价是写入均衡性（这正是 DD-002 §3.1 当初选 RANDOM 的理由）和大租户数据倾斜。这是一次三方权衡，不能由 A3 单独拍板后再让 E2 接受结果。

## 4. M2~M4 概要

### M2（2~4 月）· 最小可用 + 内部 dogfood 全量切换

- logs / metrics 端到端上线；traces 暂缓
- PII 脱敏实现 + 性能衰减实测（开启脱敏后的吞吐）
- 退租删除实测，**shared / dedicated 两条路径都要测**
- 背压故障注入：丢失率 < 0.01%；**必须覆盖 vmagent 磁盘队列那条路径**（DD-001 OQ-4，metrics 不走 Collector 与 Kafka，兜底组件与 logs 不同）
- 控制面 IF-9 的配置下发通道 + fail-static 本地快照落盘
- 串扰测试套件建成并挂 CI（DD-006 §3.2.4）
- 前端：检索页完善 + 指标查询页
- **出口**：内部 dogfood 全量切换，背压用例达标

### M3（4~6 月）· traces + 关联 + 归档 + dedicated

- traces 上线，含 cluster-gateway tail sampling
- 三信号关联动线 UI；`entity_registry` / `entity_topo` 与服务拓扑页
- 告警引擎（vmalert + SQL 调度）
- 归档链路 + 三项校验门禁 + 冷查询计算组
- **dedicated 档位基础能力**（独立库表 + 独立计算组 + per-tenant 密钥）— 已从 M4 提前
- AI 层设计评审 + IF-8 规格双签
- **出口**：首批种子租户接入；归档"先验后删"全流程演练通过；至少一个 dedicated 租户端到端打通

### M4（6~9 月）· 商业化 GA

- 多租户配额矩阵五维全部生效 + 计量计费管线 + 对账
- 大租户 Track A 在线迁移工具链
- AI 层 MVP（查询专家 + MCP Server + BYOM，**仅境内模型与私有化部署**）
- 单位经济性表填实，**按 G6 两种口径各给一次结论**
- **出口**：商业化 GA；定价评审通过

### M5 · 跨 Region 容灾

驱动因素是容灾而非合规（数据驻留已确认无强制要求），优先级可按实际客户需求调整。
