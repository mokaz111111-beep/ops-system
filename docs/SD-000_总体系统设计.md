## 0. TL;DR

多租户 SaaS 可观测性平台。对外是 **Logs / Traces / Metrics 三个可独立开通的产品**，加一层只做编排的可观测平台；对内 Logs 与 Traces **复用同一套 Doris**，Metrics 走 VictoriaMetrics。

- **产品**：租户可只买日志、只买链路、只买指标，或任意组合。平台不拥有遥测数据，只拥有开通关系、跳转契约与计量账本（§1.2）。
- **摄入**：OpenTelemetry 标准协议接入；trace 采样在客户集群内以 tail sampling 完成，只把有价值的链路传回平台。
- **存储**：Logs 与 Traces 同为"宽事件"，落同一套 Apache Doris（存算分离，S3 主存储 + 本地 NVMe 缓存），关联查询是一次 SQL JOIN；两套表族、两套 API、两套配额，**产品分立、引擎复用**。Metrics 因数据模型与查询语言高度特化，独立走 VictoriaMetrics，保留完整 PromQL 生态。
- **查询**：统一查询网关按产品路由，对外提供日志检索、PromQL、Trace 点查与跨产品关联编排，并在此处收口租户隔离、限流与审计。
- **产品接口三条并列**：控制台 UI、Open API、AI（MCP Server）。

**容量设计目标**：开局 1.5 TB/天日志、1 亿落库 span、500 万活跃 series；**架构按 10 TB/天 设计，1.5 → 10 TB 全程只需加节点与调参数，无架构变更**。整体可用性 SLO 99.9%。

## 1. 背景与问题陈述

可观测性 SaaS 的核心矛盾：**写入吞吐极大、查询模式两极分化（点查 vs 分析）、多租户隔离要求严格，而单位数据价值密度低**（成本敏感）。

单一引擎难以同时满足时序高基数写入、全文检索、OLAP 分析三类负载。因此采用**「按产品选引擎、按平台做编排」**，而不是"一个引擎打天下"，也不是"三个信号绑成一个不可拆的系统"：

- **Metrics 是独立产品，走专用引擎**：数据模型高度特化（数值时间序列 + label 索引 + PromQL），VictoriaMetrics 是事实标准级选择；
- **Logs 与 Traces 是两个独立产品，复用同一套 Doris**：两者本质同为宽事件，同引擎让关联查询从"两次查询 + 应用层拼接"降级为一次 JOIN。这是平台编排层的红利，**不是把两个产品焊成一个 SKU**。

引擎复用不等于产品合并。火山 TLS / APMPlus / VMP 对外三套产品、对内存储可以共享；我们同样：**API、配额、开通、留存按产品切，Doris 集群按引擎共享。** 一期物理上仍是一套 Doris + 一套 VM；以后按产品拆计算组或独立集群，不改表结构、不改对外契约。

### 1.1 已定稿的顶层决策：Metrics 不并入 Doris

此项曾被反复质疑，现已定稿，**不再重开**。核心理由两条：

1. **量级**：500 万 series / 30s 采集 ≈ 144 亿 samples/天，是日志条数（30 亿/天）的 4.8 倍行数。专用时序编码约 0.7 B/sample（≈10 GB/天），通用列存高一个数量级（≈150 GB/天）。用通用列存承载它等于把 Doris 集群规模翻倍，去换一个更差的查询模型。
2. **生态**：PromQL 的语义细节（counter reset、staleness marker、5m lookback delta、`@`/`offset`、`histogram_quantile`、`on/group_left`）自研翻译层是多人年投入，且难以追平用户对 Grafana 的既有预期。

> 完整量化对比见 **X-003 容量与成本模型 §2**。

### 1.2 已定稿的顶层决策：三产品 + 平台编排（v2.1）

此项已定稿，**不再重开**。对标火山「TLS / APMPlus / VMP + 统一控制台」：

| 对外产品 | 一期引擎 | 该产品拥有的数据 | 不拥有 |
|----------|----------|------------------|--------|
| **Logs** | Doris 表族 `logs` | 日志原文、日志字段目录、日志侧物化 | 租户开通、账单、Token |
| **Traces** | Doris 表族 `spans` + 派生 | span 原文、`entity_registry` / `entity_topo` / `service_metrics_1m`、`metric_exemplars` | 同上 |
| **Metrics** | VictoriaMetrics | series 与 PromQL 元数据 | 同上；exemplar 只在 Traces 侧落一份引用 |
| **可观测平台** | 无遥测引擎 | 开通关系、跳转契约、查询网关、告警编排、**计量账本（控制面库）** | 任何遥测主数据 |

四条纪律，任何模块设计不得违背：

1. **控制面（开通、鉴权、配额、路由、账本）独立 OLTP**，三个产品都是它的客户。不得把平台元数据或计量主存放进 Doris / VM。
2. **每个信号引擎只存自己的数据和自己的派生。** 禁止建一个叫 `platform_meta` 的 Doris 杂烩库。
3. **平台不拥有遥测数据。** 它拥有「这个 Org 开了哪些产品」以及关联键约定（`trace_id`、`service`、exemplar）。
4. **一期引擎复用，不锁死以后拆集群。** 表族、API 路径、配额维度必须按产品切开，使 Logs 与 Traces 日后可分计算组或分集群而不改契约。

计量用量表曾写在「Doris 同库小表」。**已否决（v2.1）**：只买 Metrics 的租户不能依赖 Logs/Traces 集群活着才出得了账单。账本进控制面库；Doris / VM 只作对账数据源。细则见 DD-006 §3.4。

## 4. 规模与容量结论

> 完整推导、水位预案、10 TB 扩容推演与成本模型全部在 **X-003**。本节只保留架构评审需要知道的结论。

| 维度 | 开局（1.5 TB/天） | 终点（10 TB/天） |
|------|------------------|-----------------|
| 日志 | 30 亿条/天，3.5 万 EPS（峰 10.5 万） | 23 万 EPS（峰 70 万） |
| Span（落库口径） | 1 亿/天（采样前约 10 亿） | 线性放大 |
| 指标 | 500 万活跃 series，16.7 万 samples/s | 约 7 倍 |
| Doris 集群 | 4 BE + 3 FE + 元数据组件 | 10 BE，**不换引擎、不改表结构** |
| VictoriaMetrics | 4 节点，180 天留存 | 14 节点 |
| Kafka | 3 节点，**保留 12 小时** | 6 节点 |
| 归档层 | Iceberg on S3，180 天 | S3 弹性，无动作 |

**三条影响架构的推论**：

1. **瓶颈不是 CPU，是 BE 本地缓存命中率**。缓存未命中会回源 S3，热查询延迟上升一个量级。因此缓存命中率被提升为**一级 SLI**，成本控制的第一杠杆是热窗口时长而非机器数。
2. **一期即采用存算分离**，而非"先存算一体、到量再切"。终点在 10 TB/天，若延后切换，迁移窗口正好落在业务量最大的时刻。代价是一期就要承担 Meta Service + Recycler + FoundationDB 的运维面——**这是本架构最大的单一技术风险**（§12 Q-3）。
3. **Kafka 保留期 12 小时既是成本项也是故障预算**。它不是"缓冲区大小"，而是**落库链路故障必须恢复完毕的硬期限**。超过即永久丢数。

### 5.1 分层原则（五条，任何模块设计不得违背）

1. **Logs/Traces 与存储之间必须有 Kafka**——解耦峰值、支持回放、写入端故障时不丢数据。**Metrics 例外**：回放价值最低（断点可容忍），直连 vminsert；但**必须实现端到端背压**，否则客户侧的持久队列兜底只存在于纸面。
2. **落库由自研 `otlp-loader` 承担，而非 Doris Routine Load**。OTLP 的嵌套结构需要展开成行，这是 Routine Load 做不到的。
3. **无状态层全部 Deployment + HPA**（网关、Collector、loader、查询网关）；有状态层（Kafka、Doris 全家、VM、FDB）各自独立扩缩容。
4. **控制面与数据面彻底分离**。控制面故障时，数据面按最后一次下发的配置继续运行（**fail-static**），不得因配置读取失败而拒绝数据。
5. **分区删除是全系统唯一不可逆操作，必须经过归档校验门禁**。任何自动化路径（包括存储引擎自带的 TTL 回收）都不得绕过。
6. **产品与引擎解耦（v2.1）**。Logs 与 Traces 对外是两个产品，对内复用 Doris；Metrics 是第三个产品。平台控制面与计量账本不得住在任一信号引擎里。细则见 §1.2。

## 6. 模块划分与文档地图

### 6.1 拆分依据

模块边界按**「谁来评审、谁来签字」**划分，而不是按篇幅或话题。判据有三条：

- **单一 owner**：一份文档只有一个人对它的正确性负责；
- **独立评审节奏**：存储建模改一个参数不应该惊动前端评审人；
- **契约稳定**：模块之间只通过 §7 的契约耦合，契约不变则内部可自由演进。

横切文档（X-00x）单独成册的理由是**评审人不同**：可靠性由 SRE 签字、合规由安全与法务签字、成本由财务与定价签字。混在模块文档里，这三拨人永远不会真正读到、也就永远不会真正签字。

> **这是拆分能够成立的前提。** 单体文档时期各章可以互相假设对方的行为；拆开之后，任何跨模块假设都必须在本节显式写出，否则子文档会各自漂移。
>
> 契约变更 = 架构评审，不是模块内部决定。

### 7.1 全局字段约定（贯穿全链路，所有模块必须遵守）

### 7.3 两条容易被忽略的契约

- **IF-3 双签**：`otlp-loader` 的批次大小同时受摄入延迟预算（DD-001）和存储侧导入稳定性（DD-002）约束，两边都能单方面改坏。规定为**双方共同拥有，任一方变更须对方签字**。切批纯函数、`S=4096`、64MiB `encoded_bytes` 帽、`label already exists` 视成功、label 范围 ⊆ 写入行已于 **2026-10-04 由双方 Owner 签字**（DD-001 §2.1 / DD-002 Q2-10）；改 `S` / `B` 或 label 格式须回签。`variant_doc_materialization_min_rows` 耦合尚未会签。
- **IF-1 的错误传播**：整条兜底链路（客户侧持久队列 → 重发）只有在每一跳都如实返回可重试错误时才成立。任何一跳"吞掉错误返回 200"，兜底就退化为静默丢数。这条写进 IF-1 而非藏在 DD-001 内部，就是为了让它被评审看见。

### 7.4 已知的契约缺口（v2.0 识别，M2 前必须补齐）

拆分过程中发现三处**契约本身不完整**的地方，记录在此以免被当成"某个模块的内部问题"而无人认领：

| 缺口 | 现状 | 归属 |
|------|------|------|
| **IF-10 只覆盖 Doris 分区删除** | 归档层（Iceberg on S3）自身的到期删除与退租删除**没有等价门禁**，也没指定执行方。而分层原则 5 说的"删除不可逆"对归档层同样成立 | DD-004 提方案，X-002 会签 |

## 8. 延迟与错误预算分解

> **目的**：把 §3.2 的端到端 SLO 拆成各模块可独立验收的分段预算。没有这一步，拆分后会出现"每个模块都说自己达标、整体不达标"的经典失败。
>
> 下表为**初稿分配，M1 实测后校准**。校准由架构 owner 统一进行，模块不得自行挪用他人余量。

### 8.1 摄入延迟预算（SLO-1：p99 < 10s）

| 段 | 预算 | 责任模块 |
|----|------|----------|
| 客户集群 Collector 攒批 | 1.0 s | DD-001 |
| 网络传输 + 摄入网关处理 | 0.5 s | DD-001 |
| Kafka 写入至可消费 | 0.5 s | DD-001 |
| `otlp-loader` 攒批 | 2.0 s | DD-001 |
| Stream Load 提交至可见 | 2.0 s | DD-002（IF-3 双签） |
| **未分配余量** | **4.0 s** | 架构 owner 持有 |
| **合计** | **10.0 s** | |

留 40% 余量是刻意的：摄入链路的抖动来源（compaction 冲突、rebalance、S3 抖动）在设计阶段无法准确建模。**余量归架构 owner 统一持有，任一模块超支需要走评审申请，而不是自行占用。**

> **预算 ≠ 估算（v2.0 澄清）**：上表是**分段预算上限**，不是链路的预期耗时。设计阶段对典型路径的估算是 **3~5 秒**（p50 落在 5 秒以内，对应 SLO-1 的 p50 目标），而预算按 p99 分配并留足抖动空间。两个数字都对，但用途不同：**估算用于判断设计是否可行，预算用于判断某个模块是否越界。** 验收时看预算，宣传时看估算，不要互相套用。

### 8.2 查询延迟预算

**SLO-2 日志检索 p95 < 3s：**

| 段 | 预算 | 责任模块 |
|----|------|----------|
| 网关鉴权、租户注入、SQL 生成 | 50 ms | DD-005 |
| Doris 查询执行（**前提：BE 缓存命中**） | 2.4 s | DD-002 |
| 结果序列化与传输 | 200 ms | DD-005 |
| 余量 | 350 ms | |

**SLO-3 Trace 点查 p95 < 1s：** 网关 50 ms + Doris 800 ms + 传输 150 ms。

> 注意 Doris 段的预算**以缓存命中为前提**。缓存未命中属于容量问题而非查询层问题，由 X-003 的水位预案兜底，不计入本预算。

#### 8.2.1 测量边界（v2.0 补充）

**SLO-2 / SLO-3 / SLO-4 的测量点在查询网关的出口**，即从网关收到请求到网关发出完整响应最后一个字节为止。**浏览器侧的反序列化与渲染不在上述预算内**，理由是它取决于用户设备与页面状态，平台无法承诺；把它塞进服务端 SLO 只会让指标失去可操作性。

这不等于渲染性能无人负责。DD-008 需要另行定义**前端感知延迟**指标（首屏可交互时间），与本表的服务端 SLO 并列而非嵌套，其目标值由前端 owner 提出、产品确认。

> 该边界在拆分前从未写明，导致 DD-008 与 DD-005 曾同时认领同一段 200 ms 预算。现予澄清：**那 200 ms 属于 DD-005 的响应序列化与网络传输，不含浏览器渲染。**

### 8.3 可用性错误预算分配（SLO-5：99.9% ≈ 43 min/月）

| 域 | 月度预算 | 责任模块 |
|----|---------|----------|
| 摄入链路 | 15 min | DD-001 |
| 存储层（Doris + VM） | 15 min | DD-002 / DD-003 |
| 查询层 | 10 min | DD-005 |
| 控制面（影响数据面的部分） | 3 min | DD-006 |

控制面预算极小，正是因为 §5.1 第 4 条要求 fail-static——控制面挂掉本不该影响数据面可用性，3 分钟只覆盖配置下发本身的故障窗口。

**预算消耗接入值班告警**，连续两个月超支触发架构复盘（X-001）。

## 9. 关键技术选型与备选方案

> 本节只记录**已定稿、不再重开**的顶层选型。模块内部的选型（如索引类型、批次策略）归各 DD 文档。

| 选型 | 结论 | 主要备选与放弃原因 |
|------|------|-------------------|
| Metrics 引擎 | VictoriaMetrics | 全量进 Doris：量级劣势 15 倍 + 需自研 PromQL 翻译层（§1.1） |
| Logs/Traces 引擎 | Apache Doris 4.0.8<br>**（已定稿，2026-10）** | **ClickHouse：基于社区公开数据否决，不做自建对比 PoC。** 能力接近，但放弃点（半结构化建模与倒排索引的工程成熟度）已有足够公开材料支撑判断，自建双跑对比的成本换不回相应的决策质量——**优先快速迭代**。ES/OpenSearch 写入与压缩率劣势明显，成本否决 |
| Doris 部署模式 | 存算分离（一期即用） | 存算一体 + cooldown 搬迁：迁移窗口落在业务高峰，风险更高（§4 推论 2） |
| Trace 后端 | 与 Logs **同引擎、不同产品**（Doris 独立表族） | Grafana Tempo：纯 trace 成本更优，但把关联查询打回跨系统拼接。引擎复用吃 JOIN 红利；产品分立保证只买链路的客户不绑死日志 SKU（§1.2） |
| 摄入落库方式 | 自研 `otlp-loader` | Doris Routine Load：jsonpaths 无法展开嵌套 OTLP 数组，且攒批延迟无法承诺 SLO |
| 冷层查询 | Doris Iceberg Catalog | 自建 DataFusion 集群：等于重做租户隔离、限流与弹性；开放性来自存储格式而非查询引擎 |
| 日志检索引擎 | Doris 倒排索引 | Loki：无真倒排索引，大查询靠暴力扫，SaaS 下成本不可控；Quickwit：无 OLAP 能力，且开源路线存在不确定性 |
| 摄入缓冲 | Kafka（logs/traces） | 直连 Doris：削峰与回放能力缺失，存储抖动直接传导为摄入丢失 |
| **后端语言**<br>（已定，2026-10） | **全部自研组件统一 Go**（摄入网关、`otlp-loader`、`metrics-ingest`、查询网关、归档调度器、控制面、计量管线） | 混合栈（数据面 Go + 控制面 Java）：语言边界会在共享的租户模型、配置结构、错误码表上产生两份实现；摄入热路径 Rust：收益集中在 CPU 密集的解析与脱敏，但整体人力成本更高，**与"快速迭代优先"的取向冲突** |
| **前端栈**<br>（已定，2026-10） | **React + TypeScript** | Vue 3 + TS：能力相当，选 React 取其可观测性领域的现成生态（时序图表、虚拟长列表、火焰图/瀑布图组件） |

## 10. 横切关注点摘要

本节只给结论与指针，细节在 X 文档。

### 10.1 可靠性（→ X-001）

- **最高等级单点是 FoundationDB**：它是 Doris 存算分离的元数据后端，元数据丢失 = 全集群数据不可读。要求 RPO ≤ 5 分钟的备份 + 季度恢复演练。
- **容灾**：一期单 Region 三 AZ，不承诺跨 Region。RPO = Kafka 未消费窗口 + FDB 备份间隔；RTO 为小时级。
- **平台自监控物理隔离**：用独立元集群监控生产集群，避免"瞎子修灯"。

### 10.2 安全与合规（→ X-002）

- PII 脱敏在**摄入侧**完成（进入存储前），不是查询侧遮蔽；
- 退租数据删除必须可验证、可出具证明；
- AI 送入模型的遥测内容已经过脱敏；BYOM 场景须向租户明示数据流向，并支持仅用私有化模型。

### 10.3 成本（→ X-003）

- G6 当前**无法验收**——只有容量估算没有成本估算，成本表须在 M1 压测后填实，它同时是定价的唯一输入；
- 第一成本杠杆是**热窗口时长**，第二是**归档压缩率**，第三是**跨 AZ 流量**（约 50~100 GB/天，此前被完全忽略）。

> **M3/M4 的 dedicated 拆分（2026-10 调整）**：原计划把 dedicated 相关工作整体放在 M4。但 M3 要接首批种子租户，而种子客户中可能存在高合规要求者——他们必须落 dedicated（否则承诺不了加密擦除，见 §12 Q-14）。因此拆为两段：**基础能力（直接供给，即 DD-006 的 Track B）提前到 M3，在线迁移工具链（Track A）留在 M4**。这个拆分成本不高，因为 DD-006 §3.5 的两条轨道本就共用同一套租户分层注册表，Track B 只是"第一天就按 dedicated 配置"而不需要搬迁能力。

**资源假设（已确认）**：后端 6~8 人 + 前端 2 人 + SRE 2 人，按现排期执行。若后续实际团队缩减，削减顺序为：AI 层降级到 M5 → 前端只保留检索与 Trace 两页（其余用 Grafana 顶上）→ 大租户双轨只做 Track B。**这个约束比任何技术选型都更可能成为项目的实际瓶颈。**

## 13. 术语表

| 术语 | 含义 |
|------|------|
| 三信号 / 三支柱 | Logs、Metrics、Traces。**信号 ≠ 产品**：三个信号对应三个可独立开通的产品，平台是第四个编排层（§1.2） |
| 产品 / 引擎 | 产品是对外 SKU 与 API 边界；引擎是对内存储实现。Logs 与 Traces 两个产品复用 Doris 一个引擎 |
| 宽事件（wide event） | 带大量可变属性的单条事件记录，日志与 span 同属此类 |
| tail sampling | 在链路结束后根据完整信息（是否报错、是否慢）决定是否保留，与 head sampling 相对 |
| 存算分离 | 计算节点不持有数据主副本，数据在对象存储，本地盘仅作缓存 |
| **热窗口** | **本文档集中该词有两个含义，务必区分**：①「缓存热窗口」= BE 本地 NVMe 缓存覆盖的时长（7 天），决定查询延迟；②「归档触发窗口」= 分区进入归档流程的年龄阈值（15 天），决定数据何时离开 Doris。二者之间的 8~15 天是**温层**（数据仍在 Doris，但已被逐出本地缓存，查询回源对象存储）。单独说"热窗口"时默认指 ① |
| exemplar | 指标数据点上附带的、指向某条具体 trace 的引用，用于"指标异常 → 链路"跳转 |
| fail-static | 依赖不可用时，按最后一次已知配置继续运行，而不是拒绝服务 |
| 错误预算 | 由可用性 SLO 反推出的允许不可用时长，用于在稳定性与迭代速度之间做量化取舍 |
| 计算组（compute group） | Doris 存算分离下共享同一份存储但物理隔离的 BE 进程组 |
