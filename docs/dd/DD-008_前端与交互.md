## 3. 详细设计

### 3.1 竞品范式提炼

> 原文迁自 v1.3 §17.1。

| 产品 | 核心范式 | 我们吸收什么 |
|------|----------|--------------|
| Datadog | Facet 驱动探索：查询栏 + 直方图 + 左侧 Facet + 主列表；一切值可点击过滤；span 侧滑面板聚合 Tags/Logs/Metrics/Errors | 检索页三段式布局；"一切皆可跳转、跳转不丢上下文" |
| 火山引擎 TLS | 云控制台工程化：检索/SQL 分析双模式；iframe + STS 免密内嵌；应用市场预置看板；Agent 长期记忆 | 控制台内嵌能力（二期卖点）；应用市场式预置看板；AI 租户知识库 |
| DataBuff | AI 对话即首页；APM 按服务/DB/MQ/缓存分类；拓扑为核心视觉 | AI 作为一级入口；APM 分类导航 |
| Google Cloud | 资源优先 IA；SLO 一等公民（burn rate 告警）；Metrics Explorer + PromQL | SLO 模块设计；资源锚点导航 |

这张表不是竞品调研的存档，它是四条设计约束的出处，后续章节都可以回溯到这里：

- **Datadog 的 facet 范式决定了检索页的骨架**（§3.4）。它同时决定了一件后端的事：facet 要"即点即用"，就必须能对任意字段路径做 top values 聚合，而不是只对预先注册过的字段。这是 §3.9 中 FE-05 / FE-06 两条需求的来源。
- **TLS 的控制台内嵌**是二期的商业化卖点，一期只借用它的"双模式查询"（检索语法 + SQL）思路，见 §3.4 与 §3.8。
- **DataBuff 的 AI 即首页**被我们改造为"双入口首页"（§3.2 决策 1）——不是把 AI 当唯一入口，而是与服务健康矩阵并列。理由是排障者进入平台时的意图分两类：知道自己要看什么（矩阵），和不知道（AI）。只留一个入口会逼另一类用户多走一步。
- **Google Cloud 的资源优先 IA 与 SLO 一等公民**决定了信息架构中"应用性能"以服务为锚点组织、告警模块内含 SLO 子页（§3.3）。

### 3.2 全局交互决策

> 原文迁自 v1.3 §17.2。五条决策为已定稿内容，本节只补充理由与它们对后端的要求。

1. **双入口首页**：默认首页 = 服务健康矩阵（全服务 RED 概览，异常置顶）+ AI 输入框合体；
2. **全局上下文条**：时间选择器 + 项目/集群过滤器固定顶栏，跨页面保留；cluster 永远是第一维度；
3. **看板策略**：一期嵌入 Grafana（Dashboards 页 iframe + token 免密），自研力量集中在排障链路；二期评估自研拖拽看板；
4. **深色主题优先**；虚拟滚动 + 分页游标应对百万级日志列表；
5. **一切皆可跳转**：页面中任何 `trace_id`、service、时间点都是链接，承载 DD-005 三信号关联动线的 UI 兑现。

补充说明：

**决策 2 的 "cluster 永远是第一维度" 不只是一个筛选器的位置问题。** SD-000 §7.1 把 `cluster_id` 定为多集群接入的第一维度，意味着**每一个查询请求都必须携带当前上下文条的 cluster 集合**，而不是由前端在返回结果里过滤。上下文条的状态因此是 URL 的一部分（见下），跳转时随链接传递——这正是"跳转不丢上下文"的实现机制：跳转 = 构造一个带完整上下文参数的 URL，而不是在内存里传状态。

由此产生一条对所有页面的硬要求：**页面状态必须可完整序列化进 URL**（时间窗、cluster/project 过滤、查询语句、facet 选择、列集合）。这条要求同时服务三件事——跳转不丢上下文、保存视图（§3.4）、AI 证据卡片的"点击回放"（§3.6）。三者本质是同一个能力。

**决策 3 的取舍代价要写明**：一期嵌入 Grafana 意味着看板页的交互风格、时间选择器、主题都与自研页面不一致，上下文条也无法穿透 iframe 自动同步。我们接受这个割裂，换取把两人的前端力量全部投到排障链路（检索 + Trace + 关联）上。缓解措施只有一条：从 Dashboards 页跳出到自研页面时，由外层把当前时间窗写进目标 URL；反向（自研 → Grafana）通过 iframe URL 参数传时间窗。两侧的 cluster 过滤如何映射到 Grafana 的模板变量，属于嵌入方案的细节，与免密方案一并列入 Open Questions。

**决策 4 的游标分页是后端契约，不是前端实现细节。** 百万级列表不能用 offset 分页——Doris 上深 offset 的代价随偏移线性增长，且数据持续写入会导致翻页错行。前端要求 IF-7 的列表类接口一律返回不透明游标（§3.9.3）。虚拟滚动只是渲染侧的配套：DOM 里始终只保留可视区若干行，滚动到底触发游标续拉。

**决策 5 的"一切皆可跳转"需要后端配合的地方**：可跳转的前提是列表行里有可跳转的值。而 §3.4 的投影规则决定了列表只返回"用户选中的列"。因此 `trace_id`、`service`、`cluster_id`、`ts` 这四个字段**无论用户是否把它们加进列配置，都必须在投影集合里强制包含**（可以不显示，但必须返回）。这条写进 §3.9 的 FE-03，是投影规则与跳转能力之间唯一的耦合点。

### 3.3 信息架构

> 原文迁自 v1.3 §17.3。

```
├── 总览（服务健康矩阵 + AI 对话框）
├── AI 助手（对话 / 巡检任务 / 报告历史）
├── 应用性能（服务目录 / 链路追踪 / 错误分析 / 服务拓扑 ← entity_topo，M3）
├── 日志（检索 / Live Tail / 模式聚类[二期]）
```

**与产品切分对齐（v2.1）**：一级导航按对外产品切开，而不是按底层引擎。「日志」= Logs 产品，「应用性能」= Traces 产品，「指标」= Metrics 产品。未开通的产品在导航中隐藏或置灰，**不因为 Logs 与 Traces 同 Doris 就合成一个「事件」入口**。总览 / 告警 / AI 是平台编排层，读取已开通产品的数据。

| 一级导航 | 数据来自 | 上线里程碑 | 备注 |

| 总览 | IF-7（服务 RED 概览，源自 DD-004 的 `service_metrics_1m`） | M3 | 矩阵依赖 span 派生指标，M2 期间首页内容不完整，见 §4 |

### 3.4 关键页面：日志检索（流量最大页）

> 原文与页面草图迁自 v1.3 §17.4。

```
┌──────────────────────────────────────────────────────────────┐
│ [查询框：关键字 + 字段过滤，可切 SQL WHERE 模式]  [时间] [Live]  │
├──────────────────────────────────────────────────────────────┤
│ ▂▃▅▂▇▅▃▂ 日志量直方图（框选缩窗，按 severity 堆叠着色）          │
├───────────┬──────────────────────────────────────────────────┤
│ Facets    │ 日志列表（虚拟滚动）                                │
│ ▸ service │ 10:23:01.234 ERROR payment-svc  pod-7f8…         │
│ ▸ cluster │   ↳ 展开: body 关键字高亮 + attributes JSON 树      │
│ ▸ severity│        [上下文 ±50条] [跳转 Trace] [创建 Facet]     │
│ ▸ trace   │ 10:23:01.118 INFO  order-svc    pod-3a2…         │
│ ▸ 动态字段 │ …                                                 │
├───────────┴──────────────────────────────────────────────────┤
│ 模式: [列表] [图表分析] [SQL 编辑器]      [保存视图] [创建告警]   │
└──────────────────────────────────────────────────────────────┘
```

三段式布局的职责划分是清晰的：**查询框做精确表达，直方图做时间定位，facet 做维度收敛**。三者作用于同一组过滤条件，任一处的操作都会同时刷新另外两处——框选直方图缩小时间窗，facet 计数随之重算；点击 facet 值追加过滤，直方图形状随之改变。这要求后端把"过滤条件"设计成三个接口共享的同一份参数结构（§3.9.3），而不是各自定义。

#### Facet 免注册

直接对半结构化列的子列查 top values，动态字段即点即用，用户无需事先注册字段。这是存储层半结构化建模红利在 UI 层最直接的兑现，也是与传统日志产品（要求预定义 schema 或字段映射）拉开差距的地方。

代价是不同字段的聚合成本差异极大，而这个差异**用户看不见**。因此 UI 必须把存储层的物理事实透出来，有两处联动：

- **平台锁定的语义约定字段在 facet 列表中置顶**。这些路径由 Schema Template 声明，一定被子列化且多数带路径级索引，聚合快、结果准。它们是 facet 列表的默认内容。
- **长尾字段标注"低频字段，聚合较慢"**。被 Top-N 字段配额取舍挤出子列化的路径，聚合要走通用路径，延迟高一个量级。UI 不阻止用户对它们做 facet，但必须在点击前给出预期，并在聚合超时后给出"缩小时间窗"的引导而不是一个红色报错。

这两条标注不是前端能自己判断的，**必须由 IF-7 在字段目录与 facet 返回中透出 `declared` / `subcolumnized` / `indexed` 三个布尔标志**（§3.9 FE-05、FE-06）。这是本页对后端最容易被忽略的一条需求：没有它，facet 列表只能按字母序平铺，"免注册"的红利会立刻退化成"随机踩坑"。

#### 展开单条看完整属性树

展开一行时显示完整的 attributes JSON 树，由存储层启用的编码模式原生支撑——原始 JSON 已由存储层维护，**无需在表里冗余一列原始 JSON，也无需前端额外请求**。

但"无需额外的原始 JSON 列"不等于"无需额外的请求"。按 DD-005 §3.2 的投影规则，列表页的 100 行只带用户选中的路径，展开行所需的完整文档不在其中。因此：**展开 = 发起一次返回 1 行的详情请求**（§3.9 FE-07），而不是从已有列表数据里取。这一点在交互上有两个后果：

1. 展开有网络延迟，需要骨架态；不能做成"纯前端展开"的即时动画。
2. 展开请求需要一个**稳定的单行定位键**。日志行没有主键，`ts` 不唯一。这个键由谁产生、编码成什么，v1.3 没有回答，记入 §4。

#### 列配置交互（与 DD-005 §3.2 的直接耦合）

这是本页最受存储物理特性约束的交互，展开说明。

DD-005 §3.2 的规则是：列表页只允许路径投影，**无法确定投影路径集合时拒绝而非放行**。把这条规则翻译成交互语言，得到四条设计结论：

1. **列配置是查询的一部分，不是视图状态。** 用户增删一列必须重新发起查询，不能在前端把已取回的数据做显示/隐藏。这与大多数表格组件的默认行为相反，需要在实现上明确。反过来说，调整列顺序、列宽属于纯视图状态，不触发查询。
2. **必须有默认列集合，且它必须是一个具体的路径清单。** 默认列为时间、severity、service、cluster、body 摘要、trace_id。"默认"不能实现成"不传 select，由后端决定"——后端在路径集合不明确时会拒绝，这是契约规定的行为。
3. **加列的入口是字段目录，不是自由文本框。** 用户从字段目录（FE-06）中选择路径加列，目录同时给出该路径的类型与是否子列化。允许手输路径作为高级用法，但手输路径不存在时后端会拒绝，UI 需要把这个拒绝渲染成"该路径在当前时间窗内没有数据，是否仍要添加"的可操作提示，而不是查询失败。
4. **保存视图必须包含列集合。** 否则恢复视图时无法构造合法查询。这一条直接决定了保存视图的数据结构（见下）。

另有一条前述的强制项：`trace_id`、`service`、`cluster_id`、`ts` 始终在投影集合内，即使用户把对应列隐藏了——否则行内的跳转链接无从构造。

#### 保存视图、上下文跳转、创建告警

- **保存视图** =（查询语句 + 时间窗 + facet 组合 + 列集合）的快照，可生成分享链接。时间窗需支持相对（"最近 1 小时"）与绝对两种保存方式：排障复盘要固定窗口，日常巡检要相对窗口。视图的持久化归属（IF-7 还是控制面）未定，记入 §4。
- **上下文跳转（±50 条）**：以当前行为锚点，取同一 pod / 容器上下相邻的日志。这是排障时使用频率最高的动作之一。它的语义比看起来复杂——日志行序在存储层没有天然定义，同一毫秒内的多行如何稳定排序、跨 tablet 时序是否可保证，需要 DD-002 与 DD-005 给出答案，记入 §4。
- **跳转 Trace**：行内 `trace_id` 为链接，携带当前时间窗与 cluster 上下文跳至 Trace 详情页（§3.5）。
- **创建 Facet**：把当前行中某个未在 facet 列表里的路径提升为常驻 facet，是"免注册"的手动补充入口。
- **创建告警**：以当前查询条件预填日志告警规则，用户只需补阈值与通知渠道。这要求检索条件与告警规则的条件表达式是同一套语法，否则预填会失真。

#### 查询框双模式

默认为关键字/字段语法（类 KQL），高级模式为 SQL WHERE。双模式的存在是为了覆盖两类用户：日常排障者不应该被迫写 SQL，而数据分析型用户需要表达能力的上限。两种模式之间能否互转（KQL → SQL 单向翻译是否够用）取决于最终语法形态，该决策与 DD-005 共同拥有，见 §4。

### 3.5 关键页面：Trace 详情

> 原文迁自 v1.3 §17.5。

页面主体为**火焰图 / 瀑布图双视图 + 服务耗时占比图例 + span 侧滑面板**。双视图不是两个页面：火焰图适合快速识别耗时最大的调用路径，瀑布图适合看时序关系与并发结构，两者共用同一份 trace 数据，切换不重新请求。

三处增强是本页与通用 trace 查看器的差别所在：

1. **span 侧滑面板的"相关日志"Tab**。点击任一 span，侧滑面板除 Tags / 耗时 / 状态外，增加一个直接加载该 span 相关日志的 Tab。由于日志与 span 同库，这是一次 JOIN 而非跨系统查询，能做到**零跳转加载**——用户不离开 Trace 页就能看到日志。这是整个产品最能体现"同库存储"红利的一处交互，优先级应高于其它增强项。关联条件为 `trace_id` 精确匹配，退化时按 `span_id`，再退化按 `service + ts±30s`（§3.9 FE-16）。

2. **"AI 分析此 Trace"入口**。把当前 trace 的上下文直送 AI 根因专家，结果以证据卡片形式回显（§3.6）。入口位置在瀑布图顶部工具栏，不在侧滑面板内——分析的对象是整条 trace 而非单个 span。

3. **跨集群 trace 标注**。当一条 trace 的 span 跨越多个 `cluster_id` 时，在瀑布图顶部提示"本 trace 跨 N 个集群，部分 span 可能因跨集群采样不一致而缺失"。

第 3 点需要说明它的性质：这是一条**启发式提示，不是缺失检测**。平台只能看到已收到的 span，无法判断哪些 span 本应存在而未到达；tail sampling 在各客户集群内独立决策，跨集群的采样结果天然可能不一致。因此 UI 的措辞必须是"可能缺失"，不能是"缺失 N 个 span"。这是 DD-001 已知缺陷在 UI 层的诚实兑现——把系统的能力边界告诉用户，好过让用户自己发现瀑布图不完整然后怀疑数据质量。

实现上只需要 trace 点查接口返回该 trace 涉及的 `cluster_id` 集合（§3.9 FE-15），前端判断集合大小是否大于 1。

### 3.6 关键页面：AI 助手

> 原文迁自 v1.3 §17.6。

- 对话流中每条结论渲染为**证据卡片**：卡片包含 AI 实际执行的 SQL / PromQL、返回的图表或表格，以及一个可点击的回放入口。巡检报告可整体转发。
- **租户级长期记忆**：runbook、历史故障、业务术语沉淀为租户知识库，在 AI 网关侧以 RAG 注入。UI 侧对应"知识库管理"入口（归属管理面）。
- 首页 AI 输入框支持 `@服务` / `@集群` / `@时间范围` 结构化引用，输入时给出补全候选。补全候选的数据源与全局上下文条相同（§3.9 FE-02）。

**证据卡片是 DD-007 防幻觉护栏在 UI 侧的落点，不是一个展示组件。** 它的设计要求只有一条，但必须硬性满足：**卡片上的每个结论都能回放到产生它的底层查询**。点击回放时，UI 跳转到对应的检索页 / Trace 页 / Metrics Explorer，并用原查询参数把页面完整还原——用户看到的是和 AI 看到的完全相同的数据，可以自行改条件继续挖。

这条要求反推出两件后端的事：

1. IF-7 的每次查询都要返回 `query_id`，AI 执行的查询也不例外（§3.9.3）。
2. 由 `query_id` 能还原出完整的查询参数与目标页面类型（§3.9 FE-28）。

如果做不到回放，证据卡片就退化成"AI 说它查了这些"，护栏形同虚设。因此把它写成对 IF-7 的硬需求，而不是 AI 层的内部实现。

### 3.7 关键页面：接入向导

> 原文迁自 v1.3 §17.7。这是新租户看到的第一个功能页面，它的完成度直接决定接入转化率。

三步流：

1. **选择集群类型**（K8s / VM / Serverless）；
2. **生成内嵌 Token 的 `helm install` 命令**，一键复制；
3. **实时数据验收页**——显示"已收到 N 条日志 / M 个 span / K 个 series，最近 10 秒"，数据来自摄入侧 metering 的实时反馈；验收通过自动弹出"去查看服务总览"。

第 3 步是这个向导的核心，也是与"贴一段文档让用户自己去试"的根本区别：**用户在离开向导之前就已经确认数据到了**。它要求摄入侧提供一个低延迟的按租户实时计数（§3.9 FE-30），窗口约 10 秒。这个接口不走常规检索路径——检索路径要经过落库，而落库延迟按 SLO-1 是 p99 10 秒，用它做实时反馈体验会很差。

验收页同时展示 **tail sampling 的实时保留率**。这条是为了回答新用户几乎一定会问的问题："为什么我发了 100 条 trace，只看到 10 条？"把保留率直接摆在验收页上，比事后在文档里解释有效得多。保留率数据依赖 tail sampling 链路，M3 才具备，M2 的验收页先只显示三类信号的到达计数。

**Agent 健康状态**在"接入管理 / Agent 状态"页持续展示，与向导共用同一数据源：每个集群的 Agent 最近心跳时间、版本、当前上报速率、是否有背压或丢弃。这是接入完成后唯一能回答"我的数据为什么少了"的页面，因此丢弃计数必须可见，不能只显示"健康/不健康"。

#### 3.9.2 M2 阻塞项小结

以下 10 条缺失则 M2 无法交付，是前端开工的前置条件，建议 DD-005 优先规格化：

**FE-02**（维度枚举）、**FE-03**（日志列表 + 投影 + 游标）、**FE-04**（直方图）、**FE-05**（facet top values + 物理标志）、**FE-06**（字段目录）、**FE-07**（单条整条读）、**FE-21**（PromQL 透传）、**FE-22**（指标元数据）、**FE-29**（Agent 状态）、**FE-30**（接入实时验收）。

其中三条的风险高于其余：

- **FE-06 字段目录**是全新能力，v1.3 全文没有任何对应设计。列配置与 facet 列表都依赖它，它不存在则日志检索页的两个核心交互（加列、facet）都只能退化为手输路径。
- **FE-05 的三个物理标志**（`declared` / `subcolumnized` / `indexed`）要求查询层把存储层的物理事实透出到 API，跨越 IF-6 与 IF-7 两个契约，需要 DD-002 与 DD-005 两位 owner 同时确认。
- **FE-30 不走检索路径**，它需要摄入侧提供一条旁路接口，这意味着它其实是 DD-001 的需求而非 DD-005 的，容易在两份文档之间漏掉。

另有两条虽标 M2 但**归属未定**，需先定归属再排期：FE-10（保存视图）、FE-23（Grafana 免密）。

#### 3.9.3 跨页面的通用要求

以下六条适用于 IF-7 的全部接口，不逐页面重复：

| 项 | 要求 | 理由 |
|----|------|------|
| **分页** | 所有列表类接口一律返回不透明游标，**不提供 offset 分页** | 深 offset 在列存上代价随偏移线性增长；持续写入会导致翻页错行（§3.2 决策 4） |
| **过滤条件的统一结构** | 检索、直方图、facet 三类接口共享同一份过滤条件结构 | 三者作用于同一组条件且需同步刷新；各自定义参数会在前端产生三套转换逻辑，且极易漂移（§3.4） |
| **时间窗参数** | 统一支持绝对区间与相对表达（如 `now-1h`），两种形式在保存视图与分享链接中都要能原样往返 | 排障复盘要固定窗口，巡检要相对窗口（§3.4 保存视图） |
| **`query_id`** | 每次查询返回唯一 `query_id`，与 DD-005 的查询审计记录同键 | 支撑 AI 证据卡片回放（§3.6）、用户反馈"这个查询很慢"时的定位、以及用量归因 |
| **错误语义可操作** | 拒绝类错误（扫描超限、时间窗过大、路径不存在、并发排队超时、租户配额耗尽）必须返回**结构化错误码 + 建议动作**，而非一段文本 | UI 要把拒绝渲染成"缩小时间窗"/"改走异步导出"/"稍后重试"的按钮。若只有文本，前端只能显示红色报错，查询治理的产品化引导就落不了地（DD-005 §3.1） |
| **查询可取消** | 长查询支持客户端主动取消，取消后释放后端配额 | 用户改条件重查的频率很高；不取消会让每租户并发配额被已被放弃的查询占满 |

#### 3.9.4 前端不需要的能力（显式声明）

为避免 DD-005 过度设计，以下能力前端一期**不需要**，不必为 UI 提供：

- 不需要跨租户查询——前端永远在单租户上下文内，租户由网关注入。
- 不需要写路径——UI 不写数据，管理动作一律走控制面 API。
- 不需要同步的大结果集导出——超限场景走异步导出任务（FE-13），前端只需任务状态与下载链接。
- 不需要 Doris 或 VM 的原生协议——前端只消费 IF-7 的 HTTP 接口，PromQL 也经网关透传而非直连 vmselect。
