## 3. 详细设计

### 3.1 定位与目标链路

AI 在本平台是**第三类产品接口**，与控制台 UI、Open API 并列（SD-000 §5 高层架构图中三者同层）。目标链路只有一条：

**自然语言提问 → 多智能体编排 → 直查实时遥测 → 携带证据的根因报告。**

> **以下三段理由为 v2.0 补写**（v1.3 §16 开篇只有上述一句定位）。补写内容不含新的技术决策，只是把既有定位的依据写出来，**需评审确认措辞**。

把 AI 定为一等接口而不是界面上的一个功能点，有三个可验证的后果，也正是本文档全部设计的出发点：

1. **它必须有自己的鉴权、配额与审计面**，而不是复用某个页面的会话。客户可以在 Cursor、Claude 或自有 Agent 里调用它（§3.5），此时根本没有"界面"存在。
2. **它必须与 UI 走同一条数据路径**。AI 查到的东西和用户在页面上能查到的东西必须完全一致，否则证据链回放（§3.6）会对不上。这是 IF-8 强制经查询网关的产品层理由，隔离只是其中一半。
3. **它的输出要能脱离对话框独立存在**。巡检报告要能转发、能存档、能被第二个人在三天后复核——所以报告的载体是带证据卡片的结构化产物，不是聊天记录。

**全景架构**（迁自 v1.3 §16.1，工具层归属按 v2.0 的模块边界标注）：

```
用户自然语言 │ Cursor / Claude / 客户自有 Agent（MCP 客户端）
        │
        ▼
┌──────────────────────────────────────────────┐
│ AI 网关（控制面，多租户）          【本文档 §3.2】│
│ 模型路由（BYOM：OpenAI 兼容接口）│ 租户级 token   │
│ 预算与限流 │ 会话审计                            │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐

└──────────────────┬───────────────────────────┘
```

### 3.2 AI 网关

AI 网关位于控制面，是所有 AI 调用的唯一入口，承担四项职责。

> **职责 1~3 的条目来自 v1.3 §16.1 与 §16.2 决策 5、6；每项下的展开说明为 v2.0 补写，需评审确认。**

**① 模型路由与 BYOM。** 对上统一 OpenAI 兼容接口，对下路由到三类 provider：平台托管模型、租户自带 key 的外部模型、租户私有化部署的模型。路由策略由 provider / model 两张配置表驱动（§3.7），租户可按技能或专家粒度指定模型。**不自训模型**（SD-000 N3 的类比条款），能力增量来自 BYOM 路由 + prompt 工程 + RAG。

**② 租户级 token 计量、预算与限流。** token 消耗按租户计量并进入 DD-006 的计费体系（§3.7）；预算耗尽时**自动降级为规则巡检**，而不是拒绝服务。注意这与查询侧配额是两套独立预算——一套约束 LLM 调用成本，一套约束遥测扫描量（DD-005 执行），**任何一套耗尽都不会自动豁免另一套**。

**③ 会话审计。** 记录谁、在什么时间、用哪个 provider 与模型、消耗多少 token、触发了哪些工具调用。AI 发起的遥测查询同样落进查询审计（X-002），因此一次 AI 会话在两个审计面上都留痕：AI 侧记录"问了什么、花了多少 token"，查询侧记录"查了哪个租户的多少数据"。

**④ 数据流向告知与租户开关（合规硬项）。** 送入模型的遥测内容已在摄入侧完成 PII 脱敏（F7），本模块不做二次脱敏、也不依赖查询侧遮蔽。BYOM 场景下必须在租户配置中明确告知"数据将发送至所选模型提供方"，并支持**租户禁用外部模型、只用私有化部署模型**。该开关的默认值须由 X-002 签字，见 §4。

**RAG 注入点在网关侧。** 租户知识库（runbook、历史故障、业务术语）以 RAG 方式在网关侧注入 prompt（v1.3 §17.6）。知识库的**页面与录入交互**归 DD-008，本模块提供注入点与租户隔离的存储。

### 3.3 Brain 编排器与专家体系

**编排流程**：任务拆解 → 并行派发专家 → 汇总为可转发报告。Brain 本身不直接调用工具，它决定"派谁去查什么"，由专家携带各自的技能去调工具。

**四类内置专家**（分类来自 v1.3 §16.1）：

| 专家 | 典型任务 | 主要依赖的工具（需求侧，见 §3.4） |
|------|----------|--------------------------------|
| 查询专家 | 把一句自然语言变成一次或多次结构化查询并解释结果 | `search_logs`、`query_metrics`、`get_trace`、`run_sql` |
| 巡检专家 | 按调度跑固定范围的健康检查，产出可转发的巡检报告 | `red_metrics`、`get_golden_metrics`、`list_alerts` |
| 根因专家 | 给定异常现象，沿拓扑与信号关联收敛到疑似根因 | `service_topology`、`get_neighbors`、`get_blast_radius`、`get_exemplars`、`get_trace`、`search_logs` |
| 运维问答专家 | 回答"这个指标什么意思""这个告警该怎么处理"，依赖租户知识库 RAG | 视问题落到上述任一工具，或不查询直接答 |

> **上表的"依赖工具"列为 v2.0 补写**——v1.3 只列了专家名称与工具清单两份独立列表，没有给出映射。该列是本文档向 DD-005 提需求时的优先级依据（被多个专家依赖的工具优先实现），**需在 IF-8 双签时确认**。

**可插拔技能（Skill）**：租户可注册自定义数字专家，把自己的排障经验固化成平台的一个专家。这是 AI 层长期的差异点，也是风险最集中的地方——**沙箱边界尚未定稿**（自定义专家能调用哪些工具、能否跨项目访问数据），见 §4。MVP（M4）是否包含租户自注册技能，取决于该问题的结论。

**来自 DataBuff 对标的结论**（v1.3 §15.2，AGPLv3，**仅作思路参考，禁止代码复用**）：多智能体编排（Brain 编排查询 / 巡检 / 运维专家）+ MCP 双向 + `config_ai_*` 配置表族这一组合，在一个真实产品里跑通过，验证了本节的形态选择；其表结构可参考。但它是**单租户**产品，表族没有租户维度（v1.3 §15.3 缺口 1），我们的全部配置表必须加 `tenant_id`（§3.7）。节奏也据此定：**M3 设计评审、M4 MVP**。

### 3.4 工具层的使用（消费 IF-8）

**本节只写需求侧。** 工具的实现、参数与返回的正式规格在 DD-005 §3.6；本节回答的是"本模块需要哪些工具、每个工具必须满足什么语义，否则 §3.6 的护栏无法兑现"。

**为什么是结构化工具而不是裸 SQL。** 工具层对 AI 暴露的是结构化工具，把常用动线固化下来，参数可校验、结果形状可预期，模型出错面比自由生成 SQL 小得多。`run_sql` 作为兜底保留，覆盖结构化工具没覆盖到的长尾问题，代价是**只读 + 行数与时间窗硬上限**（v1.3 §16.2 决策 3）。两者不是替代关系：结构化工具负责高频路径的稳定性，`run_sql` 负责能力不封顶。

**工具清单与语义要求**（清单迁自 v1.3 §16.1，"语义要求"列为本文档提出的需求）：

| 工具 | 本模块的消费场景 | 语义要求 |
|------|-----------------|---------|
| `search_logs` | 查询专家取证、根因专家收敛 | 支持时间窗 + 服务 + 关键字 + 字段过滤；**必须返回命中行数**（证据链字段之一） |
| `query_metrics`（PromQL） | 趋势判定、异常确认 | PromQL 透传，返回序列与实际执行的时间窗 |
| `get_trace` | 单条链路的完整瀑布 | 按 `trace_id` 点查；跨集群 trace 的缺失情况需在返回中可识别 |
| `service_topology` | 根因专家的拓扑上下文 | 给定时间窗返回服务级依赖边 |
| `red_metrics` | 巡检专家的健康基线 | 分钟级 RED，按服务聚合 |
| `list_alerts` | 巡检与根因的现状对齐 | 时间窗 + 状态过滤 |
| `get_neighbors` | 沿拓扑扩散排查 | 给定服务返回上下游邻居 |
| `get_blast_radius` | 影响面评估 | 给定疑似故障点推算受影响服务集合 |
| `get_golden_metrics` | 按实体语义取黄金指标，免去 AI 猜指标名 | 语义来自 Zmodel 统一语义层（DD-004） |
| `get_exemplars` | 指标异常点 → 链路的跳转 | 数据来自 `metric_exemplars`（DD-002，抽取规则见 IF-5） |
| `run_sql` | 长尾问题兜底 | **只读**；行数与时间窗硬上限；上限值由 DD-005 定，见 §4 OQ-3 |

**对所有工具共同的四条要求**（这四条是本文档对 IF-8 最硬的需求，其中第 1 条不满足则 §3.6 直接失效）：

1. **每次调用必须返回可回放句柄**：实际执行的语句、时间窗、命中行数。护栏 G1 的证据链就是由这三项拼出来的，工具不返回，AI 无从编造——也不该编造。
2. **工具参数不接受 `tenant_id`**。租户身份在查询网关侧由调用凭证注入（SD-000 §7.1），AI 既不传也不可传。这条让"AI 越权"在接口形状上就不可表达。
3. **超限必须返回结构化错误，不得静默截断**。扫描量、行数、并发任一超限时，Brain 需要知道"数据不完整"才能选择缩小时间窗重试；如果工具悄悄截断结果，AI 会拿着一份残缺数据下一个自信的结论——这是本设计里最危险的失败模式。
4. **工具集是契约**。新增工具、变更参数或返回结构，须 DD-005 与 DD-007 双签（SD-000 §7.2）。

**schema prompt 的构造**：对 `run_sql`，向模型提供**表结构 + 示例查询**（v1.3 §16.2 决策 3）。表结构的权威来源是 IF-6（DD-002 的表 schema 即对外公开接口）。v1.3 没有定义这份 prompt 的生成与更新机制，见 §4 OQ-4。

**走 IF-7 而非 IF-8 的部分**：AI 助手页面上的一些能力（如把 AI 给出的查询直接在检索页打开）实际调用的是查询 API 本身。IF-7 与 IF-8 的能力划线未定，见 §4 OQ-2。

### 3.5 MCP 双向集成

**对外：平台暴露 MCP Server。** 客户在自己惯用的 Agent 工具（Cursor、Claude 等）里直接查询其遥测数据，按平台 token 鉴权。这是把"第三类产品接口"落到实处的地方——客户不必进我们的控制台。

关键约束：**对外 MCP Server 的后端就是 IF-8 的工具层**，不是另一条路径。因此客户自有 Agent 同样自动继承租户注入、并发配额、扫描上限与审计，**不存在任何绕过查询网关的入口**。token 的签发、吊销与配额归 DD-006，与 Open API 同源。

**对内：挂载外部 MCP 作为虚拟数据源。** 把客户已有的系统（如 CMDB、工单）作为数据源接入诊断流程，让根因分析能用上平台以外的上下文。

这里有一个 IF-8 没有覆盖的边界：**外部 MCP 返回的数据不经过我们的查询网关**，它的审计、租户边界与数据流向约束目前没有归属。v1.3 只写了"可挂载"，没有写约束。这条必须在 M3 出结论并由 X-002 签字，见 §4 OQ-5。**在结论出来之前，不要把对内挂载排进 MVP。**

### 3.6 防幻觉护栏

排障场景下 AI 犯错的成本是不对称的：一个**带证据**的错误结论，值班工程师五秒钟就能证伪；一个**不带证据**的正确结论，没人敢按它操作。所以护栏的重点不是让模型少犯错，而是让每个结论都可被快速证伪。

五条护栏（G1~G4 来自 v1.3 §16.2 决策 4，G5 为文档集骨架阶段补入的表达约束）：

| # | 护栏 | 内容 |
|---|------|------|
| **G1** | 结论必须携带证据链 | 每条结论附带**执行的 SQL/PromQL、时间窗、命中行数**。这三项由工具返回（§3.4 要求 1），不是模型生成的 |
| **G2** | 证据可回放 | 报告中的证据可点击回放到底层查询，用户能用同一条件自己再查一遍。回放粒度见 §4 |
| **G3** | 一期只读原则 | 重启、回滚类运维动作**只生成建议，不执行** |
| **G4** | 执行走人工审批 | 任何落到生产的动作都经人工审批，AI 不持有执行通道（与 §3.10 非目标 1 同一条边界的两种表述） |
| **G5** | 无证据时明说查不到 | 工具返回空结果或超限错误时，输出"在该时间窗内未查到支撑数据"并给出已执行的查询，**不得据经验补全结论** |

G5 与 §3.4 要求 3 是一对：工具层保证超限时报错而不是静默截断，AI 侧保证拿到错误时如实说明。缺任何一半，另一半都不成立。

### 3.7 数据模型与计量

**AI 配置表族，全部带 `tenant_id`，存控制面库**（SD-000 G2；v1.3 §16.2 决策 1）。表族由七张表构成：

| 表 | 职责 |
|----|------|
| provider | 模型提供方：平台托管 / 租户自带 key / 私有化部署，含接入地址与凭证引用 |
| model | 具体模型及其路由策略与计价参数 |
| skill | 可插拔技能定义 |
| expert | 专家定义（内置 + 租户自定义），绑定其可用技能与工具 |
| task | 巡检 / 诊断任务的定义与调度 |
| session | 会话 |
| message | 会话内的消息，含证据链引用与 token 消耗 |

三点说明：

- **表名前缀与列级 schema 尚未锁定。** v1.3 只给了表族的七个名字，并注明 DataBuff 的 `config_ai_*` 表结构"可参考"（§15.2）。本文档不预设列定义，M3 设计评审时给出。
- **租户维度不是可选项。** 这是我们与被对标产品的结构性差异（v1.3 §15.3 缺口 1）：单租户产品的 AI 配置表天然不需要 `tenant_id`，而我们一旦漏掉任何一张，就是一处跨租户串扰。
- **凭证按控制面的既有规则处理**：租户自带的模型 key 属于凭证，存储方式遵循 X-002，不在本文档定义。

**计量**：模型 token 消耗按租户计量，进入 DD-006 的计费体系——它是 v1.3 §9.3 四个计费维度中的第四项（摄入 GB + 存储 GB·月 + 查询扫描量 + **AI token**）。**预算耗尽自动降级为规则巡检**，保证租户不会因为 AI 预算花完而失去基本的巡检能力。

一次 AI 会话同时产生 AI token 与查询扫描量两类计量事件，两者是否都计费、如何避免重复计价，v1.3 未说明，见 §4 OQ-6。

---

### 3.8 SQL 底座的长期红利

底座是标准 SQL，**自然语言转查询的准确率天花板显著高于 LogsQL / TraceQL 这类私有查询语言**——公开语料里 SQL 的数量级优势是私有 DSL 补不回来的，而 NL→DSL 的准确率直接决定 `run_sql` 兜底路径的可用性。

这是 SD-000 §1 / §9 选型决策在 AI 时代的**延迟回报**：当初选 Doris 作为 Logs/Traces 统一底座，主要理由是关联查询降级为一次 JOIN 和成本模型，AI 红利在当时并不是决策依据。

需要说清楚的是本节的定位：**它是既有选型的一项额外收益，不构成重开选型的依据**。SD-000 §9 的引擎选型已定稿，Metrics 侧的 PromQL 路径同样不因本节而改变——`query_metrics` 面对的仍然是 PromQL，AI 在这条路径上没有 SQL 红利可吃。

### 3.9 二期：观测 AI 应用

平台既是 AI-native 的，也应当是 **AI 应用的观测平台**。二期支持 OTel `gen_ai.*` 语义约定的 span：LLM 调用链、token 消耗、prompt 版本、Agent 拓扑。

`gen_ai.*` span 本质是普通 span，**与 spans 表共用，零额外存储成本**（v1.3 §16.2 决策 7）。但"零额外成本"有一个前提：这些路径要么走 VARIANT 的通用路径、不额外占用配额，要么由 DD-002 在 Schema Template 中显式声明为 typed path——后者会占用字段配额。**该前提是否成立由 DD-002 判定，本文档不做假设**，见 §4 OQ-7。

表结构与索引属于 DD-002（本文档 §0 非范围）。本模块在二期需要提供的是 AI 应用视角的查询与看板需求，届时以需求形式提给 DD-002 与 DD-008。

---

### 3.10 非目标（一期）

- 不做自动根因修复的执行闭环（只做诊断与建议）；
- 不自训模型（BYOM 路由 + prompt 工程 + RAG over 告警历史 / 工单）；
- 不做自然语言直接写库 / 改配置的通道。

第三条与 §3.6 的 G3/G4 是同一条边界：**AI 在一期不持有任何写路径**，无论是对遥测数据、对平台配置，还是对客户的生产系统。
