## 3. 详细设计

### 3.1 统一查询网关

无状态服务，核心职责六项：

1. **认证鉴权**：SSO / AKSK → 解析租户 → 强制注入 `tenant_id` 过滤（SQL 改写 + vmauth 路由）。**用户永远不直接接触底层引擎凭证。**
2. **协议适配**：
   - PromQL / Grafana datasource API → 透传 vmselect；
   - 日志 / Trace 查询（自研 DSL 或直出 SQL 子集）→ SQL 生成器 → Doris FE（MySQL 协议）；
   - Trace 点查 → 按 `trace_id` 取整条链路 + 客户端瀑布渲染；
   - SQL 生成器的 VARIANT 投影规则见 §3.2（硬性约束）。
3. **查询治理**：每租户并发配额 + 排队；扫描行数 / 时间范围硬上限（超出引导用户缩小窗口或走异步导出）。
4. **审计与计量**：每条查询记录（租户、扫描量、耗时），供计费与容量分析（DD-006）。
5. **SQL 解析与改写**：内嵌 `datafusion-sql` 作为解析库（租户谓词注入、危险查询拦截），替代手写解析器。**注意：这是把 DataFusion 当库用，与 §3.5 放弃自研 DataFusion 集群不矛盾。**
6. **无状态**：Deployment + HPA，无会话状态；查询排队队列在实例内，实例故障时排队请求失败重试即可。

#### 租户注入的实现要点

租户过滤**不是在应用层拼字符串**，而是在 SQL 解析后的 AST 上强制附加谓词，理由有二：

- 字符串拼接无法防御嵌套子查询、UNION、CTE 中的越权访问；
- AST 改写可以在同一处同时完成危险查询拦截（如无时间范围的全表扫描、`SELECT *`）。

这也是选择内嵌解析库而非手写解析器的原因——手写解析器在遇到复杂 SQL 时的漏判就是隔离漏洞。

### 3.2 SQL 生成器的硬性规则（VARIANT 投影）

官方明确不建议直接 `SELECT variant_col`：未启用 DOC mode 时这会扫描该列所有子字段。本设计已启用 DOC mode（DD-002 §3.3），整条文档读被优化到数量级级别，但**列表页一次返回约 100 行，整条读 100 份 attributes 仍远贵于只投影用户可见的几个路径**。

因此规则不是"DOC mode 解决了就不用管"，而是：

| 场景 | 允许的投影 | 理由 |
|------|-----------|------|
| 日志列表页 / Trace 列表页（返回 ~100 行） | **只允许** `v['path']` 路径投影，且路径集合来自前端当前显示的列 | 逐行整条读是列表页延迟的主要来源 |
| 单条日志展开 / 单 span 详情（返回 1 行） | 允许整条读 `SELECT log_attributes` | DOC mode 的目标场景，正是为此启用 |
| Trace 瀑布（按 `trace_id` 取整条链路，几十到几百 span） | 允许整条读 | 瀑布需要完整 attributes；这是 DD-002 为 spans 选 DOC mode 的主要依据 |
| 聚合 / GROUP BY | 只允许路径投影 | 同理，且应尽量落在已建路径级索引的路径上 |

**实现**：SQL 生成器在构造 `SELECT` 列表时，若检测到裸的 VARIANT 列名且预估返回行数 > 1，**改写为路径投影**；无法确定路径集合时**拒绝并返回明确错误，而不是放行**。同时禁止 `SELECT *`。

这条规则的存在本身也说明一件事：**DOC mode 不是"整条读变免费"，只是把它从不可接受变为可接受。**

> **与 DD-008 的联动**：列表页的列配置交互必须产出明确的字段路径集合，否则 SQL 生成器无法构造投影。这是前端交互设计的硬约束，不是可选优化。

### 3.3 三信号关联（产品差异化核心）

```
                 【主动线：指标异常 → Trace → Logs】
指标看板/告警异常点
   │ ① 查 metric_exemplars（DD-002 §3.5）：同 metric + service + 时间窗，取代表性 trace_id
   │ ② 若无 exemplar 命中 → 兜底动线（见下）
   ▼
Trace 瀑布（spans 表，trace_id 点查）
   │ 点击某 span → 携带 (trace_id, span_id, ts±30s, service)
   ▼
相关日志（logs 表：WHERE trace_id=? OR (span_id=?) OR (service=? AND ts BETWEEN ...)）
   │ 反向：日志中发现 trace_id → 一键跳 trace
   ▼
关联指标（service + 时间窗 → service_metrics_1m 或 VM PromQL）
```

#### 兜底动线（不依赖 exemplar）

指标异常点 →（`service` + 时间窗）→ 查 spans 表取该窗口内的慢 trace 与错误 trace 列表 → 用户从列表进入瀑布。

这条动线的价值不止于兜底：

1. 它完全不依赖 exemplar 链路，因此 SD-000 Q-5 的验证结果**不会阻塞 G4 交付**；
2. 由于 DD-001 的 tail sampling 策略**全量保留错误 trace 与慢 trace**，这个列表在排障场景下几乎总是非空且高相关；
3. 体验上给出的是"候选集"而非"单条"，在很多场景比 exemplar 的单点跳转更有用——Datadog 也采用类似交互。

#### SLO-9 的测量方法

「关联跳转有效命中率 ≥ 70%」需要可测量的定义，否则无法验收：

- **分母**：用户从指标异常点发起关联跳转的次数；
- **分子**：跳转后**目标页面非空**（exemplar 命中并成功加载 trace，或兜底列表非空）且用户**未在 5 秒内返回**的次数；
- 埋点在查询网关侧记录跳转请求与结果行数，在前端侧记录返回行为，两者按会话关联。

> **本段为 v2.0 新增**（单体文档只给了 SLO 数值没给测量方法），需与 DD-008 owner 确认埋点可行性。

### 3.4 告警引擎

| 告警类型 | 执行路径 | 延迟 |
|----------|----------|------|
| Metrics 阈值 / 异常 | VMAlert（规则存控制面，渲染后下发） | < 1 min |
| 日志关键字 / 模式 | 控制面调度器 → Doris 轮询 SQL（如 `count() where body match 'ERROR' group by 1m`） | < 2 min |
| Trace 服务质量（错误率 / 延迟） | 查 DD-004 的 `service_metrics_1m` 物化视图，**不扫原始 span** | < 2 min |
| 缺席告警（数据断流） | 摄入侧计数器 + VMAlert `absent()` | < 3 min |

- 告警状态机（触发 / 恢复 / 静默 / 抑制）复用 Alertmanager 语义，通知渠道自研适配；
- **告警查询走独立 Doris 计算组**（DD-002 §3.1 的 `alert` 组），与用户即席查询物理隔离，保证告警延迟 SLO 不被分析查询挤占。

### 3.5 冷层查询：Doris Iceberg Catalog

**决策**：用 Doris 4.0.8 的 Iceberg Catalog + 一个独立的 `cold` 计算组，**零新增技术栈**。早期版本计划为 180 天冷查询自建一套 Apache DataFusion executor 池，已放弃。

**为什么改**：

1. 自建方案要新建的不只是 DataFusion executor，还有 Iceberg catalog 对接、租户谓词注入、限流队列、弹性伸缩——这些在 Doris 侧已经存在且经过热路径验证，重做一遍是纯粹的重复投入；
2. Doris 的 multi-catalog 能直接查 Iceberg 外表，是其相对成熟的能力；存算分离模式下再开一个 `cold` 计算组做物理隔离，天然满足"冷查询不拖垮热路径"；
3. **开放性卖点完全不受影响**——它来自存储格式（Parquet / Iceberg，客户可用 DuckDB / Trino / Spark 自取，支持 BYO-bucket），不来自查询引擎。这一点在早期论证里被混淆了。

**保留的 DataFusion 用法**：查询网关内嵌 `datafusion-sql` 作为 SQL 解析 / 改写**库**（§3.1 第 5 条）。把它当库用是合理的，当分布式查询系统自建则不是。

**明确不做的两件事**：

- **不用任何联邦引擎替换热路径**：日志检索依赖 Doris 倒排索引 MATCH 下推，联邦查询无法下推该谓词，拉数出来扫性能不可接受；PromQL 由 VM 承担；
- **不基于 DataFusion 自研数据库**：GreptimeDB / InfluxDB 的实践表明，DataFusion 只提供引擎积木，实时摄入、compaction、缓存、分布式执行均需以年计的自研投入。

**产品侧要求**：冷层查询在 UI 上必须标注"归档查询"并给出延迟预期（秒级~十秒级），走独立限流队列。

**交付窗口**：归档从 M3 开始写入，冷查询计算组在 M3 末同步上线（因为不需要自研，不再需要推到 M4）。

### 3.6 MCP 工具层（IF-8）

**归属说明**：工具层本质是查询网关的一个适配器——它把网关能力翻译成 AI 可调用的结构化工具。因此**实现归本文档，需求与语义要求归 DD-007**。

**核心约束**：AI 发起的每条查询自动继承租户谓词注入、并发配额、扫描上限与审计。**这是多租户 SaaS 的 AI 与单租户 APM 产品的本质差异**——AI 绝不直连 Doris / VM。

| 工具 | 底层路径 | 关键约束 |
|------|----------|----------|
| `search_logs` | logs 表检索 | 强制时间窗；返回行数上限 |
| `query_metrics` | PromQL 透传 vmselect | 强制租户路由 |
| `get_trace` | 先查 `trace_summary` 摘要，再按需拉 span 明细 | 两段式，降低 AI 上下文 token 消耗 |
| `service_topology` | DD-004 的 `entity_topo` | 扇出剪枝 |
| `red_metrics` | DD-004 的 `service_metrics_1m` | 不扫原始 span |
| `list_alerts` | 告警状态存储 | — |
| `get_neighbors` / `get_blast_radius` | Zmodel 图遍历（DD-004 §3.4） | 跳数与扇出上限 |
| `get_golden_metrics` | Zmodel 语义工具 | — |
| `get_exemplars` | `metric_exemplars` 表 | — |
| `run_sql` | 只读兜底 | **行数与时间窗硬上限**，禁止 DDL / DML |

`run_sql` 是兜底而非主路径：结构化工具覆盖不到的长尾问题才用它，配合表结构 + 示例查询的 schema prompt。它的存在依据是 SD-000 §9 的选型红利——标准 SQL 底座让自然语言转查询的准确率天花板显著高于私有查询语言。

#### 3.7.1 通用约定

| 项 | 规则 |
|----|------|
| 版本化 | 路径前缀带版本号；破坏性变更须新开版本并保留旧版本至少一个发布周期 |
| 认证 | 所有接口经同一鉴权中间件解析租户，**请求体中任何 `tenant_id` 字段一律忽略** |
| 时间范围 | **所有查询接口强制要求时间范围**，无时间范围的请求直接拒绝 |
| 分页 | 统一使用**游标分页**（不用 offset），游标内编码排序键位置。理由：日志列表动辄百万行，offset 分页在深翻页时代价不可接受 |
| 错误语义 | 区分四类：参数错误（不可重试）、配额超限（可重试，带退避提示）、超时（可重试）、内部错误（可重试）。每类给出明确错误码与用户可读文案 |
| 限流 | 超配额返回配额类错误并携带当前水位与建议重试时间，**不静默排队到超时** |
| 审计 | 每次调用记录租户、接口、时间窗、扫描行数、耗时 |

#### 3.7.3 三条设计约束的理由

- **「显示列路径集合」是日志检索接口的必填参数**，不是可选优化。它直接对应 §3.2 的投影规则：前端不告诉网关要哪些字段，网关就无法构造路径投影，只能整条读或拒绝。这把存储层的物理约束一路顶到了 API 契约上——**看起来别扭，但它是真实的，藏起来只会让列表页在上线后慢得没法救**。为降低前端负担，约定 `ts` / `service` / `cluster_id` / `trace_id` 四个字段**无论是否在请求路径集合中都强制返回**。
- **关联接口把主动线与兜底动线合并为一个接口**，由服务端决定走哪条并在返回中标明。理由：前端不应该知道 exemplar 是否可用（这是 SD-000 Q-5 的待验证项），把选择权留在服务端，验证结论出来后前端无需改动。
- **`query_id` 必须从 M2 起就在所有查询接口的返回中存在**，即使 M4 才做 AI 结论回放（DD-008 FE-28）。它同时是审计、计量与回放的关联键；等到 M4 再加会导致历史查询无法回溯，属于典型的"晚加一个字段、丢掉两年数据"。

#### 3.7.4 两处待定义的基础设施（v2.0 识别）

DD-008 的需求清单暴露出两个基础问题，v1.3 完全没有交代，它们卡住多个接口：

1. **单行稳定定位键**。日志行无主键、`ts` 不唯一，但「展开单条」与「上下文 ±50 条」都需要唯一定位某一行。候选方案：由 DD-002 在写入时生成行内唯一标识，或由查询层用 `(分区, tablet, rowset, 行号)` 合成不透明游标。前者改表结构（IF-6 破坏性变更），后者在 compaction 后会失效。**须与 DD-002 owner 共同决策**，见 Q5-7。
2. **流式能力**。信息架构中有 Live Tail 入口，但查询层从未定义任何流式或长轮询能力。三种实现路径（独立流式通道 / Kafka 旁路 / 高频轮询降级）对 SLO 与成本的影响完全不同，**其中 Kafka 旁路会绕过查询网关，与 §3.1 的租户隔离收口原则冲突**，需谨慎评估。见 Q5-8。
