## 3. 详细设计

### 3.1 摄入网关层

摄入网关是平台唯一的数据入口，也是租户身份注入点。它承担五项职责：TLS 终止、Token 鉴权（查本地缓存的租户映射，控制面异步同步）、租户级限流（令牌桶，按 bytes/s 与 events/s 双维度）、**PII 脱敏规则执行**、协议归一（remote-write → OTLP metrics）。

**无状态与部署形态**：网关不持有任何会话或缓冲状态，按 SD-000 §5.1 分层原则 3 以 Deployment + HPA 部署，跨三个 AZ 打散，任一 AZ 整体失效时剩余副本承接全量流量。租户映射表与脱敏规则来自控制面的异步同步，本地缓存是权威读取源——控制面不可用时按最后一次同步的配置继续鉴权与限流（fail-static，IF-9），**不得因配置读取失败而拒绝数据**。

**租户路由**：`tenant_id` 由 token 反查得到并强制注入，下游任何环节不得信任客户端自报值（SD-000 §7.1）。集群级 Token 同时带出 `cluster_id`，两者一并注入后续管线。

**限流行为**：超限返回 429 + `Retry-After`；对日志类负载同时下发"客户端降采样"信号，避免无意义重试风暴。**爆炸半径控制**：每租户独立限流桶，大租户打满只影响自己（对应 SLO-7）。

**PII 脱敏执行点位**：脱敏在摄入网关执行，**早于 Kafka**，确保敏感数据不落盘。规则库、动作语义（`redact` / `hash` / `drop`）与合规论证由 X-002 定义，本模块只提供执行点位与规则命中数指标。需要在本文档记录的是一条性能约束：**正则扫描在 10.5 万 EPS 峰值下是实打实的 CPU 成本，M1 压测必须包含开启脱敏后的吞吐衰减实测，规则数上限按实测结果设配额。**

#### IF-1 错误码语义表

> **本表为 v2.0 新增。** v1.3 只有原则性描述（"下游不可用时必须返回可重试错误，不得吞错返回成功"），没有具体码表。下表是依据 v1.3 §6.1 的限流行为、§6.4.3 的背压强制要求和 SD-000 §7.3 推导出来的，**需在架构评审中确认，并与客户侧 SDK/Agent 的默认重试策略对齐**。

整条兜底链路（客户侧持久队列 → 重发）只有在每一跳都如实返回可重试错误时才成立。因此下表把故障分成两类并分别固定语义：**客户端错误不可重试**（重试只会制造毒消息风暴），**平台侧错误必须可重试**（重试是数据不丢的唯一途径）。

| # | 故障类别 | gRPC status | HTTP | `Retry-After` | 客户端预期行为 |
|---|---------|-------------|------|--------------|---------------|
| E1 | Token 缺失、无效或已吊销 | `UNAUTHENTICATED` | 401 | — | **不重试**，丢弃并告警；接入配置错误 |
| E2 | 租户或集群被停用（欠费、退租、熔断） | `PERMISSION_DENIED` | 403 | — | **不重试**，丢弃并告警 |
| E3 | 请求体无法解析、不符合 OTLP / remote-write 规范 | `INVALID_ARGUMENT` | 400 | — | **不重试**，丢弃并计数；重试无法改变结果 |
| E4 | 单请求体积超过上限 | `INVALID_ARGUMENT` | 413 | — | **不重试**，客户端拆小 batch 后再发 |
| E5 | 租户限流超配额（bytes/s 或 events/s） | `RESOURCE_EXHAUSTED` | 429 | 有 | **退避重试**，数据进本地持久队列；日志类负载同时按下发信号降采样 |
| E6 | 下游 Kafka 不可用或写入超时 | `UNAVAILABLE` | 503 | 有 | **必须重试**，数据进本地持久队列 |
| E7 | 下游 Collector / metrics-ingest `sending_queue` 满（背压） | `RESOURCE_EXHAUSTED` | 429 | 有 | **必须重试**，同上 |
| E8 | 网关自身过载（`memory_limiter` 触发、副本重启中） | `UNAVAILABLE` | 503 | 有 | **必须重试**，同上 |
| E9 | 批内部分记录被脱敏规则 `drop` 或因字段非法被拒 | `OK` + partial success | 200 + partial success | — | **不得整批重发**，只按响应中的 `rejected_*` 计数告警 |

两条不可协商的规则：

1. **E6/E7/E8 绝不允许折叠成 200。** 任何一跳"吞掉错误返回成功"，客户侧的 `file_storage` 持久队列就永远不会被触发，兜底退化为静默丢数——这正是 SD-000 §7.3 把这条写进契约而不是藏在模块内部的原因。
2. **E9 走 OTLP partial success 而不是整批失败。** 单条记录的问题不应导致整批重发，否则脱敏规则一旦命中高频字段，就会把客户端拖进重试循环。

### 3.2 平台侧 OTel Collector Gateway 集群

**流水线**：

```
receiver(otlp) → memory_limiter → tenant_enricher → batch → kafka_exporter(encoding=otlp_proto)
```

processor 顺序有实际含义：`memory_limiter` 必须排在最前，它是过载时产生 E8 的触发点；`tenant_enricher` 在 `batch` 之前，保证攒批后的每条记录都已带齐租户维度，下游不需要再回查。

**平台侧不做任何 trace 采样决策。** 采样已在客户集群的 cluster-gateway 以 tail sampling 完成（§3.7），平台侧 Collector 退化为富化 + 转发。

**富化**：注入 `tenant_id`、`k8s.cluster/namespace/pod`、环境标签。所有富化在摄入侧完成，查询侧不做 JOIN 维度表——宽表范式，拿空间换查询确定性。

**编码约定**：kafka exporter 使用 `otlp_proto`（而非 JSON），由下游 `otlp-loader` 解析。这比 JSON 体积小约 30%、解析快数倍，且 schema 由 OTel proto 定义保证，不会因字段顺序或转义问题出错。

**队列策略**：`sending_queue` 满时**拒绝新请求，而不是丢弃队首**。默认的丢队首行为会把一次下游抖动变成一次静默数据丢失，且客户端收到的是 200——这正是 §3.5 端到端背压要堵住的那个洞。拒绝新请求则转化为 E7，错误沿链路逐跳回传到客户侧持久队列。

### 3.3 Kafka 缓冲层

#### IF-2 正式定义

> **本节的 topic/分区正式定义为 v2.0 新增。** v1.3 的相关事实散落在 §4.2（扩容推演）与 §6.3（topic 设计），从未以契约形式汇总。下表把它们收敛为一张表，数值全部取自 v1.3，**生产者侧的 `acks` / `min.insync.replicas` 两行是本次补齐的缺项，需评审确认**（见 §4 OQ-5）。

| 项 | `logs.raw` | `traces.raw` |
|----|-----------|-------------|
| 承载信号 | Logs | Traces |
| partition key | `tenant_id + service`（保证同租户同服务有序） | `trace_id` |
| 分区数（1.5 TB/天 开局） | **12** | **6** |
| 分区数（10 TB/天 终点） | **24** | **12** |
| 消息编码 | OTLP protobuf（`otlp_proto`） | 同左 |
| 压缩 | lz4 | 同左 |
| 副本因子 | 3 | 3 |
| `retention.ms` | **12 小时** | 12 小时 |
| 生产者 `acks`（新增） | `all` | `all` |
| `min.insync.replicas`（新增） | 2 | 2 |
| 消费方 | `otlp-loader` consumer group | 同左（共用 loader 二进制，按 topic 配置不同映射） |

**Metrics 不过 Kafka**（SD-000 §5.1 分层原则 1 的例外），路径见 §3.5。

**按信号分 topic、租户以 partition key 隔离**，而不是按租户分 topic：SaaS 规模下按租户分 topic 是元数据爆炸反模式，已否决。

**分区数为什么起步就超配**：logs 12 分区起步时，当前峰值 10.5 万 EPS 实际只需 3 个，多出的是为 10 TB 时的 24 分区预留消费并行度。分区只增不减，且 `otlp-loader` 的副本数上限等于分区数，起步留余量等于给 HPA 留出扩容空间。注意 partition key 含 `tenant_id`，超大租户单 key 可能造成分区热点，超过单分区容量时在 key 中引入 bucket 后缀打散。

**保留 12 小时（v1.2 由 3 天下调）**：v1.1 的 3 天保留占用 15 TB，是 Doris 热窗口（2.8 TB）的五倍，成为仅次于归档层的第二大存储项，成本倒挂。而 3 天回放的必要性经不起推敲——Doris 故障在存算分离下数据在 S3 不丢、BE 重建即可；误删有归档层；新引擎 PoC 可从归档层灌数。真正需要 Kafka 回放的是「落库链路停摆到恢复」的窗口。12 小时后 Kafka 占用降至约 1.4 TB，从第二大存储项变为可忽略项。

#### 保留期 12 小时的三层告警阶梯

保留期就是落库链路的**故障恢复预算**。12 小时意味着一次跨夜或周末的 `otlp-loader` / Doris 写入故障如果无人响应，最老的数据会开始被 Kafka 删除且不可恢复。因此保留期下调必须与下列三条配套，**缺一条就不要下调**：

| 项 | 阈值 | 动作 |
|----|------|------|
| `otlp-loader` 消费 lag（扩容触发） | > 60s 持续 5 分钟 | HPA 自动加副本 |
| **Kafka 最老未消费消息年龄** | **> 2 小时** | **P1 呼叫值班**——留出 10 小时人工处置余量 |
| 同上 | > 6 小时 | 升级并启动降级预案（X-001），必要时临时上调 `retention.ms` 争取时间 |

`retention.ms` 是可在线修改的 topic 配置，紧急时上调即可延长窗口（受磁盘水位约束，容量模型已按 0.5~1 TB/节点规划，留有约一倍余量可临时扩到 24 小时）。**这条应当写进值班 runbook。**

#### 保留期与 `label_keep_max_second` 的耦合

Doris 对 Stream Load label 的去重依赖 `label_keep_max_second`（默认 3 天），它**必须 ≥ Kafka 保留期**，否则回放时 label 已过期、幂等失效、重复数据直接落库。默认值 3 天对 12 小时保留期有充分余量，即便紧急上调 `retention.ms` 到 24 小时仍然成立。但这两个参数是一对，**紧急上调 `retention.ms` 时要同步检查这条约束**，写入部署检查清单。该约束属于 IF-3 的一部分，变更须 DD-002 双签。

#### 两个失效窗口不要混为一谈

| 故障类型 | 兜底组件 | 窗口 |
|---------|---------|------|
| **落库链路故障**（`otlp-loader` / Doris 写入不可用） | Kafka 保留期 | 12 小时 |
| **平台摄入入口故障**（网关 / Collector 不可用） | 客户侧 cluster-gateway 的 `file_storage` 持久队列 | **≥2 小时** |

**后者才是更紧的那个约束。** 入口一旦不可用，Kafka 的 12 小时完全帮不上忙——数据还没进来。这意味着对摄入入口可用性的要求高于落库链路，15 分钟的月度错误预算应优先保护网关与 Collector 这两跳。

**其他约定**：若后续确需长保留，用 Kafka 分层存储（KIP-405）把冷段放 S3，而不是加本地盘。**不启用精确一次（EOS）**：摄入链路采用「at-least-once + Stream Load label 幂等 + DUPLICATE 模型容忍微量重复」（§3.4），EOS 的吞吐代价在日志场景不值得。

### 3.4 写入路径

| 路径 | 方案 | 理由 |
|------|------|------|
| Logs → Doris | **自研 `otlp-loader`**（无状态 Go consumer，Kafka → OTLP protobuf 解析 → 展开 → 批量 Stream Load） | Routine Load 不可行，见下 |
| Traces → Doris | 同上，共用 loader 二进制，按 topic 配置不同的展开与建表映射 | 同上 |
| Metrics → VM | **直连 vminsert（不过 Kafka）**，前置无状态 metrics-ingest 服务做写入整形与 exemplar 抽取 | metrics 回放价值最低；省掉 Kafka 上绝大部分存储压力 |

#### 为什么不能用 Routine Load

OTLP 的 JSON/protobuf 结构是三层嵌套数组——`resourceLogs[].scopeLogs[].logRecords[]`（traces 同理 `resourceSpans[].scopeSpans[].spans[]`）。**Routine Load 的 `jsonpaths` 只能做扁平字段映射，无法把一条 Kafka 消息展开成 N 行。** v1.1 曾写的「Routine Load + 预定义 JSON 展开，span 数组拍平为行」没有对应的 Doris 能力支撑，会在 M1 第一周撞墙，且影响的是 logs 与 traces 两条主链路。这是 SD-000 §5.1 分层原则 2 的全部理由。

#### `otlp-loader` 设计

```
Kafka consumer group（offset 即全部状态，服务本身无状态）
  → 解析 OTLP protobuf（官方 go.opentelemetry.io/proto 反序列化）
  → 展开：ResourceX 的 resource attributes 下推到每一行，输出扁平行
  → typed path 类型规范化 + JSON key 长度校验
  → 攒批：满 64 MB 或满 2s 触发，取先到者
  → Stream Load（HTTP PUT → FE/BE），format=json，strip_outer_array=true
  → 成功返回后才 commit Kafka offset
```

**无状态**：offset 存在 Kafka，consumer group 自动 rebalance，副本可随 HPA 增减，上限为分区数（故 §3.3 分区数起步即留余量）。

**typed path 类型规范化（VARIANT 类型冲突的第二道防线）**：对 DD-002 的 Schema Template 声明的每一个 typed path，loader 在写入前按声明类型强制转换（如 `"200"` → `200`）。转换失败时**不写入主路径**，改写入 `<path>__raw`（STRING）影子路径，并递增 `variant_type_conflict_total{tenant,path,declared_type}` 指标。

理由在存储侧：一旦不兼容的值进入主路径，Doris 会把该路径提升为 JSONB 并**静默丢失索引**，而 RANDOM 分桶意味着该 tablet 内**所有租户**的这个字段一起失去索引。这是无法事后修复的污染（只能重建分区），必须在写入前拦截。该指标是**零容忍告警**：出现即说明有租户埋点违反 OTel 语义约定，需推治理事件。

**JSON key 长度校验**：Doris VARIANT 的 JSON key 长度上限为 255 字节，超限的 key 在 loader 侧截断并计数，避免整批导入失败。

#### 幂等：label 命名规则与保留期约束

Stream Load `label = {topic}-{partition}-{startOffset}-{endOffset}`。Doris 对同名 label 的重复导入直接拒绝，因此「at-least-once 消费 + label 去重」在效果上等价于 exactly-once。

label 的保留期由 Doris `label_keep_max_second` 控制（默认 3 天），必须 ≥ Kafka 保留期（12h），否则回放时幂等失效。详见 §3.3 的耦合约束。**label 命名规则与保留期约束同属 IF-3，任一方变更须 DD-002 签字。**

#### 背压与重试

Stream Load 返回 `-235`（too many tablet versions）、`-238`、内存超限等错误时，**指数退避重试且不 commit offset**，积压由 Kafka 承接。这条是 SLO-6 在落库侧的落点：只要 offset 没提交，数据就还在 Kafka 里。

`-235` 是高频小批量导入的经典问题，缓解手段是三条叠加：

1. **批次不小于 64 MB / 2s**；
2. 表启用 `time_series` compaction policy（由 DD-002 配置）；
3. **RANDOM 分桶配合 `load_to_single_tablet=true`**——RANDOM 分桶下必须显式开启，让单次导入只写一个 tablet。否则每批导入都会写满所有 tablet，小文件数与 compaction 压力按 bucket 数倍增。这是 v1.1 选了 RANDOM 分桶却没配套的一个遗漏。

**端到端延迟核算**：Collector batch 1s + Kafka 传输 + loader 攒批 2s + Stream Load 提交 1~2s ≈ **3~5s**，对应 SLO-1 的 p99 < 10s。相比 Routine Load 攒批机制下的 10~30s 是数量级改善，这是自研 loader 的第三项收益（前两项是展开与幂等）。该核算与 SD-000 §8.1 的分段预算口径不完全一致，见 §4 OQ-1。

#### 批次大小与存储侧参数的耦合

DOC mode 下 `variant_doc_materialization_min_rows`（示例值 10000）决定"多大的批次在写入时就做子列化、多小的批次留到 compaction 再做"。64 MB 批次约合日志 12.8 万行、span 6.4 万行，**均远超该阈值**，因此子列化在写入时完成，不存在"最新数据只能扫原始 JSON"的查询退化窗口。

反过来说，**若后续为压延迟而调小批次，必须同步核对这个阈值**——这是一对耦合参数，写入部署检查清单。**调小批次属于 IF-3 变更，须 DD-002 签字后执行。**

#### 规模与副本数

1.5 TB/天 下 **4 副本**（每副本约 3 个分区）；10 TB/天 下 **16 副本**。副本数上限受 Kafka 分区数约束（logs 12 / traces 6 起步，终点 24 / 12），这是 §3.3 分区数起步即超配的直接原因。

> **对 v1.1「取消自研 Writer 消费组」决策的修正说明**：该决策对 metrics 成立（metrics 直连 VM，确实不需要消费组），对 logs/traces 不成立。v1.2 恢复自研 loader，但它与 v1.0 设想的"有状态 Writer"不同——offset 在 Kafka，服务完全无状态，运维成本接近于一个普通的 Deployment。

### 3.5 Metrics 写入整形与端到端背压

**高基数防护**：metrics-ingest 服务（无状态，可水平扩）内置 per-tenant series 基数计数器（HyperLogLog 近似），超配额后按控制面下发的 label 白名单做 drop 或聚合（drop `pod_uid`、`container_id` 类 churn label），并生成"基数审计事件"供租户自查。这是 SaaS 模式区别于自建 VM 的核心增量。配额值与白名单由 DD-006 下发（IF-9，fail-static）；超限时的降级行为（drop / 聚合）语义由 IF-4 定义。

**exemplar 抽取**：metrics-ingest 从 OTLP metrics 中抽取 exemplar，按 **IF-5** 的采样规则写入 Doris `metric_exemplars` 表。这一步替代了 v1.1 依赖的「VM 原生 exemplar 存储」。抽取规则、采样率与写入目标表均由 IF-5 定义，本模块只负责执行。

#### 端到端背压

取消 Kafka 的兜底逻辑是「vmagent 磁盘队列 + 客户端重发」，但 metrics 的实际路径是：

```
客户集群 gateway → 平台摄入网关 → 平台 Collector → metrics-ingest → vminsert
                    └────────── 两跳平台侧无状态服务 ──────────┘
```

这两跳的 exporter 默认使用**内存队列**。若 vminsert 或 metrics-ingest 故障，平台侧内存队列撑爆就直接丢数据，客户侧的 `file_storage` 持久队列完全用不上——因为没有人把错误透传回去。**兜底链路只在纸面上成立。**

强制要求：

1. 每一跳在下游不可用时**必须返回可重试错误**（gRPC `UNAVAILABLE` / `RESOURCE_EXHAUSTED`，HTTP 503/429），不得吞掉错误后返回成功——对应 §3.1 的 E6/E7/E8；
2. 平台侧 Collector 与 metrics-ingest 的 `sending_queue` 满时**拒绝新请求而非丢弃队首**；
3. **M2 必须包含一个故障注入用例**：停掉 vminsert 30 分钟，验证数据最终从客户侧 gateway 的持久队列完整回补，**丢失率 < 0.01%**（这是 SLO-6 在 metrics 路径上唯一的验收手段）；
4. **可选工程优化**：把 metrics-ingest 的基数防护与 exemplar 抽取做成 Collector 的自研 processor，将两跳合成一跳——少一跳就少一处丢数据的地方。列为 M2 备选项，**不阻塞主线**。

### 3.6 多 K8s 集群接入

**接入模型：一个集群 = 一套轻量 Agent + 一个集群身份。** 用户操作仅三步：控制台"接入集群" → 复制内嵌凭证的 `helm install` 命令 → 在目标集群执行。每集群重复一次即完成多集群接入。

**集群内 Agent 拓扑**（cluster-gateway 承担 tail sampling）：

```
K8s 集群内：
┌────────────────────────────────────────────────────┐
│ DaemonSet：node-agent（OTel Collector）              │
│  · filelog receiver 采集 /var/log/pods（容器日志）    │
│  · 接收本机 Pod OTLP（trace/metrics，应用打 localhost）│
│  · kubelet stats / host metrics                     │
│  · trace 出口用 loadbalancing exporter，             │
│     routing_key=traceID，k8s resolver 发现 gateway   │
│     → 保证同一 trace 的所有 span 落到同一个 gateway 副本│
└──────────────┬─────────────────────────────────────┘
               │ 集群内 gRPC（trace 按 traceID 一致性路由）
┌──────────────▼─────────────────────────────────────┐
│ Deployment：cluster-gateway（OTel Collector，2+ 副本）│
│  · k8sattributes 富化（namespace/labels/owner）       │
│  · 注入 cluster_id + tenant_id                      │
│  · tail_sampling processor（见 §3.7）                │
│  · batch + file_storage 持久队列（断网缓冲 ≥2h）      │
│  · 唯一出口：TLS 443 → 平台摄入网关                   │
└────────────────────────────────────────────────────┘
配套：vmagent（或 Collector prometheus receiver）抓取
      kube-state-metrics / cadvisor / 应用 /metrics
```

**设计要点**：

1. **单出口原则**：DaemonSet 只采集不出集群，所有外发流量收敛到 cluster-gateway——企业客户安全团队只需放行一条 egress 规则（出方向 443），平台永不主动连入客户集群。
2. **身份与凭证**：层级模型 `租户 → 项目（环境） → 集群`；注册集群时生成 `cluster_id` + 集群级 Token（Helm values 注入为 Secret），Token 可独立吊销、限流、计量——某集群异常刷量只熔断该集群（对应 §3.1 的 E2）。
3. **cluster 是一等公民**：跨集群必然存在同名 namespace/service，因此摄入侧强制注入 `k8s.cluster.id`（平台分配不可变，显示名可改）；VM 侧由 vmagent `external_labels` 统一注入 `cluster` label，防止用户伪造串数据；UI 上 cluster 是全局过滤维度。
4. **大租户形态**：单集群日增 > 1 TB 时 gateway 独立 HPA（按上行速率扩缩），Kafka 分区键升级为租户+集群组合（仍为共享 topic，不开独立 topic）；混合云/无外网集群支持"边缘中转"模式。大租户的判定与迁移策略由 DD-006 拥有。

**客户侧持久队列与兜底窗口**：cluster-gateway 的 `file_storage` 队列按**断网缓冲 ≥2 小时**配置，这是平台摄入入口故障时唯一的兜底（见 §3.3 的两个失效窗口对比）。队列水位需由 cluster-gateway 上报至平台并纳入自监控（§3.8）——水位不可见的持久队列等于没有兜底。

### 3.7 Trace 采样策略

#### 为什么 head sampling + 网关补偿不成立

> v1.1 定稿的是「SDK 按 trace_id 哈希做 head sampling（默认 10%）+ 集群 gateway 对错误 span 与慢 trace 做补偿保留」。这个组合在实现层面是空操作：**SDK 的采样决策发生在 span 创建时，未被采样的 span 根本不会导出**，gateway 能看到的只有那 10%，对它们做"补偿保留"没有任何增量——错误 trace 依然按 10% 随机丢弃 90%，而错误 trace 恰恰是排障最需要的部分。v1.2 改为在 cluster-gateway 做真正的 tail sampling。

#### cluster-gateway tail sampling 方案

| 层 | 职责 | 配置要点 |
|----|------|----------|
| 应用 SDK | **AlwaysOn**（不做采样决策，全量导出到本机 node-agent） | 集群内 localhost 流量，成本可忽略 |
| node-agent（DaemonSet） | 不做采样决策；trace 出口用 `loadbalancing` exporter，`routing_key: traceID`，`resolver: k8s`（服务发现 cluster-gateway） | **保证同一 trace 的所有 span 汇聚到同一个 gateway 副本**——这是 tail sampling 能工作的前提 |
| cluster-gateway | `tail_sampling` processor，`decision_wait: 10s` | 策略取并集（OR）：① `status_code = ERROR` 全保留；② `latency > 服务 p99` 全保留；③ `probabilistic 10%` 基线采样 |

**内存开销核算**（此前被推迟到二期的唯一理由）：

- 1.5 TB/天 基线：采样前约 1.2 万 span/s（峰值 3.5 万），`decision_wait 10s` → 峰值驻留 ≈ 35 万 span × 1 KB ≈ **350 MB**，分摊到客户集群 2~4 个 gateway 副本，**每副本 100~175 MB**；
- 10 TB/天 终点：总驻留 ≈ 2.3 GB，分摊到 8+ 副本仍在单副本 300 MB 量级。

结论：内存不是障碍，v1.1 把它推到二期是过度保守。**一期即上。**

**收益**：

1. **错误 trace 100% 保留**——这是 head sampling 方案根本做不到的，也是排障场景最核心的诉求；
2. **慢 trace 100% 保留**，延迟分析不再受随机采样干扰；
3. **exemplar 跳转命中率大幅提升**：exemplar 挂载的通常是异常指标点（高延迟、错误率上升），其指向的 trace 大概率正是被策略 ① ② 保留的那批，实际有效命中率预期 ≥ 70%（远高于 head sampling 的 10%），对应 SLO-9；
4. 采样率调整由控制面下发到 gateway（IF-9），**无需应用重启或改代码**。

**已知缺陷（一期接受，二期解决）**：

- **跨集群 trace 采样不一致**：微服务调用跨集群时，一条 trace 的 span 散落多个客户集群，各集群 gateway 独立决策会导致瀑布图残缺。一期在 UI 上对跨集群 trace 标注「部分 span 可能因跨集群采样不一致缺失」（标注形态由 DD-008 定义）；**二期**在平台摄入层按 `trace_id` 哈希路由做全局 tail sampling，集群 gateway 降级为纯转发。
- **计量口径变化**：采样丢弃发生在客户集群内，平台侧无法直接计量被丢弃的 span。要求 cluster-gateway 上报自身的 `otelcol_processor_tail_sampling_*` 指标到平台，作为「被丢弃 span 计入账单折扣项」的数据源。**计量与折扣口径归 DD-006**，本模块只负责产出并上报该指标。这条不做，采样率与账单的对账就会有缺口。

**摄入相关容量水位**（完整水位表归 X-003，此处只列由本模块触发动作的行）：

| 信号 | 水位 | 动作 | 注意点 |
|------|------|------|--------|
