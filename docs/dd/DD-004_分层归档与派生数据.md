## 3. 详细设计

### 3.1 冷热温分层

| 层 | 实现 | 留存 | 查询能力 | 说明 |
|----|------|------|----------|------|
| 热 | S3 主存储 + BE 本地 NVMe 缓存 | 7 天 | 全功能，p95 < 3s | 缓存命中率保障热路径性能，是一级 SLI |
| 温 | S3 主存储（缓存逐出） | 8~15 天 | 全功能，p95 < 15s（限并发） | 查询回源 S3，延迟高一个量级 |
| 冷（归档） | Iceberg（Parquet + zstd）on S3，由 Doris cold 计算组查询 | 180 天 | 检索可用（秒级~十秒级），标注"归档查询" | 查询侧实现见 DD-005 |

> 源：v1.3 §7.4

#### 存算分离下"温层"的真实含义

三层是**查询体验上的三层，物理上只有两种形态**。热与温的数据是同一份 Doris 表里的同一批数据，都存在 S3 主存储上，唯一差别是它还在不在 BE 本地 NVMe 缓存里。

因此"数据进入温层"**不是一次搬迁动作**，而是缓存 LRU 逐出的自然结果：没有调度器触发它，没有对应的运维操作，也没有独立的失败模式。全生命周期中真正发生数据移动的只有一次——热/温 → 冷的归档（Doris → Iceberg），也就是 §3.2 的对象。

这个认识有两条直接推论：

1. **热窗口长度不是一个可配置的 TTL，而是"缓存容量 ÷ 日增数据量"的结果**。压缩热窗口等价于缩小缓存容量需求（G6 的第一成本杠杆），但同时按比例降低缓存命中率。SD-000 §4 推论 1 明确禁止只按成本单向压缩它。
2. **温层查询慢不是查询层的问题**。8~15 天区间的 p95 < 15s 是回源 S3 的代价，属于容量问题，由 X-003 的水位预案兜底，不计入 SD-000 §8.2 的查询延迟预算。

#### 为什么不走存算一体的 cooldown 搬迁

选型结论已在 SD-000 §9 定稿、不再重开，此处只记它对本模块的工程后果：

在存算一体 + cooldown 模式下，"热 → 温"本身就是一次真实的数据搬迁，需要为它单独设计搬迁调度、失败重试与搬迁期间的查询可见性——也就是说本文档会有**两条**需要保证一致性的数据移动链路。存算分离把其中一条消解成了缓存策略，只留下归档这一条，使"先验后删"的门禁只需要在一个地方成立。

代价记在别处：一期即承担 Meta Service + Recycler + FoundationDB 的运维面，这是本架构最大的单一技术风险（SD-000 §4 推论 2、Q-3）。

### 3.2 归档与分区删除流程（本文档核心）

> **本节的形式化表述是 v2.0 拆分时新增、需评审确认**：v1.3 §7.4 中这部分是一个五行伪代码块，下文把它展开为七个步骤，并为每一步补齐前置条件、成功判据、失败动作与可重试性。**语义与 v1.3 等价，没有新增或放宽任何判据**；补齐的部分是原文未写明、但实现时必须回答的问题。凡 v1.3 未定义且无法从既有约束推出的，一律记入 §4 Open Questions，不在此处代为决定。

#### 3.2.0 语义基线（v1.3 §7.4 原文）

```
归档调度（`ops-control` 内每日运行，无独立进程）：
  1. 选出 Doris 中超过热窗口（15 天）且未归档的分区
  2. 写入 Iceberg：INSERT INTO iceberg_catalog.archive.logs
                   SELECT * FROM logs PARTITION (pYYYYMMDD)
     （Doris 写 Iceberg 的成熟度见 SD-000 Q-6；
       备选路径：EXPORT 为 Parquet + 外部工具登记 catalog）
  3. ★ 校验门禁（三项全过才继续，任一失败则保留分区并告警）：
       a. 行数比对：Doris 分区行数 == Iceberg 对应分区行数
       b. 校验和比对：抽样列的 checksum 一致
       c. Iceberg catalog snapshot 登记成功且可被 cold 计算组读到
  4. 校验通过 → 显式 ALTER TABLE logs DROP PARTITION pYYYYMMDD
  5. 校验失败 → 保留分区 + 告警 + 计入「归档校验失败率」SLI（阈值 0.1%）
```

#### 3.2.1 全局不变式（任何实现都必须成立）

这四条在展开成步骤之前先立住，因为下面每一步的失败分支都是从它们推出来的：

- **I1 · 唯一路径**：本流程是 Doris 分区删除的**唯一**路径。动态分区的自动回收已在建表层面关闭（`dynamic_partition.start = -3650`，只保留自动建分区能力，见 DD-002），`DROP PARTITION` 只由归档调度器在校验通过后显式执行。
- **I2 · 先验后删**：删除不可逆，三项门禁全过才允许进入 S6。不存在"部分通过 + 人工判断"的中间态。
- **I3 · 失败即保留**：任何一步失败的默认动作都是**保留分区**。保留分区的成本是 S3 存储费，删错分区的成本是永久丢数——两者不对等，所以默认值只能偏向保留。
- **I4 · 无自动兜底**：不允许存在"连续失败 N 次后强制删除""分区堆积超过 M 个后强制删除"之类的兜底逻辑。堆积由 §3.2.4 的对偶指标告警给人处理。

适用范围：`logs` 与 `spans` 两张表的动态分区自动回收都已关闭，因此两张表的分区删除都只能走本流程。v1.3 只给出了 `logs` 的语句示例，`spans` 的归档目标表名未明确，记入 §4。

#### 3.2.2 步骤序列（S1~S7）

**S1 · 选取候选分区**

- 前置条件：调度器每日运行一次；能读到当前生效的留存配置（来源 DD-006 / IF-9）。
- 动作：选出 Doris 中**超过热窗口（15 天）且未归档**的分区。上一轮校验失败而被保留的分区仍然满足这个条件，因此会自然重新入选，不需要单独的重试队列。
- 成功判据：得到一个候选分区列表（可能为空，空列表是正常状态，不是异常）。
- 失败动作：读不到留存配置时**不执行本轮归档**，告警。注意这与数据面的 fail-static 语义有冲突，见 §3.5 与 §4。
- 可重试：是。S1 无副作用。

**S2 · 写入归档层**

- 前置条件：候选分区非空；Iceberg catalog 可写；本分区在归档层没有上一趟留下的残留数据。
- 动作：`INSERT INTO iceberg_catalog.archive.logs SELECT * FROM logs PARTITION (pYYYYMMDD)`。同一趟扫描顺带产出 L2 粗粒度 rollup（§3.3），边际成本≈0。
- 成功判据：写入语句返回成功。**注意这只是"写入侧自认为成功"，不构成归档完成的判据**——归档是否完成由 S3~S5 裁定。
- 失败动作：保留 Doris 分区，告警。该分区留待下一轮调度重新进入 S1。
- 可重试：是，**但重试前必须先清理上一趟的残留写入**，否则 S3 的行数比对必然失败（Iceberg 侧行数 > Doris 分区行数）。清理的具体语义（回滚到上一个 snapshot，还是按分区 overwrite）v1.3 未定义，记入 §4。同一问题波及 L2 rollup 是否会因重试而重复产出。

**S3 · 门禁 a — 行数比对**

- 前置条件：S2 返回成功。
- 动作：比对 Doris 分区行数与 Iceberg 对应分区行数。
- 成功判据：**严格相等**。不设容差——容差在这里没有任何合理取值，允许差 1 行和允许差 1 万行在原则上是同一件事。
- 失败动作：判定为一次**归档校验失败**，进入 §3.2.3。
- 可重试：不可单独重试。行数不等意味着 S2 的产物不可信，必须回到 S2 重写（含残留清理）。

**S4 · 门禁 b — 校验和抽样比对**

- 前置条件：S3 通过。
- 动作：对抽样列计算 checksum，比对两侧结果。
- 成功判据：抽样列的 checksum 一致。
- 失败动作：同 S3，判定为一次归档校验失败。
- 可重试：不可单独重试，回到 S2。
- 待定：抽样列集合、抽样比例与 checksum 算法 v1.3 未定义，记入 §4。这是三项门禁中唯一有自由度的一项，取值直接决定门禁的实际强度，不能留给实现者临场决定。

**S5 · 门禁 c — 归档层可读性确认**

- 前置条件：S4 通过。
- 动作：确认 Iceberg catalog snapshot 登记成功，**并且由 cold 计算组实际发起一次读取**，确认该 snapshot 可读。
- 成功判据：snapshot 已登记且 cold 计算组读取成功。只检查 catalog 元数据不算通过——这一项的全部价值就在于它是从消费侧发起的。
- 失败动作：同 S3，判定为一次归档校验失败。
- 可重试：可单独重试（catalog 登记与 cold 计算组连通性可能是瞬时问题），但重试仍在同一轮调度内，且不得因为"数据肯定写进去了"而跳过。

**为什么必须是三项、不能裁剪成两项。** 三项覆盖的是三类互不重叠的失败：行数比对只能发现"少写"，发现不了"写错"；checksum 能发现内容损坏，但它和行数比对都站在写入侧视角；S5 是唯一站在消费侧视角的验证——catalog 登记成功但 cold 计算组读不到（权限、endpoint、catalog 配置漂移）这类故障，行数和 checksum 都发现不了，而它恰恰是"数据还在但等于没有"的典型形态。

**S6 · 显式删除（不可逆）**

- 前置条件：**S3、S4、S5 在同一轮调度内全部通过**。跨轮复用历史校验结果不成立——分区在两轮之间可能因 compaction 或补写而变化。
- 动作：`ALTER TABLE logs DROP PARTITION pYYYYMMDD`。
- 成功判据：分区删除成功。
- 失败动作：分区仍在，告警。这是**唯一一种"失败反而是安全的"**的失败：数据没丢，只是空间没释放。
- 可重试：DROP 本身可重试，但**其不可逆性意味着重试前必须重新确认 S6 的前置条件仍然成立**。任何绕过门禁直接执行 DROP 的人工操作都违反 I1/I2，且会被管理面操作审计记录（X-002）。

**S7 · 登记与记账**

- 前置条件：S6 成功。
- 动作：把该分区标记为已归档并已回收；更新 §3.6 的自监控信号（归档校验失败率、已过期未归档分区数、Iceberg snapshot 新鲜度）。
- 成功判据：状态登记完成。
- 失败动作：告警。此时数据已归档且 Doris 分区已删，登记状态滞后不影响正确性，但会让下一轮 S1 的候选集判断出错，需人工修正。
- 可重试：是。

#### 3.2.3 校验失败的处理

任一门禁（S3/S4/S5）失败时，动作固定为三条，不可裁剪：

1. **保留 Doris 分区**——不执行 S6，分区原样留在 Doris；
2. **告警**——归档管线失败必须有人看见，不能只写日志；
3. **计入「归档校验失败率」SLI**——对应 SLO-8，阈值 **0.1%**。

失败分区不进入任何特殊队列，它在下一轮调度中仍满足 S1 的条件（超过 15 天且未归档），自然重新参与。

明确禁止的三种"处理方式"：

| 反模式 | 为什么禁止 |
|--------|-----------|
| 人工跳过门禁直接 DROP | 违反 I1/I2。门禁的价值在于无例外，开一个口子它就退化为建议 |
| 配置"连续失败 N 次后自动删除" | 违反 I4。这正是门禁要防的那件事，换了个触发条件而已 |
| 把失败分区标记为"已归档"使其退出候选集 | 制造了一个校验从未通过、却再也不会被重试的分区。比直接删除更隐蔽 |

**失败分支汇总**：

| 步骤 | 失败后分区状态 | 数据是否可能丢失 | 可重试 | 重试前是否需要清理 |
|------|---------------|-----------------|--------|------------------|
| S1 选取 | 未动 | 否 | 是 | 否 |
| S2 写归档 | 保留 | 否 | 是 | **是**（Iceberg 侧残留） |
| S3 行数 | 保留 | 否 | 回到 S2 | 是 |
| S4 校验和 | 保留 | 否 | 回到 S2 | 是 |
| S5 可读性 | 保留 | 否 | 是（可单独重试） | 否 |
| S6 删除 | 保留（未删成） | 否 | 是，须重新确认前置条件 | 否 |
| S7 登记 | 已删除 | 否（仅状态滞后） | 是 | 否 |

整张表只有一列全是"否"：**任何单步失败都不会导致数据丢失**。这是流程设计成立的判据——如果某一行的"是否可能丢失"能填出"是"，流程就不能上线。

#### 3.2.4 对偶指标：已过期但未归档的分区数

门禁把天平压向了"宁可不删"，代价是它会在归档管线卡住时让分区无限堆积并占满 S3。因此必须监控**「已过期但未归档的分区数」**，阈值 **> 2 告警**。

这个指标与 SLO-8 是**一对**，必须同时看：

- SLO-8 约束的是"不该删的被删了"；
- 对偶指标约束的是"该归档的一直没归档"。

只盯其中一个都会走向极端：只盯 SLO-8，理性做法是把门禁放宽到永不失败；只盯堆积数，理性做法是加一条自动删除兜底。两者同时在看板上，才能把"归档管线坏了"这件事逼成一个必须修管线的工单，而不是一个可以调参数绕过的告警。

**硬约束：绝不允许配置自动 DROP 兜底。** 分区堆积到影响容量时，正确动作是排查归档管线或临时扩容 S3 存储，而不是删数据。

已知的一条触发路径：控制面整体故障时归档调度器停摆，分区随之堆积，由本指标告警（故障矩阵见 X-001）。

#### 3.2.5 备选实现路径

若 Doris 直写 Iceberg 的成熟度不达标（SD-000 Q-6），S2 退回 **EXPORT 为 Parquet + 外部工具登记 catalog**。这只影响 IF-10 的实现方式，不影响架构。

**三项门禁不变**——它们是 IF-10 的硬契约，与实现路径无关。但落地形式有三处变化：

1. S3/S4 的归档侧读取对象从"Doris 写出的 Iceberg 表"变为"EXPORT 产物 + 外部登记后的表"，比对时点必须在登记完成之后，否则比的是一堆还没成为表的文件；
2. **S5 的重要性上升**：登记由外部工具完成，"文件已在 S3、catalog 未登记"的不一致窗口比直写路径更大，而 S5 正是唯一能发现它的门禁；
3. S2 的失败恢复更复杂：EXPORT 与 catalog 登记是两个独立步骤，中间失败会留下未被任何 snapshot 引用的孤儿文件。孤儿文件的清理责任方 v1.3 未定义，记入 §4。

> 源：v1.3 §7.4

### 3.3 派生数据：三级物化体系

**决策：精细物化放热路径（Doris 异步物化视图）；冷数据不单独物化，仅在归档写 Iceberg 的同趟扫描中顺带产出粗粒度 rollup。**

理由有两条，都是关于查询分布的：排障关联查询 **95%+ 落在最近 24~72h**，物化视图把高频页面从"扫原始数据"变成"点小表"（聚合体积仅原始数据的 **1%~5%**）；冷数据查询低频且延迟容忍，为它常驻预付计算不划算。

| 级 | 位置 | 内容 | 新鲜度/粒度 |
|----|------|------|------------|
| L1 热路径 | Doris 异步 MV + 调度任务 | `service_metrics_1m`（RED 分钟级）；`trace_summary`（trace_id → 入口服务/总耗时/错误标记/涉及服务集合）；`entity_topo` 拓扑边表（§3.4）；error 日志 digest | ~1 分钟 |
| L2 归档时刻 | 写 Iceberg 管道 | 小时/天粒度服务级 rollup，随归档同趟扫描产出（边际成本≈0） | 小时/天 |
| L3 冷数据本体 | Iceberg 归档层 | 不预建任何物化，临时取证走 Doris cold 计算组即席查询（DD-005） | — |

三级的划分依据不是"数据有多老"，而是**查询频次与延迟容忍度的组合**：L1 服务高频低延迟，值得常驻计算；L2 搭归档扫描的便车，所以只在归档发生时存在；L3 低频且容忍十秒级，即席查询即可。

#### 物化刷新的资源归属

L1 物化刷新跑**独立 Doris 计算组**，与摄入、即席查询三方隔离（计算组划分见 DD-002）。刷新不得挤占热查询资源——热查询的延迟预算（SD-000 §8.2）里没有给物化刷新留任何余量。刷新 lag 纳入 §3.6 自监控。

#### 服务 RED 指标的产出位置（跨模块决策）

`service_metrics_1m` 是 L1 中**对新鲜度最敏感的一路**：Trace 服务质量告警（错误率/延迟）直接查它而不扫原始 span，告警延迟 SLO 是 2 分钟，而 MV 新鲜度承诺是 ~1 分钟——余量只有一倍。

若 M1 PoC 证明异步 MV 的 lag 不稳定，**仅将这一路升级为 loader 侧预聚合，其余维持 MV**。这项决策横跨 DD-001 与 DD-004，两边都不能单独决定（SD-000 Q-7），见 §4。

#### trace_summary 的第二个消费方

`trace_summary` 同时服务 AI 层：`get_trace` 工具先查摘要、再按需拉 span 明细，降低 AI 上下文的 token 消耗（工具契约归 DD-007 / IF-8）。这意味着它的字段集有两个约束方，改字段时需要知会 DD-007。

#### 原始数据全量留存原则

**派生只做加速，绝不用聚合结果替代原始数据。** 任何一级物化都不构成删除原始数据的理由——原始数据的生命周期只由 §3.2 的归档流程决定，与派生数据无关。

**产品归属（v2.1）**：派生表是所属产品的数据，不是平台元数据。一期物理上仍在 Doris 同集群（量大、要和原文 JOIN），逻辑主人如下：

| 派生 | 所属产品 | 理由 |
|------|----------|------|
| 日志侧 rollup / 模式聚类底表 | **Logs** | 只服务日志检索与分析 |
| `service_metrics_1m`、`entity_registry`、`entity_topo` | **Traces**（APM） | 从 span / K8s 事实派生，服务拓扑与 RED |
| 跨信号 JOIN 本身 | **平台编排** | 查询网关发起，不落一张「平台宽表」 |

控制面实体类型注册表（字段、约束、TTL）留在控制面库；`entity_registry` 行数据留在 Traces 表族。

具体到最容易出问题的一处：`spans.duration` 保留原始微秒值，**P50/P99 由 `percentile_approx` 在线计算**，而不是预聚合成固定分位数列。原始 span 全量留存，因此不存在"预聚合时没算 p999、事后再也算不出来"的问题。预聚合丢分位数是有明确反面教材的一类错误，本设计从数据保留层面排除它，而不是靠事先猜准需要哪些分位数。

> **边界说明**：v1.2 已删除「Metrics 长期降采样写回 Doris」一项。指标的降分辨率改由 recording rules 在指标引擎内产出低频 series 写回原库（详见 DD-003），不属于本文档的派生体系。此处记一笔是为了让读到 v1.3 §7.3 的人知道那段内容去了哪里。

> 源：v1.3 §7.3

### 3.4 Zmodel 统一语义层

**定位**：把 §3.3 的三级物化体系从"查询加速层"升级为**"实体-关系-数据"统一语义层**——物化视图是 Zmodel 的物理实现，Zmodel 是其语义抽象。目标是为 AI 层提供可推理上下文（上下游、爆炸半径、黄金指标）为 RCA 打底，同时兑现信号关联与服务拓扑页的统一数据源。

#### 核心抽象

| Zmodel 概念 | 一期范围 |
|-------------|----------|
| EntitySet / Entity | 白名单类型：`k8s.cluster` / `k8s.namespace` / `service` / `service_instance` / `host` / `database` / `mq`；二期开放自定义类型 |
| Link（实体边） | `calls`（service→service，span 派生）、`contains`（cluster→ns→service）、`runs_on`（instance→host）、`depends_on`（service→db/mq，client span 派生） |
| DataLink（数据挂载） | 实体 ↔ logs / spans / `service_metrics_1m` 的挂载点 = `tenant_id + entity_key + 时间窗`，同库 JOIN 兑现 |
| Schema 注册 | `entity_registry` 表（Traces 产品，Doris）+ 控制面实体类型注册表（字段、约束、TTL；控制面库） |

**实体粒度纪律**：实体只建到 **service_instance 级**；pod / container **不进实体表**（churn 太高，降级为 instance 的属性）。单实体类型总量控制在万级，超限触发治理告警——实体表是语义层不是明细层，爆炸即失效。

#### 物理实现（复用 Doris，一期不引入图数据库）

- **`entity_registry`**：`entity_id, tenant_id, entity_type, name, attributes VARIANT, first_seen, last_seen, status`。首见 upsert，`last_seen` 滚动更新，**30 天未见标记 stale**。
- **`entity_topo`**：`src_entity, dst_entity, link_type, first_seen, last_seen` + **5 分钟聚合 RED**（调用量/错误率/p99）。**边上自带黄金指标**，RCA 下钻零额外查询——这是把拓扑和指标放在同一张表里的唯一理由。
- **确定性原则**：边只从 span、k8s 元数据等**事实数据**派生；AI 推断的关系打 `INFERRED` 标签分开存储（二期）。Agent 做 RCA 时必须能无条件信任每一跳，事实边和推断边混在一张表里就做不到了。

#### 图遍历策略与扇出剪枝

图遍历 = **应用层迭代 BFS**，每跳一次 Doris 点查（走倒排索引），**深度 ≤ 3**。

必须加的两道剪枝：

| 剪枝 | 取值 | 超限行为 |
|------|------|----------|
| 单跳 fanout 上限 | 20（按调用量 top-N 保留） | 截断，并在返回中标注 |
| 全遍历访问节点上限 | 200 | 截断，并在返回中标注 |

不剪枝的后果是具体的：高扇出服务（如网关，下游可达数百）在深度 3 下会退化成十万量级的点查风暴。"在返回中标注"这一条同样不可省——上层（尤其是 AI）必须知道自己拿到的是不是完整子图。

#### 构建管线

span → caller/callee 5 分钟聚合 → `entity_topo` upsert；摄入侧 k8s 富化 labels → `contains` / `runs_on`。实体注册与边发现均走 Doris 调度任务，刷新 lag 纳入 §3.6 自监控。

**排期**：`entity_registry` 与 `entity_topo` 的构建管线在 **M3**，它是服务拓扑页的数据源，属于 M3 的产品需求，不与 AI 层绑定在 M4。M4 只保留 Zmodel 的语义工具层。

#### 它服务的上层场景

1. **服务拓扑页（DD-008）**：`entity_topo` 直接就是拓扑图的边集，边上的 RED 就是边的粗细与颜色，不需要额外查询。
2. **信号关联（DD-005）**：DataLink 的 `tenant_id + entity_key + 时间窗` 挂载点使"从实体跳到它的日志/链路"变成同库 JOIN。
3. **AI 语义工具（DD-007 / IF-8）**：一期**不自研查询语言**，改为提供固定语义工具 `get_entity` / `get_neighbors(entity, direction, depth≤3)` / `get_golden_metrics(entity, timerange)` / `get_entity_logs` / `get_entity_traces` / `get_blast_radius(entity)`，以压低幻觉率与 token 消耗。二期再评估 pipeline 式统一查询语言。工具集本身的契约归 DD-007，本文档只保证其底层数据可得。
4. **RCA 动线（M4 随 AI 层 MVP 兑现）**：告警事件 → 挂载实体 → 取告警实体 + 1~2 跳邻居的**最小连接子图**（受上述剪枝约束）→ 各实体黄金指标时间序对齐 → 叠加变更事件（二期）→ 携带证据链的根因报告。

> 源：v1.3 §7.6

### 3.5 留存策略执行

> **本节为 v2.0 拆分时新增、需评审确认**：v1.3 §7.4 关于留存执行只有一句话——"留存策略 per-tenant 可配（商业版差异化卖点），由控制面下发"。下文是把这句话落到执行侧时必须回答的问题清单；其中三处 v1.3 没有给出答案，已原样记入 §4，**未在此处代为决定**。

#### 职责边界

留存策略的**配置、租户级差异化定义与下发**归 DD-006（IF-9）；本文档只负责**执行**：把"某分区已过期"翻译成 §3.2 的一次归档 + 删除。退租删除的合规要求（删除时限、删除证明、备份副本处置）归 X-002，本文档提供执行能力。

#### per-tenant 差异化与分区粒度的矛盾（待决）

这是本节最重要的一处：**执行单位与配置单位对不齐**。

- 配置单位是**租户**：留存策略 per-tenant 可配；
- 执行单位是**分区**：分区按天划分，共享表下同一个分区里混着全部租户的数据。`DROP PARTITION` 的粒度是"某一天 × 全体租户"，**无法表达租户级差异**。

v1.3 只在退租场景给过一条行级路径：共享表租户执行 `DELETE WHERE tenant_id = ?` 并触发 compaction，并注明这在 DUPLICATE 模型上代价不低、M2 需实测单租户删除的耗时与资源占用。但**常规的 per-tenant 留存差异化是否也走这条路径，v1.3 没有说**，也没有说留存较短的租户的数据是提前从 Doris 物理删除、还是只在查询侧按其留存策略截断可见范围。两种做法的成本模型与合规含义完全不同，记入 §4。

在该问题出结论之前，可以确定的只有一点：无论走哪条路径，**只要动作是删除，就受分层原则 5 约束**，不得绕过校验门禁。

#### 与控制面故障的关系（待决）

分层原则 4 要求数据面 fail-static：控制面故障时按最后一次下发的配置继续运行。分层原则 5 要求删除极端保守。两条原则在"留存配置读取失败"这一情形下给出的动作不同——前者倾向于"按旧配置继续删"，后者倾向于"读不到就别删"。

§3.2 的 S1 目前写的是**不执行本轮归档**（偏向原则 5），理由是漏删一天的成本远小于误删一天。但这是本次拆分时的取向，不是 v1.3 的既有决策，记入 §4 等待评审确认。

#### 与退租删除（X-002）的衔接点

退租删除会同时触及两处数据：

| 位置 | 执行能力 | 门禁是否覆盖 |
|------|---------|-------------|
| Doris 热/温层 | 大租户走独立库表可直接 DROP；共享表租户走 `DELETE WHERE tenant_id = ?` + 触发 compaction | 受分层原则 5 约束 |
| Iceberg 归档层 | 需要删除该租户在归档层的数据 | **IF-10 的门禁只覆盖 Doris 分区删除，归档层删除没有等价门禁** |

第二行是一个真实的缺口。同类缺口还有一个：归档层留存 180 天，**到期之后由谁删、是否需要门禁，v1.3 没有定义**。两者合并记入 §4，需与 X-002 共同决策。

归档层为开放 Iceberg 格式，支持 BYO-bucket 与客户自助导出，这一点在退租场景下反而增加了执行面——客户自有 bucket 中的数据删除责任划分属于合同与合规范畴，归 X-002。

### 3.6 本模块自监控信号

| 信号 | 阈值/口径 | 触发动作 |
|------|----------|----------|
| **归档校验失败率** | **< 0.1%**（SLO-8） | 失败即阻断该分区删除 + 告警；纳入 SLO-8 月度考核 |
| **已过期但未归档的分区数** | **> 2 告警** | 排查归档管线；**不允许自动 DROP 兜底** |
| Iceberg snapshot 新鲜度 | v1.3 未给阈值 | 反映归档管线是否在推进；与上一项互为佐证 |
| L1 物化刷新 lag | v1.3 未给阈值 | `service_metrics_1m` 一路最敏感（告警延迟 SLO 2 分钟） |
| Zmodel 构建管线刷新 lag | v1.3 未给阈值 | 影响服务拓扑页与 RCA 的可信度 |

前两项是一对，理由见 §3.2.4。后三项的告警阈值 v1.3 未给出，记入 §4。

全部信号汇总进 X-001 的平台自监控 SLI 体系；本文档只负责定义口径与产出，不定义告警路由与值班响应。
