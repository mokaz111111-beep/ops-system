## 3. 详细设计

### 3.1 租户与项目模型

```
Organization（客户，= 计费主体）
  └── Project（环境：prod / staging，= 数据隔离边界）
        └── Cluster（一个 K8s 集群或一个自建机房，= 故障与限流边界）
              └── Token（摄入凭证，可独立吊销、限流、计量）
```

四层的划分依据是**四种不同的"边界"各自需要独立控制**，而不是为了层级好看：

| 层 | 它是什么边界 | 独立控制的对象 |
|----|-------------|---------------|
| Organization | 计费与合同边界 | 账单、合同配额、`tenant_tier` |
| Project | 数据隔离边界 | 查询可见范围、留存策略、脱敏规则 |
| Cluster | 故障与限流边界 | 限流桶、采样策略、健康状态 |
| Token | 凭证边界 | 吊销、速率上限 |

**`tenant_id` 的语义锁定**：全链路字段 `tenant_id` 对应 **Organization**，不是 Project。Project 以独立字段 `project_id` 传递。这一点必须在这里锁死——DD-002 的 `DUPLICATE KEY(tenant_id, ts)` 前缀裁剪、DD-003 的 vmauth accountID、DD-005 的谓词注入全部依赖它，若两个模块对 `tenant_id` 的粒度理解不同，隔离就是纸面上的。

**身份传递**：客户侧只持有 Token。摄入网关用 Token 查本地缓存的映射表解析出 `(tenant_id, project_id, cluster_id)` 并**强制注入**，覆盖客户端自报的同名字段。查询侧由查询网关从 SSO/AKSK 会话解析并注入（IF-7）。**任何环节都不信任请求体里的 `tenant_id`。**

### 3.2 三级资源隔离

#### 3.2.1 数据隔离

| 租户档位 | Logs / Traces | Metrics |
|---------|--------------|---------|
| 共享（shared） | 共享大表 + `tenant_id` 谓词注入 + Doris Row Policy 兜底 | VM accountID 隔离 |
| 专属（dedicated） | 独立库表 | 独立 accountID 段 |

谓词注入与 Row Policy 是**两道独立的机制**，不是一道加保险：前者在查询网关（DD-005 §3.1 的 AST 改写），后者在 Doris 内部。保留两道是因为它们的失效模式不相关——网关改写漏掉某条路径时 Row Policy 仍然挡住，而 Row Policy 配置错误时网关改写仍然生效。

#### 3.2.2 计算隔离

存算分离提供**计算组（compute group）**，是比 Workload Group 更彻底的隔离手段——不同计算组是不同的 BE 进程组，共享同一份对象存储数据但 CPU / 内存 / 本地缓存完全物理隔离。一期划分四组：

| 计算组 | 用途 |
|--------|------|
| `hot` | 用户交互查询 + 摄入 |
| `alert` | 告警调度 SQL + L1 物化刷新（可与 `hot` 混部起步，量大后拆出） |
| `cold` | Iceberg 归档查询 |
| `dedicated-{tenant}` | 大租户专属 |

组内再用 Workload Group 做租户级 CPU / 内存软限制。规格与拓扑属于 DD-002，此处只定义**谁应该进哪个组**。

> **这是"一期即上存算分离"的直接红利**：大租户隔离从"共享 BE + 软限制"升级为"独立 BE 进程组"，爆炸半径真正收敛。软限制在 CPU 上尚可，在内存和本地缓存上基本无效——一个大租户的扫描能把整个 BE 的 page cache 冲走，而这是软限制管不到的。

#### 3.2.3 查询资源隔离

每租户并发配额 + 排队；归档/回源查询走独立队列（避免一个冷查询把交互查询的槽位占满）。执行在 DD-005，配额值在本文档 §3.3。

#### 3.2.4 隔离有效性的验证方法（v2.0 新写）

> v1.3 声称"零数据串扰"，但没有任何验证方案。**"零串扰"如果不可证伪，它就不是一条工程约束，而是一句愿望。** 本节给出它的可证伪定义与验收方法。

**可证伪定义**：存在一对测试租户 A、B，A 写入的任何一条数据，在 B 的任何一条读路径上都不可检索、不可聚合、不影响 B 的聚合结果。

**串扰测试套件（每次发布前必跑，红线级）**：

1. A 写入带唯一特征值的三类信号（日志正文含哨兵串、span 属性含哨兵值、metric 含哨兵 label）；
2. B 通过**每一条读路径**尝试取到它，断言零命中：
   - IF-7 检索 API（含 SQL 模式、参数篡改、越权 `tenant_id`、时间范围越界）
   - IF-7 Facet 聚合（**聚合结果的分母也不得包含 A 的数据**——这是最容易漏的一类串扰，数据本身取不到，但 top values 的计数被污染了）
   - IF-8 MCP 工具路径
   - 告警规则与订阅的导出
   - Grafana / PromQL 数据源
3. 断言 A 的数据量变化不影响 B 的任何聚合数值。

**覆盖每一条读路径**是重点。历史上多租户平台的串扰事故极少发生在主检索路径（那里一定有人盯着），几乎都发生在后加的旁路上——导出、告警、看板、AI 工具。所以这个清单必须随新增读路径同步扩充，作为新增读路径的**合并门禁**。

**计算隔离的验证（SLO-7 的验收方法）**：在 `dedicated-{test}` 计算组内打满 CPU 与本地缓存，同时测量 `hot` 组的查询 p95 与摄入延迟，断言均不突破 SLO。这条比数据隔离更需要实测——**物理隔离的声称来自"不同进程组"这一事实，但它们共享同一份对象存储和同一套 Meta Service**，共享部分是否成为串扰通道，只能压出来。

**生产持续验证**：常驻一个金丝雀租户，持续执行上述断言的子集并产生指标，进入 X-001 的自监控面板。

### 3.3 配额矩阵

> **命名更正**：v1.3 §9.2 标题为"三道防线"，但表内已有四行，且 DD-003 所需的 series 基数配额不在其中。本文档改称**配额矩阵**并补全为五维。这不是新增机制——五种机制 v1.3 都已在各自章节描述——而是把它们的**配额值**归拢到唯一的定义处。

| # | 维度 | 配额对象 | 执行位置 | 超限行为 |
|---|------|---------|---------|----------|
| 1 | **摄入速率** | bytes/s、EPS（按 Cluster） | 摄入网关令牌桶（DD-001） | 429 + 客户端降采样信号 |
| 2 | **摄入总量** | GB/日、GB/月 vs 合同配额（按 Org） | 计量管线离线比对（§3.4） | 触发升配销售流程；硬超限强制上调采样率 |
| 3 | **查询** | 并发数、单查询扫描行数、时间范围 | 查询网关（DD-005） | 排队 / 拒绝并提示优化 |
| 4 | **Schema 字段数** | per-tenant attributes 不同 key 数（默认 200） | `otlp-loader`（DD-001） | 超出字段进 sparse 存储 + 治理事件推送 |
| 5 | **Series 基数**<br>（v2.0 补入） | per-tenant 活跃 series 数 | metrics-ingest 的 HLL 计数器（DD-001 §/ DD-003） | 按下发的 label 白名单 drop 或聚合高 churn label；生成基数审计事件 |

五个维度的**超限行为刻意不同**，理由是它们的滥用后果不同：

- 维度 1 和 3 的超限是**瞬时资源争抢**，必须实时硬拦（429 / 拒绝），否则伤害其他租户；
- 维度 2 是**商业问题**，不应技术硬拦——把付费客户的数据拒之门外是最糟糕的产品行为，走销售流程；
- 维度 4 和 5 是**慢性污染**，既不能拒收也不能放任，所以选择"降级接收 + 推治理事件"：数据仍然进来，但以不损害他人的形式（sparse 存储 / 聚合后的 series），同时让租户看见自己的埋点在恶化。

> 维度 4 的必要性在 v1.3 中被下调了：Schema Template 把平台关心的 OTel 语义约定路径从子列额度竞争中直接摘出（DD-002 §3.3），字段数配额从第一道防线降为第二道。**但它不能取消**——租户私有字段的长尾仍然共享同一份动态子列预算。

### 3.4 计量计费管线

**主链路**：摄入网关在 **Kafka ack 成功之后**为每批数据生成 metering event（`tenant_id`、signal、bytes、events、采样率、时间戳，**携带批次幂等键**，客户端重试不重复计费）→ 独立 topic `metering` → 聚合任务 → 用量表（Doris 同库小表）→ 计费系统。metrics 直连路径由 metrics-ingest 以同样方式计量。

**"Kafka ack 之后"是刻意的**：ack 之前生成会把网关重试算成两次收入，ack 之后生成则最坏是漏计（对客户有利）。计量宁可少算，不可多算。

**计费维度**：摄入 GB（分信号定价）+ 存储 GB·月（分热/温/冷）+ 查询扫描量（超免费额度后）+ AI token。

#### 3.4.1 口径统一表

> v1.3 之前三处丢弃口径分散在不同章节，容易对不上账。此表是唯一口径来源。

| 事件 | 发生位置 | 是否计费 | 数据来源 |
|------|----------|----------|----------|
| 正常摄入 | 平台摄入网关 | 是 | metering event |
| 限流拒绝（429） | 平台摄入网关 | 否 | 网关计数器，用于容量分析 |
| tail sampling 丢弃 span | **客户集群 gateway** | 否，但计入**账单折扣项** | cluster-gateway 上报的 `otelcol_processor_tail_sampling_*` |
| 过载降级丢弃日志 | 平台 Collector | 否，计入**服务质量事件**（可能触发 SLA 赔付） | 降级动作日志（X-001） |
| 基数防护 drop label | metrics-ingest | 是（按整形后的 series 计） | 基数审计事件 |
| Schema 配额超限进 sparse | `otlp-loader` | 是（数据已接收） | 治理事件 |
| **AI 会话产生的查询扫描**<br>（v2.0 补入，回应 DD-007 OQ-6） | 查询网关 | **计量是，计价待定** | 查询审计事件，带 `source=ai` 标记 |

最后一行需要展开，因为它是 DD-007 明确提问的点：

> **计量与计价必须分开回答。** 技术上，AI 发起的查询**必须**照常计入租户的查询扫描量额度——否则 AI 工具层就成了绕过查询配额的通道，任何想突破扫描上限的用户只要改走 AI 入口即可，配额矩阵维度 3 直接失效。这一条没有商量余地。
>
> 商业上，是否就同一次 AI 会话同时向客户收取 token 费与扫描费，是**定价决策**，本文档不做。查询审计事件带 `source=ai` 标记正是为了让定价侧有能力选择（例如 AI 扫描计入额度但不单独计价）。**默认值需财务签字**，见 §4。

#### 3.4.2 准确性与对账

计量数据直接变成账单，错了是收入问题也是信任问题，因此需要独立对账而非自证：

| 对账项 | 方法 | 偏差告警 |
|-------|------|---------|
| 摄入计量 vs 实际入库 | metering event 的 events 总和 vs Doris 当日行数 + loader 丢弃计数 | 偏差 > 0.5% |
| 计量事件自身的完整性 | `metering` topic 的幂等键去重后计数 vs 网关侧发送计数 | 任一缺口 |
| 存储计量 vs 实际占用 | 用量表的 GB·月 vs Doris/S3 的实际分区体积 | 偏差 > 2% |

两侧天然对不齐是正常的（摄入按客户交付的字节数计，入库按解析后的行数计），**对账的目的不是让两个数字相等，而是让它们的差保持在一个稳定的、能解释的比例上**——比例突变才是信号。

### 3.5 大租户双轨策略

**大租户定义线**（按 1.5 TB 基线设定，随 X-003 校准）：日增 > 300 GB **或** 活跃 series > 200 万 **或** attributes 字段数持续触顶 → 建议独立；日增 > 1 TB → 强制独立。

**第四条触发线（已定，2026-10）：合规要求。** 客户提出强删除或加密隔离合规要求 → **一律定级 dedicated，与数据量无关。**

理由是平台采用 per-tenant 加密密钥，而该密钥只对 dedicated 档位有效——共享大表的一个 rowset 文件混有全部租户数据，对象级加密无法按租户切分（X-002 §2.6.3）。因此**加密擦除与租户级强删除承诺只能对 dedicated 租户兑现**。

> 这条改变了 dedicated 的定位：它不再是"大客户"的同义词，而是**"大客户或高合规要求客户"**。两点连带影响：
>
> - **定价**：dedicated 的"专属资源占用计费"现在也适用于小体量的高合规客户。对这类客户，专属资源的成本分摊比大客户差得多（资源利用率低），定价模型需要单独一档。**需财务在 M4 定价评审时一并处理。**
> - **排期**：dedicated 基础能力（Track B 直接供给）已从 M4 提前到 M3，因为 M3 的首批种子租户中可能就有这类客户（SD-000 §11）。

**共同地基：租户分层注册表。** 控制面维护 `tenant_tier`（shared / dedicated）+ 路由元数据（目标库表、计算组、Kafka 分区键规则、vmauth accountID 段、查询并发配额）。摄入网关、`otlp-loader`、metrics-ingest、查询网关统一读这张表做路由。**迁移因此退化为"搬数据 + 一次配置变更"**——两条轨道只是同一机制的两种触发方式，而不是两套实现。

**Track A：渐进型（小租户长成大租户）——在线迁移，零停机**

1. **监测**：基于计量的增长趋势告警——日增达大租户线 50% 时提示销售介入，80% 时启动迁移预案；
2. 建独立库表（独立分区/bucket 配置）与独立计算组；
3. **以日分区边界切流**：新一天的分区直接写新表（`otlp-loader` 路由配置变更，Kafka 回放兜底）；
4. 历史分区后台**限速**搬迁（分区级 `INSERT INTO SELECT`），限速避免挤占生产负载；
5. 追平后查询网关切读；过渡窗口内按时间范围双路由（新数据查新表、旧数据查旧表），对用户透明；
6. 旧数据清理，**保留 7 天回滚窗口**（路由配置一键回切）。

> 第 3 步依赖 Kafka 回放兜底，而 Kafka 保留期是 **12 小时**（SD-000）。这意味着**切流必须在 12 小时内确认成功**，否则兜底手段已经过期。迁移预案要把这个时间盒写进操作手册。

**Track B：原生大租户（接入即大）——直接独立供给**

1. **接入前定级**：销售/POC 阶段申报量级；接入向导提供"试跑一天"模式（全量计量、只读额度），**用真实计量数据定级，不靠客户自报**；
2. **第一天落独立资源**：独立 Doris 库表（bucket 数按其量级配置）、独立计算组、Kafka 分区键含 bucket 后缀打散热点、vmauth 独立 accountID 段、独立查询并发配额；
3. **计费口径切换**：从纯用量计费叠加"专属资源占用计费"。

**降级方向**：大租户缩水**不回迁**共享表——回迁的迁移成本大于资源节省，仅在其专属计算组内缩容。

### 3.6 配置下发与 fail-static 语义（IF-9，v2.0 完整新写）

> v1.3 把 fail-static 列为架构原则（分层原则 4）却从未定义它的行为。这是拆分暴露出的第二大文档缺口。**一个没有定义的原则在实现时一定会被各模块各自解释成不同的东西**，而配额与凭证恰恰是最不能各自解释的部分。

#### 3.6.1 下发通道

控制面写入配置并递增**全局单调版本号** → 数据面各实例通过长轮询 watch 变更 → 拉取全量配置快照 → **原子落盘到本地** → 切换生效 → 上报当前生效版本号。

三条硬性规定：

1. **数据面在请求路径上绝不同步查询控制面。** 任何同步依赖都会把控制面的可用性乘进数据面的可用性——控制面 99.99% 会让 99.99% 的数据面变成 99.98%，而这正是分层原则 4 要避免的。配置只能从本地快照读。
2. **本地快照必须落盘，不能只在内存。** 否则控制面故障期间的实例重启（K8s 驱逐、OOM、发布）会让该实例失去全部配置，fail-static 退化为 fail-empty。
3. **快照是全量而非增量。** 增量下发在丢事件时会产生静默的状态分歧，而配置的规模（租户数 × 配置项）完全放得下全量。

**可观测性**：控制面持续采集各数据面实例的生效版本号，暴露"落后于最新版本的实例数"与"最大版本滞后时长"。这是 IF-9 是否健康的唯一权威信号，进入 X-001。

#### 3.6.2 生效时延承诺

| 配置类别 | p99 生效时延 |
|---------|-------------|
| Class-S（安全类：Token 吊销、租户封禁、退租冻结） | **≤ 15 秒** |
| Class-Q（配额、采样率、留存、脱敏规则） | ≤ 60 秒 |

#### 3.6.3 fail-static 的具体语义

控制面不可用时，数据面的行为**按配置类别分级**，而不是一刀切。这是本节的核心，理由是两类配置的"用错了"代价完全不对称：

| 配置类别 | 快照过期后的行为 | 为什么这样选 |
|---------|----------------|-------------|
| **Class-Q**（配额、采样、留存、脱敏、路由） | **永不过期，无限期沿用最后快照** | 用旧配额的代价是"多收了一点数据"或"少收了一点钱"，这远小于拒收客户数据的代价。给它设 TTL 等于把 fail-static 悄悄变成 fail-closed |
| **Class-S**（Token 吊销、租户封禁） | 快照 TTL **24 小时**。TTL 内沿用；TTL 后对**新出现的 Token**拒绝（fail-closed），对快照中已知且未被吊销的 Token 继续放行 | 安全类配置"用旧的"意味着被吊销的凭证仍可写入。但代价必须与"全站拒收"权衡——所以只对快照覆盖不到的新凭证收紧，不牵连已知的正常租户 |

> **注意 Class-S 的 TTL 不是"过期即全拒"。** 一个常见的实现错误是 TTL 到期后整份快照作废，结果控制面宕机超过一天就变成全站鉴权失败——这恰恰是 fail-static 要防的灾难。这里 TTL 只作用于"快照里没有的 Token"这一类判定。
>
> **退租冻结属于 Class-S 但走独立通道**：它同时关系合规（X-002 的退租删除）与收入，不能容忍 24 小时误差。若控制面持续不可用超过 Class-S TTL，退租冻结由人工在数据面执行，并记入操作审计。

**降级期间的行为必须可见**：数据面在使用过期快照时持续上报"配置陈旧"指标与陈旧时长，并在管理面横幅提示。**静默地用着旧配置，比用旧配置本身更危险。**

#### 3.6.4 与控制面 3 分钟错误预算的关系

SD-000 给控制面的月度错误预算是 3 分钟，比数据面各层都严格得多。这看起来与 fail-static 矛盾——既然数据面不受影响，为什么控制面还要这么高的可用性？

因为**这 3 分钟度量的是"配置下发本身不可用"，不是"数据面受影响"**。fail-static 保证的是数据不丢，但它不保证配置及时生效：控制面宕机期间，新租户开不了通、吊销的 Token 还在写、超限的租户限不住。这些都是真实的业务与安全损害，只是不表现为数据丢失。**把预算定得严格，正是因为 fail-static 让这类故障变得"看不见"**，需要用预算强制它被认真对待。
