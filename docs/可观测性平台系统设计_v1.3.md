# SaaS 可观测性平台系统设计文档

> Google Design Doc 风格 | 状态：草案 v1.3 | 日期：2026-09
> 存储基线：VictoriaMetrics（Metrics）+ **Apache Doris 4.0.8 存算分离**（Logs + Traces）
> 容量基线：**1.5 TB/天日志开局，架构按 10 TB/天 设计**（1.5 → 10 TB 全程零架构变更，见 §4.2）
> 半结构化建模基线：**VARIANT + Schema Template + DOC 编码 + Storage Format V3**（§7.1.1）

> **v1.3 变更记录**（对齐 Apache Doris 官方可观测性实践与 4.x VARIANT 文档）：
>
> 本版只做一件事：**把 VARIANT 的建模方式从"默认用法"升级为官方推荐配置**。v1.2 的 §7.1.1 把子列数触顶描述为"天花板、触顶即退化"，这个判断不准确——官方机制是按「非空比例/访问频率」自动排序并保留 Top-N 热点路径，属于渐进降级而非悬崖；在本平台多租户同构（全租户热点路径都是 OTel 语义约定字段）的前提下，风险低于 v1.2 的估计。但查阅官方文档发现了三类 v1.2 完全没有处理的问题，其中第一类比子列数严重得多。
>
> 1. **跨租户类型冲突会静默摧毁索引（新增，P2 首位）**：官方明确「同一路径出现不兼容类型将提升为 JSONB」且「子列类型不兼容变更会丢失索引」。共享表下租户 A 写 `http.status_code: 200`、租户 B 写 `"200"`，该路径被提升为 JSONB，**索引丢失且影响该 tablet 内所有租户**；RANDOM 分桶意味着每个 tablet 都含全部租户。无报错、无感知。对策：Schema Template 锁类型 + loader 侧类型强制 + 类型冲突监控（§7.1.1 / §6.4.2 / §11）；
> 2. **启用 Schema Template 锁定 OTel 语义约定路径**：官方规定 typed path 一定参与子列列式提取且**默认不计入 `variant_max_subcolumns_count` 预算**（`variant_enable_typed_paths_to_sparse` 默认 false）。这把平台关心的字段从租户间的子列额度竞争中直接摘出，比 v1.2 的"per-tenant 字段数配额"更根本（配额降为第二道防线）；
> 3. **两张表统一启用 DOC 编码模式**：官方 VARIANT 选型矩阵将「Trace / 写入优先 / 整条返回」归入 DOC mode。关键更正——**DOC mode 并不牺牲子字段过滤**，官方原文为「子路径仍可执行子列列式提取用于按路径查询，同时额外保存一份原始 JSON」；且 `otlp-loader` 的 64 MB 批次（约 6.4 万行 span / 12.8 万行日志）远超 `variant_doc_materialization_min_rows` 默认阈值，子列化在写入时即完成，不存在"最新数据只能扫原始 JSON"的窗口。收益：compaction 内存降约 2/3、稀疏宽列导入性能提升 5~10 倍、整条文档读取数量级提升，并直接支撑 UI 展开单条日志/span 的完整 attributes（消除 v1.2 §17.4 的反模式）。代价：额外存一份原始 JSON，logs/traces 日增上调约 20%/30%（§4，M1 实测校准）；
> 4. **`storage_format = V3`（v1.2 遗漏）**：官方对"会产生超过 2000 个子列的宽表"强烈建议开启，作用是把列元数据与 Segment Footer 解耦，否则宽 JSON 场景下文件打开慢、内存开销高。注意它与既有的 `inverted_index_storage_format = V2` 是两个不同属性，两者都要设；
> 5. **倒排索引改为路径级（`field_pattern`）**：v1.2 对整个 VARIANT 列建倒排索引，会为所有子列建索引，是索引膨胀的直接来源；官方 FAQ 亦点名「误以为给 VARIANT 整体建的索引可用于子列」。3.1.x/4.0 起可用 `field_pattern` 只对指定子路径建索引，且同一路径可并存分词与不分词两套索引。**路径级索引必须配合 Schema Template**，与第 2 条配套。这取代了 v1.2「超阈值租户降级为仅 body 索引」的事后补救；
> 6. **BE 改为多盘配置，分桶数按官方双规则联立**：官方给出两条并列规则——单桶压缩后约 5 GB，且桶数约为集群磁盘总数的 3 倍。v1.2 的「4 台 BE × 1 块 1TB NVMe」只有 4 块盘，反推仅 12 桶（单 tablet 会达 19 GB）。改为 **4 台 × 3 块 500GB NVMe = 12 块盘 → logs 36 桶**，两条规则同时满足（§4 / §7.1）。这同时让 §4.2 中 10 TB 时的动作从"换大盘"变为"加盘"，更平滑；
> 7. **查询侧纪律进网关规则**：官方要求避免 `SELECT` 整个 VARIANT、应使用 `SELECT v['path']` 路径投影。查询网关的 SQL 生成器需硬性约束：列表页只允许路径投影，整条文档读仅在单条展开时发起（§8.1）；
> 8. **BE 参数与监控信号补齐**：`max_cumu_compaction_threads ≥ 8`、`vertical_compaction_num_columns_per_group = 500`、`segment_cache_memory_percentage = 20`（§7.4）；新增 Compaction Score、schema 漂移（热点路径被挤出子列化导致查询突然退化）、类型冲突事件数三类监控（§11）；
> 9. **§14 P2 重排并新增 P11**：P2 的实测优先级改为「跨租户类型冲突的发生率与爆炸半径 → 子列数增长曲线与 Top-N 取舍后的衰减 → 路径级索引 vs 整列索引的体积对比 → `trace_id` 索引占比」；新增 **P11** 跟踪 DOC mode 的三项实测（子列上限与路径级索引在 DOC mode 下是否完全生效、额外存储开销的真实比例、`variant_doc_hash_shard_count` 取值验证），其中第一项是 §7.1.1 整个方案成立的前提，若结论为否则 logs 表退回稀疏列模式。
>
> **未改动**：架构分层、采样方案、摄入链路、存储分层、多租户与计量、AI 层均沿用 v1.2；里程碑仅在 M1 的内容与出口标准中补入 VARIANT 建模基线验证与 P11。

## 0. TL;DR

构建一个多租户 SaaS 可观测性平台，覆盖 Logs / Metrics / Traces 三支柱。摄入层基于 OpenTelemetry Collector，trace 采样在客户集群内以 tail sampling 完成；Logs/Traces 经 Kafka 削峰后由自研无状态 `otlp-loader` 批量 Stream Load 进 Doris 4.0.8（VARIANT 半结构化 + 路径级倒排索引 + SQL 分析；半结构化建模基线为 **Schema Template + DOC 编码 + Storage Format V3**，§7.1.1），Metrics 直连 VictoriaMetrics 集群（PromQL 生态，本地留存 180 天）；之上是统一查询网关，负责认证、租户路由与三信号关联跳转。

**容量设计目标：开局 1.5 TB/天日志、1 亿落库 span、500 万活跃 series；架构按 10 TB/天 设计，1.5 → 10 TB 全程只需加节点与调参数，无架构变更**（§4.2 逐项推演）。所有无状态层水平扩展，存储层按分片扩展，整体可用性 SLO 99.9%。

## 1. 背景与问题陈述

可观测性 SaaS 的核心矛盾是：**写入吞吐极大、查询模式两极分化（点查 vs 分析）、多租户隔离要求严格，而单位数据价值密度低**（成本敏感）。单一引擎很难同时满足时序高基数写入、全文检索、OLAP 分析三类负载，因此采用"专用引擎 + 统一分析底座"的混合架构：

- Metrics：数据模型高度特化（数值时间序列 + label 索引 + PromQL），VictoriaMetrics 是事实标准级选择；
- Logs / Traces：本质同为"宽事件"（wide event），同库存储使 Log↔Trace 关联成为一次 SQL JOIN，且 VARIANT 类型对 OTel 的半结构化 attributes 建模自然。

**为什么 metrics 不并入 Doris**（v1.2 补充论证，此项为已定稿决策，不再重开）：

| 维度 | VictoriaMetrics（本设计） | 全量并入 Doris |
|------|--------------------------|----------------|
| 查询语言 | PromQL 原生，Grafana 零成本接入 | 需自研 PromQL→SQL 翻译层（counter reset、staleness marker、5m lookback delta、`@`/`offset`、`histogram_quantile`、`on/group_left`），多人年投入且难以追平生态预期 |
| 日均落盘（500 万 series） | 约 10 GB/天（TSID 倒排 + delta/gorilla 编码，约 0.7 B/sample） | 约 150 GB/天（通用列存每行开销高一个量级），与日志同量级 |
| 单 series 时间窗点查 | TSID 索引直接定位 | label 匹配后列扫描 |
| 高基数 churn 承压 | 成熟（K8s 场景事实标准） | compaction 写放大未经验证 |

500 万活跃 series / 30s 采集 ≈ **16.7 万 samples/s ≈ 144 亿 samples/天**，是日志条数（30 亿/天）的 4.8 倍行数；用通用列存承载它等于把 Doris 集群规模翻倍去换一个更差的查询模型。

## 2. 目标与非目标

### 2.1 目标（Goals）

| # | 目标 | 验收标准 |
|---|------|----------|
| G1 | 三信号统一摄入 | 标准 OTLP 协议接入，兼容 Prometheus remote-write / scrape |
| G2 | 多租户隔离 | 数据、配额、查询资源三级隔离；租户间零数据串扰 |
| G3 | 查询体验 | 日志检索 p95 < 3s（7 天热数据）；单 trace 瀑布加载 p95 < 1s；PromQL 查询兼容 Grafana |
| G4 | 信号关联 | 指标异常点 → Trace → Logs 一键跳转；**实现不依赖 VM exemplar**（§7.7 / §8.2），跳转有效命中率纳入实测 SLI |
| G5 | 告警 | Metrics 告警延迟 < 1min；日志告警（基于调度 SQL）延迟 < 2min |
| G6 | 成本可控 | Doris 存算分离（S3 主存储 + 本地缓存），180 天长期留存走 Iceberg 开放归档层；**单位经济性模型见 §4.3，M1 后填数并作为定价输入** |
| G7 | 可运维 | 存储节点故障自动恢复；**摄入链路回放窗口 12 小时**（Kafka），更长窗口的数据重建走归档层 + 客户侧 gateway 持久队列（v1.2 调整，原为 3 天）。**12 小时是承诺上限，落库链路故障必须在此窗口内恢复**（§6.3） |
| G8 | 架构前瞻性（v1.2 新增） | 1.5 → 10 TB/天 的扩容路径全程无架构变更，仅加节点与调参数（§4.2 逐项推演，每个扩容动作零停机） |

### 2.2 非目标（Non-Goals）

- N1：不做 APM 的代码级 profiling（Pyroscope 类），留作二期
- N2：不做 RUM / 前端监控的 Session 回放
- N3：不自研时序引擎或 OLAP 引擎
- N4：一期不做 eBPF 自动埋点，要求用户侧显式接入 OTel
- N5：不做跨云多活的写双活（一期单 Region 三 AZ，跨 Region 容灾列入 M5，一期不承诺）

## 3. 需求

### 3.1 功能需求

1. **摄入**：OTLP gRPC/HTTP、Prometheus remote-write、vmagent scrape 兼容；摄入端鉴权（per-tenant token）
2. **日志**：全文检索（关键字/短语）、字段过滤、时间范围、直方图趋势、日志模式聚类（二期）
3. **指标**：PromQL 全量兼容、Grafana 数据源、**180 天本地留存 + recording rules 降分辨率视图**
4. **Trace**：按 trace_id 点查、按服务/操作/耗时/状态多维过滤检索、瀑布图、服务依赖拓扑（由 span 聚合生成）
5. **告警**：阈值/异常/缺席告警，通知渠道（Webhook/IM），静默与分组
6. **管理面**：租户/项目/Token 管理、配额与用量计量、留存策略配置、采样策略下发
7. **数据治理（v1.2 新增）**：摄入侧 PII 脱敏规则、退租数据删除、管理面操作审计（§9.5）

### 3.2 非功能需求（SLO/SLI）

| 指标 | SLO | v1.2 变更说明 |
|------|-----|--------------|
| 摄入端到端延迟（写入 → 可查询） | **p99 < 10s，目标 p50 < 5s** | v1.1 为 TBD。改用自研 `otlp-loader`（§6.4）后延迟可控：Collector batch 1s + Kafka + loader 攒批 2s + Stream Load 提交 1~2s ≈ 3~5s。M1 实测复核后定稿 |

| PromQL 即时查询（24h 窗口） | p95 < 2s | — |
| 平台可用性（摄入 + 查询） | 99.9%（月度，约 43 分钟/月） | BE 由 3 台改 4 台（N+1）以匹配此预算 |

| exemplar 跳转有效命中率 | ≥ 70%（M1/M3 实测标定） | v1.2 新增，对应 G4 |

## 4. 规模估算（Back-of-the-Envelope）

**基线：1.5 TB/天日志开局**，峰值按均值 3 倍计（全文统一使用 3 倍峰均比，v1.1 中公式用 200%、正文用 300% 的不一致已修正）。**架构按 10 TB/天 设计**，扩容推演见 §4.2。

| 维度 | 假设 | 推导 |
|------|------|------|
| 日志写入 | 1.5 TB/天原始，平均 500 B/条 | ≈ 30 亿条/天 ≈ **3.5 万 EPS（峰值 10.5 万 EPS）** |
| Span 写入 | **1 亿 span/天（采样后落库口径）**，平均 1 KB | ≈ 1150 span/s（峰值 3500），≈ 100 GB/天原始。**采样前约 10 亿 span/天**（tail sampling 保留率约 10%），即客户集群 gateway 需处理 ≈ 1.2 万 span/s（峰值 3.5 万） |
| 指标写入 | 500 万活跃 series，30s 采集间隔 | ≈ 16.7 万 samples/s ≈ 144 亿 samples/天 |
| Doris 侧存储（存算分离，**v1.3 含 DOC 编码开销**） | 压缩率 8:1；DOC mode 额外存一份原始 JSON（logs +20%、traces +30%，§7.1.1，M1 校准） | logs ≈ **230 GB/天** + traces ≈ **17 GB/天** + 派生/元数据 ≈ 12 GB/天 ≈ **260 GB/天** → 热窗口 7 天 ≈ **1.8 TB**（S3 上另有温层至 15 天） |
| **BE 本地缓存**（v1.3 重算） | 7 天数据 + **倒排索引（路径级索引后按 60% 计）** | 1.8 TB × 1.6 ≈ **2.9 TB** → **4 台 BE × 3 × 500GB NVMe = 6 TB**，留约 50% 余量 |
| 归档层存储 | Iceberg（Parquet + zstd）on S3，180 天 | ≈ 42 TB，与 Doris 内部 S3 数据分 bucket 隔离 |
| Doris 集群 | 官网公式：峰值 CPU 核数 =（日增量/86400 × 峰均比 300%）/ 单核 10MB/s；再按查询预留 50% 折算 | 1.6 TB/天 → 均值 18.5 MB/s → 峰值 56 MB/s → 5.6 核 → 含查询预留 ≈ 12 核。**约束项不是 CPU 而是缓存容量、磁盘数与 N+1 可用性** → **4 台 16C64G + 3 × 500GB NVMe BE**（CPU 常态水位预期 < 20%；**多盘是为满足官方「桶数 ≈ 磁盘数 × 3」规则**，见 §7.1）；FE 3 台小规格 |
| **Doris Meta Service**（v1.2 新增） | 存算分离必备，无状态 | **3 副本 × 4C8G**，与 Recycler 同机部署 |
| **Doris Recycler**（v1.2 新增） | 回收 S3 上的过期 rowset | **2 副本 × 4C8G**（与 MS 混部） |
| **FoundationDB**（v1.2 新增） | Meta Service 的元数据后端，`double` 冗余 | **3 节点 × 4C16G + 200GB SSD**（每 AZ 一台）；元数据量在 GB 级，瓶颈是事务 QPS 不是容量。**元数据丢失 = 全集群数据不可读，是本架构最高等级单点**，备份策略见 §10.1 |
| VM 集群 | 单 vmstorage 承载 ≈ 500 万活跃 series，**副本因子 2** | 500 万 × 2 = 1000 万 series 副本 → **4 个 vmstorage（2 分片 × 2 副本）**，每节点 250 万 series；内存 250 万 × 2GB × 1.5 churn ≈ 7.5GB → **16GB 规格** |
| **VM 存储（180 天，v1.2 调整）** | 144 亿 samples/天 × ≈0.7 B/sample × 2 副本 | ≈ **20 GB/天 → 180 天 ≈ 3.6 TB**，摊到 4 节点 ≈ **0.9 TB/节点**。这是全平台最便宜的一块存储，无需降采样外置（原 v1.1「降采样回 Doris」已删除） |
| Kafka（v1.2 调整） | 仅 logs + traces；峰值摄入带宽 ≈ 56 MB/s；**保留 12 小时** | **3 节点**；1.8 TB/天（OTLP 编码后）× 0.5 天 × 3 副本 ≈ 2.7 TB，lz4 后 ≈ **1.4 TB** → 单节点 0.5~1 TB 磁盘。v1.1 保留 3 天时为 15 TB，是 Doris 热窗口的 5 倍，成本倒挂；12 小时后 Kafka 从第二大存储项降为可忽略项 |
| 查询 QPS | 日志检索 10 QPS，PromQL 50 QPS，Trace 点查 5 QPS | 查询层无状态，横向扩 |

**关键推论**：

- 瓶颈在**日志写入带宽与 BE 本地缓存命中率**（缓存命中决定热查询 p95，未命中回源 S3 延迟上升一个量级）——因此 v1.2 把**缓存命中率提升为一级 SLI**（§11），并在缓存容量计算中计入倒排索引；
- 500 万活跃 series 中典型 20% 为高基数 churn（K8s 短生命周期 pod label），vmstorage 内存规划按 1.5 倍计；
- **tablet 粒度与分桶数校验（v1.3 按官方双规则联立）**：官方日志实践给出两条并列规则——① 单桶压缩后约 5 GB；② 桶数约为**集群磁盘总数的 3 倍**。v1.2 的单盘配置只有 4 块盘，规则 ② 反推仅 12 桶、单 tablet 达 19 GB，与规则 ① 冲突。改为 4 台 × 3 盘 = 12 块盘后两条规则收敛：logs ≈ 230 GB/天 ÷ **36 buckets** ≈ 6.4 GB/tablet ✓（12 × 3 = 36 ✓）；traces ≈ 17 GB/天 ÷ **8 buckets** ≈ 2.1 GB/tablet ✓（traces 体量小，规则 ① 为准，8 桶已足够并行度）。**规模增长后两条规则会分叉**（§4.2 的 10 TB 点上规则 ① 要 300 桶、规则 ② 只要 90 桶），届时以规则 ①（tablet 物理大小）为准，规则 ② 视为并行度下限；
- 存储成本结构：存算分离后全部数据落 S3，本地 NVMe 只承担 7 天缓存；成本控制的第一杠杆是**热窗口时长与归档压缩率**；
- **跨 AZ 流量费**（Kafka 3 副本 + VM 2 副本 + FDB 跨 AZ 复制，约 50~100 GB/天量级）需计入 §4.3 成本模型；
- **一期即采用存算分离的理由**：终点规模在 10 TB/天，存算分离在该规模下 BE 数量减半且写入只需单副本；若先走存算一体、到 10 TB 再切换，迁移窗口正好落在业务量最大的时刻。代价是一期就要承担 Meta Service + Recycler + FoundationDB 的运维面，这三个组件已补入本节、§5 架构图、§10.1 故障矩阵与 §14 P9。

### 4.1 容量水位与扩容预案

**原则：按水位触发动作，不凭感觉扩容；所有动作零停机。**

| 信号 | 水位 | 动作 | 注意点 |
|------|------|------|--------|
| Doris 单 tablet 大小 | > 8 GB | 上调 `dynamic_partition.buckets` | **只对新分区生效，须提前一个分区周期调整**，旧分区不自动 rebalance |
| BE 本地缓存命中率 | < 90% | 加 BE（扩缓存层）或缩短热窗口 | 存算分离下加 BE 只扩缓存，自动 warmup；**这是热查询 p95 的第一因** |
| BE CPU 常态 | > 50% | 加 BE | — |
| **Compaction Score**（v1.3 新增） | 持续上升 | 降低导入压力 / 复核 `variant_max_subcolumns_count` 是否过高 | 官方给出的 VARIANT 宽列首要预警信号；DOC mode 下 compaction 内存已降约 2/3，若仍上升说明导入速率或子列规模超预期 |
| **VARIANT 类型冲突事件**（v1.3 新增） | 任一 typed path 出现 > 0 | 立即排查该租户埋点，在 loader 侧强制转换或旁路 | **类型冲突会把路径提升为 JSONB 并静默丢失索引，污染该 tablet 内所有租户**（§7.1.1），不允许积压 |
| **热点路径被挤出子列化**（v1.3 新增） | 关键路径退出子列存储 | 补入 Schema Template 锁定该路径 | 官方称之为 schema 漂移，症状是某字段查询性能突然退化而平台侧无任何配置变更 |
| FoundationDB 事务延迟 p99 | > 10 ms | 加 FDB 节点 / 检查 rowset 元数据膨胀 | MS 元数据写入与 Doris compaction 频率强相关 |
| 单 vmstorage series | > 400 万 | 成对加分片（4 → 6 → 8） | 新数据走新分片，旧数据随留存自然过期，**无数据迁移** |
| Kafka 磁盘 | > 70% | 加 broker + 分区重分配 | — |
| Kafka 单分区峰值 | > 4 万 EPS | 加分区 | 分区只增不减，对新消息生效 |
| `otlp-loader` 消费 lag | > 60s 持续 5 分钟 | 加 loader 副本（上限 = 分区数） | 无状态，HPA 可自动 |
| **Kafka 最老未消费消息年龄** | > 2 小时 | **P1 呼叫值班**；> 6h 时临时上调 `retention.ms` | 保留期仅 12h，这是数据丢失前的最后预警（§6.3） |
| 已过期未归档分区数 | > 2 | 排查归档管线 | **不允许自动 DROP 兜底**（§7.4） |
| 单租户日增 | > 300 GB | 触发大租户评估（§9.4） | 按 1.5 TB 基线下调，原为 500 GB |

### 4.2 向 10 TB/天 的扩容推演（v1.2 新增，对应 G8）

**目的：证明 1.5 → 10 TB/天 全程无架构变更。** 下表逐组件给出终点规格与迁移动作。

| 组件 | 1.5 TB/天（开局） | 10 TB/天（终点） | 扩容动作 | 是否零停机 |
|------|------------------|-----------------|----------|-----------|
| 日志 EPS | 3.5 万（峰 10.5 万） | 23 万（峰 70 万） | — | — |
| Doris BE | 4 × 16C64G + 3 × 500GB NVMe | **10 × 16C64G + 3 × 1TB NVMe** | 加节点 + 换盘，存算分离下新 BE 挂同一 S3 自动 warmup，无数据搬迁 | ✓ |
| Doris 磁盘总数（决定分桶下限） | 12 块 | 30 块 | 加节点即加盘 | ✓ |
| Doris 热缓存需求（v1.3 含 DOC 开销） | 2.9 TB | **19 TB**（1.7 TB/天 × 7 天 × 1.6 索引系数） | 随 BE 数与单盘容量线性扩（30 块 × 1TB = 30 TB） | ✓ |
| Doris FE | 3 × 小规格 | 3 × 中规格（纵向） | FE 滚动替换 | ✓ |
| Meta Service / Recycler | 3 + 2 副本 | 5 + 3 副本 | 无状态，加副本 | ✓ |
| FoundationDB | 3 × 4C16G | **5 × 8C32G**（元数据仍在 GB 级，扩的是事务 QPS） | FDB 支持在线加机器与重配置 | ✓ |
| logs 表 buckets | 36 | **300**（1.5 TB/天 ÷ 5 GB；此处规则①主导，规则②的 30 盘 × 3 = 90 仅为下限） | 调 `dynamic_partition.buckets`，只对新分区生效 | ✓ |
| traces 表 buckets | 8 | **24** | 同上 | ✓ |
| Kafka | 3 节点，logs 12 / traces 6 分区 | **6 节点，logs 24 / traces 12 分区** | 加 broker + 分区扩容（只增不减） | ✓ |
| Kafka 存储（12h×3副本，lz4） | 1.4 TB | 8.5 TB | 随 broker 扩 | ✓ |
| `otlp-loader` | 4 副本 | 16 副本 | 无状态 HPA，上限受分区数约束（故分区数起步即留余量） | ✓ |
| VM vmstorage | 4（2 分片 × 2 副本） | **14（7 分片 × 2 副本）** | 成对加分片，旧数据随留存过期，无迁移 | ✓ |
| VM 存储（180 天） | 3.6 TB | 24 TB | 随节点扩 | ✓ |
| 归档层（180 天） | 42 TB | 280 TB | S3 弹性，无动作 | ✓ |
| 摄入网关 / Collector / 查询网关 | HPA | HPA | 无动作 | ✓ |

**结论**：终点规格里没有任何一项需要更换引擎、改变数据模型或重建表结构。三个需要**提前决策**的参数是：

1. **Kafka 分区数起步即按增长预留**（分区只增不减，但过多分区会增加 broker 开销）——logs 起步 12 分区（当前只需 3 个），为 10 TB 时的 24 分区留一半余量；
2. **`dynamic_partition.buckets` 必须提前一个分区周期调整**，否则当天分区的 tablet 会过大；把它接到 §4.1 的水位告警上，由容量巡检任务自动提单；
3. **BE 盘位与单盘容量选型（v1.3 调整）**：起步即按**多盘**配置（4 台 × 3 盘），一是满足官方「桶数 ≈ 磁盘数 × 3」规则，二是让 10 TB 时的动作从"换大盘"变为"加节点顺带加盘"。机型需预留 ≥3 个 NVMe 盘位并支持换 1TB 盘。

**真正的下一个架构决策点在 10 TB/天 之后**：届时跨 AZ 流量费显著化、大租户独立计算组成为常态（§9.4）、可能需要按 Region 做数据面分片。这些不在本文档范围。

**分层原则**：

1. **Logs/Traces 与存储之间必须有 Kafka**——解耦峰值、支持回放、写入端故障时数据不丢；**Metrics 例外**：回放价值最低（断点可容忍），直连 vminsert，由 vmagent 磁盘队列 + 客户端重发兜底。**但 metrics 路径必须实现端到端背压**，否则兜底只存在于纸面（§6.4）；
2. **落库由自研 `otlp-loader` 承担而非 Routine Load**（v1.2 修正，§6.4）——OTLP 的嵌套结构需要展开成行，这是 Routine Load 做不到的；
3. **无状态层（网关、Collector、loader、查询网关）全部 Deployment + HPA**，有状态层（Kafka、Doris 全家、VM、FDB）各自独立扩缩容；
4. **控制面与数据面彻底分离**：控制面（租户、配额、规则）故障时，数据面按最后一次下发的配置继续运行（fail-static）；
5. **分区删除是唯一不可逆操作，必须经过归档校验门禁**（§7.4），任何自动化路径都不得绕过。

## 6. 详细设计 — 摄入链路

### 6.1 摄入网关层

- **职责**：TLS 终止、Token 鉴权（查本地缓存的租户映射，控制面异步同步）、租户级限流（令牌桶，按 bytes/s 与 events/s 双维度）、**PII 脱敏规则执行（§9.5）**、协议归一（remote-write → OTLP metrics）。
- **限流行为**：超限返回 429 + `Retry-After`；对日志类负载同时下发"客户端降采样"信号，避免无意义重试风暴。
- **爆炸半径控制**：每租户独立限流桶，大租户打满只影响自己。

### 6.2 平台侧 OTel Collector Gateway 集群

- **流水线**：`receiver(otlp) → memory_limiter → tenant_enricher → batch → kafka_exporter(encoding=otlp_proto)`
- **v1.2 重要变更：平台侧不再做任何 trace 采样决策。** 采样已在客户集群的 cluster-gateway 以 tail sampling 完成（§6.5.4），平台侧 Collector 退化为富化 + 转发。
- **富化**：注入 `tenant_id`、`k8s.cluster/namespace/pod`、环境标签。所有富化在摄入侧完成，查询侧不做 JOIN 维度表——宽表范式，拿空间换查询确定性。
- **编码约定**：kafka exporter 使用 `otlp_proto`（而非 JSON），由下游 `otlp-loader` 解析。这比 JSON 体积小约 30%、解析快数倍，且 schema 由 OTel proto 定义保证，不会因字段顺序或转义问题出错。

> **v1.1 采样方案为何被推翻（保留记录，避免后续讨论反复）**
> v1.1 定稿的是「SDK 按 trace_id 哈希做 head sampling（默认 10%）+ 集群 gateway 对错误 span 与慢 trace 做补偿保留」。这个组合在实现层面是空操作：**SDK 的采样决策发生在 span 创建时，未被采样的 span 根本不会导出**，gateway 能看到的只有那 10%，对它们做"补偿保留"没有任何增量——错误 trace 依然按 10% 随机丢弃 90%，而错误 trace 恰恰是排障最需要的部分。v1.2 改为在 cluster-gateway 做真正的 tail sampling（§6.5.4）。

### 6.3 Kafka 缓冲层

- **Topic 设计**（按信号分 topic，租户以 partition key 隔离；SaaS 规模下按租户分 topic 是元数据爆炸反模式，已否决）：`logs.raw`（partition key = `tenant_id + service`，保证同租户同服务有序）、`traces.raw`（partition key = `trace_id`）。metrics 不过 Kafka（§6.4）。
- **分区数**：logs **12 分区起步**（当前峰值 10.5 万 EPS 只需 3 个，多出的是为 10 TB 时的 24 分区预留消费并行度，见 §4.2）；traces **6 分区**。注意 partition key 含 tenant_id，超大租户单 key 可能造成分区热点，超过单分区容量时在 key 中引入 bucket 后缀打散。
- **保留 12 小时（v1.2 由 3 天下调）**：v1.1 的 3 天保留占用 15 TB，是 Doris 热窗口（2.8 TB）的五倍，成为仅次于归档层的第二大存储项，成本倒挂。而 3 天回放的必要性经不起推敲——Doris 故障在存算分离下数据在 S3 不丢、BE 重建即可；误删有归档层；新引擎 PoC 可从归档层灌数。真正需要 Kafka 回放的是「落库链路停摆到恢复」的窗口。12 小时后 Kafka 占用降至约 1.4 TB，从第二大存储项变为可忽略项。
- **12 小时窗口的代价必须被显式管理（v1.2）**：保留期就是落库链路的**故障恢复预算**，12 小时意味着一次跨夜或周末的 `otlp-loader` / Doris 写入故障如果无人响应，最老的数据会开始被 Kafka 删除且不可恢复。因此保留期下调必须与下列三条配套，缺一条就不要下调：

  | 项 | 阈值 | 动作 |
  |----|------|------|
  | `otlp-loader` 消费 lag（扩容触发） | > 60s 持续 5 分钟 | HPA 自动加副本（§4.1） |
  | **Kafka 最老未消费消息年龄** | **> 2 小时** | **P1 呼叫值班**——留出 10 小时人工处置余量 |
  | 同上 | > 6 小时 | 升级并启动降级预案（§10.2），必要时临时上调 `retention.ms` 争取时间 |

  `retention.ms` 是可在线修改的 topic 配置，紧急时上调即可延长窗口（受磁盘水位约束，§4.1 已按 0.5~1 TB/节点规划，留有约一倍余量可临时扩到 24 小时）。这条应当写进值班 runbook。
- **两种故障的保护窗口不同，不要混为一谈**：落库链路故障由 Kafka 的 12 小时兜底；**平台摄入入口故障**（网关/Collector 不可用）由客户侧 cluster-gateway 的 `file_storage` 持久队列兜底，窗口仍是 ≥2 小时（§6.5），与本次调整无关。后者是更短的那个约束，对入口可用性的要求高于落库链路。
- **若后续确需长保留**，用 Kafka 分层存储（KIP-405）把冷段放 S3，而不是加本地盘。
- **不启用精确一次（EOS）**：摄入链路采用「at-least-once + Stream Load label 幂等 + DUPLICATE 模型容忍微量重复」（§6.4）。EOS 的吞吐代价在日志场景不值得。

### 6.4 写入路径（v1.2 重写）

| 路径 | 方案 | 理由 |
|------|------|------|
| Logs → Doris | **自研 `otlp-loader`**（无状态 Go consumer，Kafka → OTLP protobuf 解析 → 展开 → 批量 Stream Load） | Routine Load 不可行，见下 |
| Traces → Doris | 同上，共用 loader 二进制，按 topic 配置不同的展开与建表映射 | 同上 |
| Metrics → VM | **直连 vminsert（不过 Kafka）**，前置无状态 metrics-ingest 服务做写入整形与 exemplar 抽取 | metrics 回放价值最低；省掉 Kafka 上绝大部分存储压力 |

#### 6.4.1 为什么不能用 Routine Load（v1.2 核心修正）

OTLP 的 JSON/protobuf 结构是三层嵌套数组——`resourceLogs[].scopeLogs[].logRecords[]`（traces 同理 `resourceSpans[].scopeSpans[].spans[]`）。**Routine Load 的 `jsonpaths` 只能做扁平字段映射，无法把一条 Kafka 消息展开成 N 行**。v1.1 §6.4 写的「Routine Load + 预定义 JSON 展开，span 数组拍平为行」没有对应的 Doris 能力支撑，会在 M1 第一周撞墙，且影响的是 logs 与 traces 两条主链路。

#### 6.4.2 `otlp-loader` 设计

```
Kafka consumer group（offset 即全部状态，服务本身无状态）
  → 解析 OTLP protobuf（官方 go.opentelemetry.io/proto 反序列化）
  → 展开：ResourceX 的 resource attributes 下推到每一行，输出扁平行
  → ★ v1.3：typed path 类型规范化 + JSON key 长度校验（见下第 8、9 条）
  → 攒批：满 64 MB 或满 2s 触发，取先到者
  → Stream Load（HTTP PUT → FE/BE），format=json，strip_outer_array=true
  → 成功返回后才 commit Kafka offset
```

**关键设计点**：

1. **幂等**：Stream Load `label = {topic}-{partition}-{startOffset}-{endOffset}`。Doris 对同名 label 的重复导入直接拒绝，因此「at-least-once 消费 + label 去重」在效果上等价于 exactly-once。**注意**：Doris 的 label 保留期由 `label_keep_max_second` 控制（默认 3 天），必须 ≥ Kafka 保留期（12h），否则回放时幂等失效。默认值已满足，但**紧急上调 `retention.ms` 时要同步检查这条约束**（§6.3）——这两个参数是一对，写入部署检查清单。
2. **无状态**：offset 存在 Kafka，consumer group 自动 rebalance，副本可随 HPA 增减，上限为分区数（故 §6.3 分区数起步即留余量）。
3. **背压**：Stream Load 返回 `-235`（too many tablet versions）、`-238`、内存超限等错误时，指数退避重试且**不 commit offset**，积压由 Kafka 承接。`-235` 是高频小批量导入的经典问题，缓解手段是三条叠加：批次不小于 64MB/2s、表启用 `time_series` compaction policy（§7.1）、RANDOM 分桶配合 `load_to_single_tablet=true`（下条）。
4. **`load_to_single_tablet=true`**（v1.2 补强项）：RANDOM 分桶下必须显式开启，让单次导入只写一个 tablet。否则每批导入都会写满所有 tablet，小文件数与 compaction 压力按 bucket 数倍增——这是 v1.1 选了 RANDOM 分桶却没配套的一个遗漏。
5. **端到端延迟**：Collector batch 1s + Kafka 传输 + loader 攒批 2s + Stream Load 提交 1~2s ≈ **3~5s**，对应 §3.2 的 `p99 < 10s`。相比 Routine Load 攒批机制下的 10~30s 是数量级改善，这是自研 loader 的第三项收益（前两项是展开与幂等）。
6. **可观测性**：loader 自身暴露消费 lag、Stream Load 成功率、`-235` 错误率、批次大小分布、端到端延迟直方图，全部进 §11 自监控。
7. **规模**：1.5 TB/天 下 4 副本（每副本约 3 个分区）；10 TB/天 下 16 副本。
8. **★ v1.3 — typed path 类型规范化（VARIANT 类型冲突的第二道防线）**：对 §7.1 / §7.2 Schema Template 声明的每一个 typed path，loader 在写入前按声明类型强制转换（如 `"200"` → `200`）。转换失败时**不写入主路径**，改写入 `<path>__raw`（STRING）影子路径，并递增 `variant_type_conflict_total{tenant,path,declared_type}` 指标。
   - 理由见 §7.1.1（2）：一旦不兼容的值进入主路径，Doris 会把该路径提升为 JSONB 并**静默丢失索引**，而 RANDOM 分桶意味着该 tablet 内**所有租户**的这个字段一起失去索引。这是无法事后修复的污染（只能重建分区），必须在写入前拦截。
   - 该指标是零容忍告警（§4.1 / §11）：出现即说明有租户埋点违反 OTel 语义约定，需推治理事件。
9. **★ v1.3 — JSON key 长度校验**：Doris VARIANT 的 JSON key 长度上限为 255 字节，超限的 key 在 loader 侧截断并计数，避免整批导入失败。
10. **★ v1.3 — 批次大小与 DOC 编码的关系**：DOC mode 下 `variant_doc_materialization_min_rows`（示例值 10000）决定"多大的批次在写入时就做子列化、多小的批次留到 compaction 再做"。64 MB 批次约合日志 12.8 万行、span 6.4 万行，**均远超该阈值**，因此子列化在写入时完成，不存在"最新数据只能扫原始 JSON"的查询退化窗口。反过来说，**若后续为压延迟而调小批次，必须同步核对这个阈值**——这是一对耦合参数，写入部署检查清单。

> **对 v1.1「取消自研 Writer 消费组」决策的修正说明**：该决策对 metrics 成立（metrics 直连 VM，确实不需要消费组），对 logs/traces 不成立。v1.2 恢复自研 loader，但它与 v1.0 设想的"有状态 Writer"不同——offset 在 Kafka，服务完全无状态，运维成本接近于一个普通的 Deployment。

#### 6.4.3 Metrics 写入整形与端到端背压

**高基数防护**：metrics-ingest 服务（无状态，可水平扩）内置 per-tenant series 基数计数器（HyperLogLog 近似），超配额后按控制面下发的 label 白名单做 drop 或聚合（drop `pod_uid`、`container_id` 类 churn label），并生成"基数审计事件"供租户自查。这是 SaaS 模式区别于自建 VM 的核心增量。

**exemplar 抽取（v1.2 新增）**：metrics-ingest 从 OTLP metrics 中抽取 exemplar，按 §7.7 的采样规则写入 Doris `metric_exemplars` 表。这一步替代了 v1.1 依赖的「VM 原生 exemplar 存储」。

**端到端背压（v1.2 新增，对应评审 H5）**：取消 Kafka 的兜底逻辑是「vmagent 磁盘队列 + 客户端重发」，但 metrics 的实际路径是：

```
客户集群 gateway → 平台摄入网关 → 平台 Collector → metrics-ingest → vminsert
                    └────────── 两跳平台侧无状态服务 ──────────┘
```

这两跳的 exporter 默认使用**内存队列**。若 vminsert 或 metrics-ingest 故障，平台侧内存队列撑爆就直接丢数据，客户侧的 `file_storage` 持久队列完全用不上——因为没有人把错误透传回去。**兜底链路只在纸面上成立。**

强制要求：

1. 每一跳在下游不可用时**必须返回可重试错误**（gRPC `UNAVAILABLE` / `RESOURCE_EXHAUSTED`，HTTP 503/429），不得吞掉错误后返回成功；
2. 平台侧 Collector 与 metrics-ingest 的 `sending_queue` 满时拒绝新请求而非丢弃队首；
3. **M2 必须包含一个故障注入用例**：停掉 vminsert 30 分钟，验证数据最终从客户侧 gateway 的持久队列完整回补，丢失率 < 0.01%；
4. **可选工程优化**：把 metrics-ingest 的基数防护与 exemplar 抽取做成 Collector 的自研 processor，将两跳合成一跳——少一跳就少一处丢数据的地方。列为 M2 备选项，不阻塞主线。

### 6.5 多 K8s 集群接入设计（用户视角）

**接入模型：一个集群 = 一套轻量 Agent + 一个集群身份。** 用户操作仅三步：控制台"接入集群" → 复制内嵌凭证的 `helm install` 命令 → 在目标集群执行。每集群重复一次即完成多集群接入。

**集群内 Agent 拓扑（v1.2 调整：cluster-gateway 承担 tail sampling）**：

```
K8s 集群内：
┌────────────────────────────────────────────────────┐
│ DaemonSet：node-agent（OTel Collector）              │
│  · filelog receiver 采集 /var/log/pods（容器日志）    │
│  · 接收本机 Pod OTLP（trace/metrics，应用打 localhost）│
│  · kubelet stats / host metrics                     │
│  · 【v1.2】trace 出口用 loadbalancing exporter，      │
│     routing_key=traceID，k8s resolver 发现 gateway   │
│     → 保证同一 trace 的所有 span 落到同一个 gateway 副本│
└──────────────┬─────────────────────────────────────┘
               │ 集群内 gRPC（trace 按 traceID 一致性路由）
┌──────────────▼─────────────────────────────────────┐
│ Deployment：cluster-gateway（OTel Collector，2+ 副本）│
│  · k8sattributes 富化（namespace/labels/owner）       │
│  · 注入 cluster_id + tenant_id                      │
│  · 【v1.2】tail_sampling processor（见 §6.5.4）       │
│  · batch + file_storage 持久队列（断网缓冲 ≥2h）      │
│  · 唯一出口：TLS 443 → 平台摄入网关                   │
└────────────────────────────────────────────────────┘
配套：vmagent（或 Collector prometheus receiver）抓取
      kube-state-metrics / cadvisor / 应用 /metrics
```

**设计要点**：

1. **单出口原则**：DaemonSet 只采集不出集群，所有外发流量收敛到 cluster-gateway——企业客户安全团队只需放行一条 egress 规则（出方向 443），平台永不主动连入客户集群。
2. **身份与凭证**：层级模型 `租户 → 项目（环境） → 集群`；注册集群时生成 `cluster_id` + 集群级 Token（Helm values 注入为 Secret），Token 可独立吊销、限流、计量——某集群异常刷量只熔断该集群。
3. **cluster 是一等公民**：跨集群必然存在同名 namespace/service，因此摄入侧强制注入 `k8s.cluster.id`（平台分配不可变，显示名可改）；VM 侧由 vmagent `external_labels` 统一注入 `cluster` label，防止用户伪造串数据；UI 上 cluster 是全局过滤维度。
4. **大租户形态**：单集群日增 > 1 TB 时 gateway 独立 HPA（按上行速率扩缩），Kafka 分区键升级为租户+集群组合（仍为共享 topic，不开独立 topic）；混合云/无外网集群支持"边缘中转"模式。

#### 6.5.4 Trace 采样：一期即在 cluster-gateway 做 tail sampling（v1.2 重写）

> 编号沿用 v1.1（6.5.1~6.5.3 的内容已并入上方「设计要点」列表），以保持评审记录中对 §6.5.4 的引用有效。

**方案**：

| 层 | 职责 | 配置要点 |
|----|------|----------|
| 应用 SDK | **AlwaysOn**（不做采样决策，全量导出到本机 node-agent） | 集群内 localhost 流量，成本可忽略 |
| node-agent（DaemonSet） | 不做采样决策；trace 出口用 `loadbalancing` exporter，`routing_key: traceID`，`resolver: k8s`（服务发现 cluster-gateway） | **保证同一 trace 的所有 span 汇聚到同一个 gateway 副本**——这是 tail sampling 能工作的前提 |
| cluster-gateway | `tail_sampling` processor，`decision_wait: 10s` | 策略取并集（OR）：① `status_code = ERROR` 全保留；② `latency > 服务 p99` 全保留；③ `probabilistic 10%` 基线采样 |

**内存开销核算**（此前被推迟到二期的唯一理由）：

- 1.5 TB/天 基线：采样前约 1.2 万 span/s（峰值 3.5 万），`decision_wait 10s` → 峰值驻留 ≈ 35 万 span × 1 KB ≈ **350 MB**，分摊到客户集群 2~4 个 gateway 副本，**每副本 100~175 MB**；
- 10 TB/天 终点：总驻留 ≈ 2.3 GB，分摊到 8+ 副本仍在单副本 300 MB 量级。

结论：内存不是障碍，v1.1 把它推到二期是过度保守。**一期即上。**

**收益**：

1. **错误 trace 100% 保留**——这是 head sampling 方案根本做不到的，也是排障场景最核心的诉求；
2. **慢 trace 100% 保留**，延迟分析不再受随机采样干扰；
3. **exemplar 跳转命中率大幅提升**：exemplar 挂载的通常是异常指标点（高延迟、错误率上升），其指向的 trace 大概率正是被策略 ① ② 保留的那批，实际有效命中率预期 ≥ 70%（远高于 head sampling 的 10%），纳入 §3.2 SLI 实测；
4. 采样率调整由控制面下发到 gateway，**无需应用重启或改代码**。

**已知缺陷（一期接受，二期解决）**：

- **跨集群 trace 采样不一致**：微服务调用跨集群时，一条 trace 的 span 散落多个客户集群，各集群 gateway 独立决策会导致瀑布图残缺。一期在 UI 上对跨集群 trace 标注「部分 span 可能因跨集群采样不一致缺失」；**二期**在平台摄入层按 `trace_id` 哈希路由做全局 tail sampling，集群 gateway 降级为纯转发。
- **计量口径变化（v1.2 必须同步处理）**：采样丢弃发生在客户集群内，平台侧无法直接计量被丢弃的 span。要求 cluster-gateway 上报自身的 `otelcol_processor_tail_sampling_*` 指标到平台，作为 §9.3「被丢弃 span 计入账单折扣项」的数据源。这条不做，采样率与账单的对账就会有缺口。

## 7. 详细设计 — 存储层

> **版本基线：Apache Doris 4.0.8，存算分离（Compute-Storage Decoupled）模式。** 下文标注 `[4.0 特性]` 的能力需在 M1 PoC 对 4.0.8 实测确认后定稿。

### 7.1 Doris：Logs 表设计

```sql
CREATE TABLE logs (
    ts              DATETIME(3)      NOT NULL COMMENT '事件时间',
    tenant_id       VARCHAR(64)      NOT NULL COMMENT '租户',
    cluster_id      VARCHAR(64)      NOT NULL COMMENT 'K8s 集群（§6.5）',
    service         VARCHAR(128)     NULL,
    severity        VARCHAR(16)      NULL,
    trace_id        VARCHAR(64)      NULL COMMENT '关联键',
    span_id         VARCHAR(16)      NULL,
    body            STRING           NULL COMMENT '原始日志体',

    -- ★ v1.3：Schema Template 锁定 OTel 语义约定路径。
    --   官方规定 typed path 一定参与子列列式提取，且默认不计入
    --   variant_max_subcolumns_count 预算（variant_enable_typed_paths_to_sparse
```

**★ v1.2 阻塞级修正：`dynamic_partition.start = -3650`**

v1.1 写的是 `-7`，Doris 会在分区超过 7 天时**自动 DROP，不等待任何外部条件**。而 §7.4 新增的归档门禁要求「EXPORT 完成、行数与校验和比对通过、Iceberg 登记成功之后才允许删除分区」。两者同时存在时，动态分区调度会先把分区删掉——**这正是 v1.1 想要防住的数据丢失窗口，在配置层面却没有落实**。

修正方案：

1. `dynamic_partition.start` 设为 `-3650`（十年），**只保留自动建分区能力，关闭自动回收**；
2. `DROP PARTITION` 交由归档调度器在校验通过后显式执行（§7.4）；
3. 新增自监控 SLI **「已过期但未归档的分区数」**（§11），阈值 > 2 告警——归档管线卡住时分区会无限堆积，必须有人知道，但**绝不允许配置自动 DROP 兜底**，因为删除不可逆。

**其他设计要点**：

- **DUPLICATE KEY 而非主键模型**：日志只写不更新，DUPLICATE 模型写入开销最低；幂等去重交给 Stream Load 的 label 机制（§6.4）+ 微量重复容忍。
- **`tenant_id` 作为 DUPLICATE KEY 前缀**：tablet 内数据按 `(tenant_id, ts)` 排序，租户过滤可借助前缀稀疏索引与 zone map 裁剪——这补偿了 RANDOM 分桶没有分桶裁剪的损失。
- **分桶策略 RANDOM**：此类负载的过滤性由时间分区裁剪 + 倒排索引承担，分桶裁剪收益边际；而 `HASH(tenant_id)` 会让大租户永久落到同一批 bucket，数据倾斜不可控。RANDOM 保证写入绝对均衡，**但必须配套 `load_to_single_tablet=true`**（§6.4）。
- **倒排索引选择性建设（v1.3 改为路径级）**：body 必建；高频过滤字段（service/trace_id）必建；attributes **不再对整个 VARIANT 建索引**，改为对 Schema Template 声明的关键路径逐个建路径级索引（`field_pattern`）。对"任意字段关键字搜"的兜底能力由 body 全文索引 + DOC mode 的整条文档扫描承担，代价是长尾字段的精确过滤会慢一档——这是用确定的索引体积换不确定的长尾查询，在 SaaS 成本模型下是对的取舍（详见 §7.1.1）。

#### 7.1.1 VARIANT 建模基线：Schema Template + DOC 编码 + V3（v1.3 重写）

本节是 v1.3 的核心。v1.2 把「子列数触顶」列为首要风险，经对照 Apache Doris 官方 4.x VARIANT 文档与可观测性实践后，该判断需要修正，同时暴露出三类 v1.2 未处理的问题。

##### （1）修正：子列触顶是渐进降级，不是天花板

官方机制：系统按「非空比例 / 稀疏度」对路径排序，**高频（不稀疏）路径优先参与子列列式提取并存为独立子列，其余低频路径合并进共享结构**；系统会优先让非空比例高、访问频率高的路径留在子列化中。也就是说超限后的行为是**自动 Top-N 取舍**，而非整列退化。

这个机制在本平台是有利的：全部租户的热点路径高度同构（都是 `http.*` / `db.*` / `rpc.*` / `k8s.*` 这些 OTel 语义约定字段），Top-2048 会自然被这些共享字段占据，各租户的私有字段本就属于该进共享结构的长尾。所以 v1.2「1000 租户 × 50 字段 = 5 万子路径」的算术没错，但推不出"查询性能崩塌"的结论。

其余官方硬约束（作为设计边界记录）：`variant_max_subcolumns_count` 默认 **2048**，官方明确不建议激进调大，实践上限 10000；接近 10000 时单机需 ≥128G 内存、≥32C，此时应优先转 DOC mode。JSON key 长度 ≤ 255（loader 侧校验，§6.4.2）。VARIANT 不能作主键或排序键、不能嵌套进 ARRAY/STRUCT。**同一张表内所有 VARIANT 列的 `variant_max_subcolumns_count` 必须一致**（要么全 0、要么全 > 0），否则建表或 Schema Change 报错。

##### （2）真正的首要风险：跨租户类型冲突会静默摧毁索引

官方两条规则叠加起来在多租户共享表下很危险：

- 「当同一路径出现不兼容类型（如同一字段既出现整数又出现字符串）时，将提升为 JSONB 类型以避免信息丢失」；
- 「类型变更导致索引丢失：子列类型发生不兼容变更（如 INT→JSONB）会丢失索引」。

后果：租户 A 的埋点写 `http.status_code: 200`，租户 B 写 `"200"`，该路径被提升为 JSONB，**索引丢失，且影响该 tablet 内的所有租户**。而 RANDOM 分桶意味着每个 tablet 都包含全部租户的数据（这是 §7.1 选 RANDOM 的代价的另一面），因此**一个客户的埋点质量问题会静默地拖垮所有客户在该字段上的查询性能**。没有报错，没有告警，官方 FAQ 里「为什么我的查询/索引没有生效」列的第一条正是这个。

这比子列数触顶严重得多：触顶是渐进、可测量的，类型冲突是突发、静默的。**故 §14 P2 的优先级重排，此项置首位。**

三道防线：

1. **Schema Template 锁类型（主）**：在建表时为 OTel 语义约定路径声明强类型（§7.1 DDL）。官方规定 typed path **一定参与子列列式提取，且默认不计入 `variant_max_subcolumns_count` 预算**（`variant_enable_typed_paths_to_sparse` 默认 false）——既锁死类型，又不挤占租户的动态子列额度。这比 v1.2 提出的"字段数配额"更根本：配额是限制租户，Schema Template 是把平台字段从竞争中直接摘出来；
2. **`otlp-loader` 侧类型强制**：typed path 上的值若类型不符，按声明类型转换；无法转换时旁路到 `<path>_raw` 影子路径并计一次类型冲突事件，**绝不让它污染主路径**（§6.4.2）；
3. **监控**：类型冲突事件数为零容忍指标（§4.1 / §11），任一 typed path 出现即排查。

per-tenant attributes 字段数配额（默认 200 个不同 key）与大租户独立库表（§9.4，触发条件扩展为「数据量 **或** attributes 基数」）作为第二、第三道防线保留。

##### （3）两张表统一启用 DOC 编码模式

官方 VARIANT 选型矩阵把负载分为四类：A 事件日志/审计日志（默认）、B 宽而热点少的遥测/画像（稀疏列）、**C 模型输出 / Trace / 归档，写入优先或整条返回（DOC mode）**、D 关键路径需稳定类型（Schema Template，可与 A/B 组合）。本平台取 **C + D**。

**关键更正（v1.2 的误判）**：DOC mode **不牺牲子字段过滤**。官方 DOC 编码机制第一条原文为「子路径**仍可**执行子列列式提取用于按路径查询，同时会**额外**保存一份原始 JSON 作为存储字段」。稀疏列与 DOC 编码互斥的是这两种"宽列应对机制"本身，不是子列化能力。

唯一可能的过滤退化来自 `variant_doc_materialization_min_rows`——小批量写入暂不子列化、留到 compaction 再做。**该参数对本设计不构成风险**：`otlp-loader` 按 64 MB 攒批（§6.4.2），日志约 12.8 万行、span 约 6.4 万行，均远超该阈值（示例值 10000），子列化在写入时即完成，不存在"最新数据只能扫原始 JSON"的窗口。

选择 DOC mode 的收益（官方数据）：

- compaction 内存下降约 **2/3**；稀疏宽列导入场景下导入性能提升约 **5~10 倍**——直接缓解 §6.4.2 的 `-235 too many tablet versions` 风险；
- `SELECT variant_col` 整条文档读取效率获得**数量级**提升；
- 超宽列场景下比即时子列化更稳定，尤其当子列规模接近万列时。

两张表都选 DOC mode 的依据略有不同：

- **spans 表**：trace 瀑布是「按 `trace_id` 取出该 trace 的全部 span 并完整返回 attributes」，整条文档读就是主查询路径，与官方 C 类完全吻合；
- **logs 表**：主查询是"关键字检索 + 字段过滤，返回一页约 100 行"，整条读只发生在用户展开单条时。按官方矩阵本可走 B 类（稀疏列），但选 DOC mode 有两个额外理由：一是它原生支撑 §17.4 的"展开单条日志看完整 attributes JSON 树"，**否则需要额外存一列原始 JSON 的 STRING**（官方在「限制」一节直接给出该变通建议），DOC mode 省掉这份冗余；二是两张表配置统一，降低运维与调参的认知负担。代价是放弃稀疏列分片，以及额外存一份原始 JSON。

**代价量化（已计入 §4）**：DOC 编码额外存原始 JSON，估计 logs 日增 +20%（190 → 230 GB/天）、traces +30%（13 → 17 GB/天），合计日增 215 → 260 GB/天，热缓存需求 2.4 → 2.9 TB。**该比例是估算，M1 必须实测校准（§14 P11）**——原始 JSON 经 zstd 后的膨胀幅度取决于 attributes 的重复度，实测值可能显著低于估计。

分片参数：`variant_doc_hash_shard_count` 默认 64，官方估算口径为「JSON key 总个数 / 128」。按 5 万子路径估算 → logs 取 **384**，resource 列基数低取 64，spans 的 `span_attributes` 取 128。这些值需随 M1 实测的真实路径数调整。

##### （4）`storage_format = V3`（v1.2 遗漏的必设项）

官方在「限制」一节明确：对于会产生大量独立子列的宽表场景（例如超过 2000 列），**强烈建议开启 V3 存储格式**，作用是把列元数据与 Segment Footer 解耦，加快文件打开速度并降低内存占用；官方 VARIANT 配置指南亦称"新的 VARIANT 表优先使用 V3，没有它宽 JSON 场景下文件打开慢、内存开销高"。

注意 `storage_format` 与本设计已有的 `inverted_index_storage_format` 是**两个不同的属性**，前者管列元数据布局、后者管索引存储格式，两者都要显式设置。

##### （5）倒排索引改为路径级（`field_pattern`）

v1.2 写的 `INDEX idx_attrs (log_attributes) USING INVERTED` 是对**整个 VARIANT 列**建索引，会为其所有子列建索引，这本身就是索引膨胀的来源；官方 FAQ 也提示不要"误以为给 VARIANT 整体建的索引可用于子列"。

3.1.x / 4.0 起支持路径级索引：`PROPERTIES("field_pattern" = "<子路径>")` 只对指定路径建索引，支持通配批量（如 `'pattern_*'`），且**同一路径可并存分词与不分词两套索引**，`MATCH` 与 `=` 各走各的。**前提是路径必须在 Schema Template 中声明类型**，因此与（2）是同一套机制的两面。

这取代了 v1.2「监控索引膨胀率，超阈值租户降级为仅 body 索引」的事后补救方案——从一开始就不产生膨胀，优于事后降级。

##### （6）查询侧纪律

官方要求：未启用 DOC mode 时读取整个 VARIANT 列会扫描所有子字段，一般不建议直接 `SELECT variant_col`，应使用 `SELECT v['path']` 路径投影；并避免大范围 `SELECT *`。

本设计虽已启用 DOC mode（整条读被优化），但列表页返回约 100 行，整条读 100 份 attributes 仍显著贵于只投影所需路径。**查询网关的 SQL 生成器需硬性约束**（§8.1）：列表页只允许路径投影，整条文档读仅在单条展开时发起。

##### （7）BE 侧参数（官方给出）

`max_cumu_compaction_threads ≥ 8`、`vertical_compaction_num_columns_per_group = 500`（提升纵向合并效率，代价是内存占用上升）、`segment_cache_memory_percentage = 20`（提升元数据缓存命中）。写入侧适度增大客户端 batch（本设计 64 MB 已足够）。

##### （8）监控信号（官方给出的三类症状，已接入 §4.1 与 §11）

| 症状 | 含义 | 动作 |
|------|------|------|
| Compaction Score 持续上升 | `variant_max_subcolumns_count` 过高或导入速率过快 | 降导入压力 / 复核子列上限 |
| 某字段查询性能突然退化，平台侧无配置变更 | schema 漂移——热点路径被挤出子列化 | 补入 Schema Template 锁定 |
| 同一路径频繁类型冲突 | 该路径必须锁类型，否则 JSONB 提升 + 索引失效 | 加入 Schema Template + loader 强制转换 |

**索引删减说明（v1.2）**：v1.1 建了 8 个倒排索引，其中 `span_id` 与 `duration` 是每行唯一或近似唯一的超高基数列，倒排索引的 term dictionary 体积接近原始数据本体，而查询收益为零（span_id）或为负（duration）。删掉这两个后，spans 表的索引占比预期从接近 100% 降到 40% 量级，直接改善 §4 的 BE 缓存容量需求。`trace_id` 同样是超高基数列但必须保留——它是 trace 点查与 log↔trace 关联的唯一路径，其膨胀率纳入 §14 P2 实测。

### 7.3 派生数据：三级物化体系（关联/血缘加速）

**决策：精细物化放热路径（Doris 异步物化视图）；冷数据不单独物化，仅在归档写 Iceberg 的同趟扫描中顺带产出粗粒度 rollup。** 理由：排障关联查询 95%+ 落在最近 24~72h，物化视图把高频页面从"扫原始数据"变"点小表"（聚合体积仅原始数据 1%~5%）；冷数据查询低频且延迟容忍，为其常驻预付计算不划算。

| 级 | 位置 | 内容 | 新鲜度/粒度 |
|----|------|------|------------|
| L1 热路径 | Doris 异步 MV + 调度任务 | `service_metrics_1m`（RED 分钟级）；`trace_summary`（trace_id → 入口服务/总耗时/错误标记/涉及服务集合）；`entity_topo` 拓扑边表（§7.6）；error 日志 digest | ~1 分钟 |
| L2 归档时刻 | 写 Iceberg 管道 | 小时/天粒度服务级 rollup，随归档同趟扫描产出（边际成本≈0） | 小时/天 |
| L3 冷数据本体 | Iceberg 归档层 | 不预建任何物化，临时取证走 Doris cold 计算组即席查询（§8.4） | — |

**工程要点**：

- L1 物化刷新跑独立 Doris 计算组，与摄入、即席查询三方隔离；刷新 lag 纳入 §11 自监控 SLI；
- 告警依赖的 RED 指标（§8.3，SLO < 2min）是 L1 中对新鲜度最敏感的一路——若 M1 PoC 证明异步 MV lag 不稳定，仅将此路升级为 loader 侧预聚合，其余维持 MV（即 §14 P6 的试验目标）；
- `trace_summary` 同时服务 AI 层：`get_trace` 工具先查摘要再按需拉 span 明细，降低 AI 上下文的 token 消耗。

> **v1.2 删除项：「Metrics 长期降采样写回 Doris」。** v1.1 让 15~180 天的 5m/1h 降采样数据落 Doris，动机是规避 VM 企业版的 downsampling 特性。但这条制造了一个伪问题——§14 P5「Grafana 长期趋势查询走 SQL 翻译层还是控制台」正是它的产物：用户在 Grafana 上看 30 天趋势会查不到数据，而为此自研 PromQL-over-SQL 兼容层完全不划算。
>
> 算一下就清楚：指标 180 天双副本总量约 **3.6 TB**，摊到 4 个 vmstorage 是每节点 0.9 TB，在日志动辄几十 TB 的盘子里是零头。**直接把 VM retention 从 15 天开到 180 天**，成本可以忽略，PromQL 与 Grafana 全程可用。确需降分辨率时用 **vmalert recording rules** 产出低频 series 写回 VM（开源版即可），而不是换一个查不了 PromQL 的库。§14 P5 随之关闭。

### 7.4 存储模式与冷热分层（存算分离）

**采用 Doris 4.0.8 存算分离模式**，不走"存算一体 + cooldown 搬迁"。**一期即采用而非到 10 TB 再切换**的理由见 §4 关键推论——终点规模在 10 TB/天，若先走存算一体，迁移窗口正好落在业务量最大的时刻。

| 层 | 实现 | 留存 | 查询能力 | 说明 |
|----|------|------|----------|------|
| 热 | S3 主存储 + BE 本地 NVMe 缓存 | 7 天 | 全功能，p95 < 3s | 缓存命中率保障热路径性能，是一级 SLI |
| 温 | S3 主存储（缓存逐出） | 8~15 天 | 全功能，p95 < 15s（限并发） | 查询回源 S3，延迟高一个量级 |
| 冷（归档） | Iceberg（Parquet + zstd）on S3，由 Doris cold 计算组查询 | 180 天 | 检索可用（秒级~十秒级），标注"归档查询" | 见 §8.4 |

**归档与分区删除流程（★ v1.2 阻塞级修正的落地）**：

```
归档调度器（控制面组件，每日运行）：
  1. 选出 Doris 中超过热窗口（15 天）且未归档的分区
  2. 写入 Iceberg：INSERT INTO iceberg_catalog.archive.logs
                   SELECT * FROM logs PARTITION (pYYYYMMDD)
     （[4.0 特性] Doris 写 Iceberg 的成熟度见 §14 P7；
       备选路径：EXPORT 为 Parquet + 外部工具登记 catalog）
  3. ★ 校验门禁（三项全过才继续，任一失败则保留分区并告警）：
       a. 行数比对：Doris 分区行数 == Iceberg 对应分区行数
       b. 校验和比对：抽样列的 checksum 一致
       c. Iceberg catalog snapshot 登记成功且可被 cold 计算组读到
  4. 校验通过 → 显式 ALTER TABLE logs DROP PARTITION pYYYYMMDD
  5. 校验失败 → 保留分区 + 告警 + 计入「归档校验失败率」SLI（§3.2，阈值 0.1%）
```

- **删除不可逆，必须先验后删。** 动态分区的自动回收已在 §7.1 关闭，本流程是分区删除的**唯一**路径；
- **「已过期但未归档的分区数」是必须监控的对偶指标**——门禁防住了误删，但会让归档管线卡住时分区无限堆积占满 S3。阈值 > 2 告警（§11）；
- 温冷/归档查询走独立计算组与限流队列，防止长区间全扫拖垮热路径（§9.1）；
- 留存策略 per-tenant 可配（商业版差异化卖点），由控制面下发。

**★ v1.3 — BE 侧参数（官方针对 VARIANT 宽列场景给出）**：

| 参数 | 取值 | 作用 | 代价 |
|------|------|------|------|
| `max_cumu_compaction_threads` | ≥ 8 | VARIANT 宽列的 compaction 开销远高于普通列，线程不足会直接体现为 Compaction Score 攀升与 `-235` 导入失败 | CPU 占用上升 |
| `vertical_compaction_num_columns_per_group` | 500 | 提升纵向合并效率 | **内存占用上升**，需与 BE 内存水位一起观察 |
| `segment_cache_memory_percentage` | 20 | 提升 segment 元数据缓存命中，配合 `storage_format=V3` 缓解宽列的文件打开开销 | 挤占查询内存 |

这三项与 §7.1.1（3）选择的 DOC mode 是互补关系：DOC mode 把 compaction 内存降了约 2/3，上面的线程与分组参数则把腾出的空间转成吞吐。**M1 需在真实写入压力下联调这组参数**，单独调任何一项都可能把瓶颈推到另一处。

### 7.5 VictoriaMetrics 集群

- **拓扑**：vmauth（租户路由，accountID = tenant_id）→ vminsert（无状态，多副本）→ vmstorage（分片 + 副本因子 2）；vmselect 独立部署多副本；vmalert 承担告警规则与 recording rules。
- **留存：本地 180 天高分辨率（v1.2 由 15 天上调）**。依据见 §7.3 的删除说明：180 天双副本总量约 3.6 TB，每节点 0.9 TB，成本可忽略。这一变更同时消除了 v1.1 的 §14 P5。
- **降分辨率视图**：用 vmalert recording rules 对关键指标产出 5m/1h 分辨率的新 series 写回 VM（开源版能力），供长期趋势看板使用。PromQL 与 Grafana 全程可用，无需任何翻译层。
- **容量**：500 万活跃 series × 2 副本 = 1000 万 series 副本 / 4 vmstorage ≈ 每节点 250 万 series；内存按官方每百万 series ≈ 2GB 规划并预留 1.5 倍 churn 缓冲（≈7.5GB → 16GB 规格）。扩缩容路径：series 增长 → 成对加分片（节点数 = ⌈series × 2 / 500 万⌉），10 TB 时为 14 节点（§4.2）。
- **租户隔离粒度**：vmauth 提供读写路由与软隔离；噪声邻居的最终防线在摄入侧 metrics-ingest 的基数整形（§6.4.3），而不是查询侧。
- **明确不依赖的能力**：exemplar 存储与查询（见 §7.7）、企业版 downsampling（用 recording rules 替代）。

### 7.6 Zmodel：统一语义层

**定位**：把 §7.3 的三级物化体系从"查询加速层"升级为**"实体-关系-数据"统一语义层**——物化视图是 Zmodel 的物理实现，Zmodel 是其语义抽象。目标是为 §16 AI 层提供可推理上下文（上下游、爆炸半径、黄金指标），为 RCA 打底；同时兑现 §8.2 信号关联与 §17 服务拓扑的统一数据源。

**核心抽象**：

| Zmodel 概念 | 一期范围 |
|-------------|----------|
| EntitySet / Entity | 白名单类型：`k8s.cluster` / `k8s.namespace` / `service` / `service_instance` / `host` / `database` / `mq`；二期开放自定义类型 |
| Link（实体边） | `calls`（service→service，span 派生）、`contains`（cluster→ns→service）、`runs_on`（instance→host）、`depends_on`（service→db/mq，client span 派生） |
| DataLink（数据挂载） | 实体 ↔ logs / spans / `service_metrics_1m` 的挂载点 = `tenant_id + entity_key + 时间窗`，同库 JOIN 兑现 |
| Schema 注册 | `entity_registry` 表 + 控制面实体类型注册表（字段、约束、TTL） |

**实体粒度纪律**：实体只建到 **service_instance 级**；pod / container **不进实体表**（churn 太高，降级为 instance 的属性）。单实体类型总量控制万级，超限触发治理告警——实体表是语义层不是明细层，爆炸即失效。

**物理实现（复用 Doris，一期不引入图数据库）**：

- `entity_registry` 表：`entity_id, tenant_id, entity_type, name, attributes VARIANT, first_seen, last_seen, status`；首见 upsert，`last_seen` 滚动更新，30 天未见标记 stale；
- `entity_topo` 表：`src_entity, dst_entity, link_type, first_seen, last_seen` + 5 分钟聚合 RED（调用量/错误率/p99）——**边上自带黄金指标**，RCA 下钻零额外查询；
- **图遍历 = 应用层迭代 BFS**：每跳一次 Doris 点查（倒排索引），深度 ≤3。**（v1.2 补强）必须加剪枝**：单跳 fanout 上限 20（按调用量 top-N 保留），全遍历访问节点上限 200，超限时截断并在返回中标注。高扇出服务（如网关，下游可达数百）不剪枝的话深度 3 会退化成十万量级的点查风暴；
- **确定性原则**：边只从 span、k8s 元数据等**事实数据**派生；AI 推断的关系打 `INFERRED` 标签分开存储（二期）——Agent 做 RCA 时必须能无条件信任每一跳。

**构建管线**：span → caller/callee 5 分钟聚合 → `entity_topo` upsert；摄入侧 k8s 富化 labels → `contains` / `runs_on`；实体注册与边发现均走 Doris 调度任务，刷新 lag 纳入 §11 自监控。

**（v1.2 排期调整）`entity_registry` 与 `entity_topo` 的构建管线提前到 M3**——它是 §17.3「应用性能 / 服务拓扑」页面的数据源，属于 M3 的产品需求，不应与 AI 层绑定在 M4。M4 只保留 Zmodel 的语义工具层（下条）。

**对 Agent 的接口**：一期**不自研查询语言**，在 §16 工具层提供语义工具：`get_entity` / `get_neighbors(entity, direction, depth≤3)` / `get_golden_metrics(entity, timerange)` / `get_entity_logs` / `get_entity_traces` / `get_blast_radius(entity)`——压低幻觉率与 token 消耗。二期评估 pipeline 式统一查询语言。

**RCA 动线（M4 随 AI 层 MVP 兑现）**：告警事件 → 挂载实体 → 取告警实体 + 1~2 跳邻居的**最小连接子图**（受上述剪枝约束）→ 各实体黄金指标时间序对齐 → 叠加变更事件（二期）→ 携带证据链的根因报告。

### 7.7 metric_exemplars 表（v1.2 新增，替代 VM exemplar）

**背景**：v1.1 §8.2 写「VM 原生支持 exemplar 存储与查询」。据现有资料，VictoriaMetrics 长期未实现 Prometheus exemplars，remote-write 中的 exemplar 字段会被丢弃，官方立场是建议改用 trace_id label 关联。**若属实，G4 这条核心差异化目标在 v1.1 架构上根本没有落点**——这不是体验降级，是功能不存在。**M1 第一周必须用一条带 exemplar 的 remote-write 实测确认**（§14 P10），不要等到 M3 做关联 UI 时才发现。

**方案**：由 metrics-ingest 在写入路径上抽取 exemplar，单独落 Doris 小表。这比依赖 VM 原生能力更强——可 SQL 过滤、可按服务聚合、可与 spans 表直接 JOIN。

```sql
CREATE TABLE metric_exemplars (
    ts           DATETIME(3)   NOT NULL,
    tenant_id    VARCHAR(64)   NOT NULL,
    cluster_id   VARCHAR(64)   NOT NULL,
    service      VARCHAR(128)  NULL,
    metric_name  VARCHAR(256)  NOT NULL,
    labels       VARIANT       NULL COMMENT '产生该 exemplar 的 series labels',
    value        DOUBLE        NULL,
    trace_id     VARCHAR(64)   NOT NULL,
    span_id      VARCHAR(16)   NULL,
    span_status  VARCHAR(16)   NULL COMMENT 'metrics-ingest 无法填充时留空，由 MV 回填',
    INDEX idx_metric (metric_name) USING INVERTED,
    INDEX idx_trace  (trace_id)    USING INVERTED,
    INDEX idx_svc    (service)     USING INVERTED
)
ENGINE=OLAP
DUPLICATE KEY(tenant_id, ts)
PARTITION BY RANGE(ts) ()
DISTRIBUTED BY RANDOM BUCKETS 4
PROPERTIES (
    "compression" = "zstd",
    "compaction_policy" = "time_series",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-3650",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "4"
);
```

**量级控制（关键）**：不加节制地全量落 exemplar 会产生每秒数千条记录。metrics-ingest 侧执行**保留策略：每 `(tenant_id, metric_name, service)` 每分钟最多保留 5 条**，优先级为「关联 span 为 ERROR」>「value 最大」>「随机」。按 1000 个活跃组合估算约 **700 万条/天，压缩后约 250 MB/天**，在 §4 的 Doris 日增里已计入"派生/元数据 12 GB/天"。这个策略足以支撑"从图上某个异常点跳到一条有代表性的 trace"，而这正是 exemplar 的全部用途。

**留存**：30 天（短于日志的热+温窗口，exemplar 的价值高度集中在近期排障）。

## 8. 详细设计 — 查询层与信号关联

### 8.1 统一查询网关

无状态服务，核心职责：

1. **认证鉴权**：SSO/AKSK → 解析租户 → 强制注入 `tenant_id` 过滤（SQL 改写 + vmauth 路由），**用户永远不直接接触底层引擎凭证**；
2. **协议适配**：
   - PromQL / Grafana datasource API → 透传 vmselect；
   - 日志/Trace 查询（自研 DSL 或直出 SQL 子集）→ SQL 生成器 → Doris FE（MySQL 协议）；
   - Trace 点查 → `SELECT ... FROM spans WHERE trace_id = ?` + 客户端瀑布渲染；
   - **★ v1.3 — SQL 生成器的 VARIANT 投影规则（硬性）**：见下方专节；
3. **查询治理**：每租户并发配额 + 排队；扫描行数/时间范围硬上限（超出引导用户缩小窗口或走异步导出）；
4. **审计与计量**：每条查询记录（租户、扫描量、耗时），供计费与容量分析（§9.3、§9.5）；
5. **SQL 解析与改写**：内嵌 `datafusion-sql` 作为解析库（租户谓词注入、危险查询拦截），替代手写解析器。**注意：这是把 DataFusion 当库用，与 §8.4 放弃自研 DataFusion 集群不矛盾。**

#### 8.1.1 VARIANT 投影规则（v1.3 新增，对应 §7.1.1 第 6 点）

官方明确不建议直接 `SELECT variant_col`：未启用 DOC mode 时这会扫描该列所有子字段。本设计已启用 DOC mode，整条文档读被优化到数量级级别，但**列表页一次返回约 100 行，整条读 100 份 attributes 仍远贵于只投影用户可见的几个路径**。因此规则不是"DOC mode 解决了就不用管"，而是：

| 场景 | 允许的投影 | 理由 |
|------|-----------|------|
| 日志列表页 / Trace 列表页（返回 ~100 行） | **只允许** `v['path']` 路径投影，且路径集合来自前端当前显示的列 | 逐行整条读是列表页延迟的主要来源 |
| 单条日志展开 / Trace 瀑布单 span 详情（返回 1 行） | 允许 `SELECT log_attributes`（整条） | DOC mode 的目标场景，正是为此启用 |
| Trace 瀑布（按 `trace_id` 取整条链路，通常几十到几百 span） | 允许整条读 | 瀑布需要完整 attributes；这是 §7.1.1 选 DOC mode 的主要依据 |
| 聚合 / GROUP BY | 只允许路径投影 | 同理，且应尽量落在已建路径级索引的路径上 |

实现：SQL 生成器在构造 `SELECT` 列表时，若检测到裸的 VARIANT 列名且预估返回行数 > 1，**改写为路径投影**；无法确定路径集合时拒绝并返回明确错误，而不是放行。同时禁止 `SELECT *`（官方亦建议避免大范围 `SELECT *`）。

这条规则的存在本身也说明一件事：**DOC mode 不是"整条读变免费"，只是把它从不可接受变为可接受**。

### 8.2 三信号关联（产品差异化的核心，v1.2 改写实现路径）

```
                 【主动线：指标异常 → Trace → Logs】
指标看板/告警异常点
   │ ① 查 metric_exemplars（§7.7）：同 metric + service + 时间窗，取代表性 trace_id
   │ ② 若无 exemplar 命中 → 兜底动线（见下）
   ▼
Trace 瀑布（spans 表，trace_id 点查）
   │ 点击某 span → 携带 (trace_id, span_id, ts±30s, service)
   ▼
相关日志（logs 表：WHERE trace_id=? OR (span_id=?) OR (service=? AND ts BETWEEN ...)）
   │ 反向：日志中发现 trace_id → 一键跳 trace
   ▼
关联指标（service + 时间窗 → service_metrics_1m 或 VM PromQL）
```

**兜底动线（v1.2 新增，不依赖 exemplar）**：指标异常点 →（`service` + 时间窗）→ 查 spans 表取该窗口内的慢 trace 与错误 trace 列表 → 用户从列表进入瀑布。

这条动线的价值不止于兜底：

1. 它完全不依赖 exemplar 链路，因此 §14 P10 的验证结果不会阻塞 G4 交付；
2. 由于 §6.5.4 的 tail sampling 策略**全量保留错误 trace 与慢 trace**，这个列表在排障场景下几乎总是非空且高相关；
3. 体验上给出的是"候选集"而非"单条"，在很多场景比 exemplar 的单点跳转更有用——Datadog 也采用类似交互。

**tail sampling 对 exemplar 命中率的正向作用**：exemplar 挂载的通常是异常指标点，其指向的 trace 大概率正是被 tail sampling 策略保留的错误/慢 trace，因此有效命中率预期 ≥ 70%（§3.2 SLI）。对比之下，v1.1 的 head sampling 是纯随机 10%，命中率天然只有 10%——v1.1 §6.2 已识别这个问题但只给了"UI 提示跳转落空"的兜底，那不是解决方案。

### 8.3 告警引擎

| 告警类型 | 执行路径 | 延迟 |
|----------|----------|------|
| Metrics 阈值/异常 | VMAlert（规则存控制面，渲染后下发） | < 1 min |
| 日志关键字/模式 | 控制面调度器 → Doris 轮询 SQL（如 `count() where body match 'ERROR' group by 1m`） | < 2 min |
| Trace 服务质量（错误率/延迟） | 查 §7.3 的 `service_metrics_1m` 物化视图，不扫原始 span | < 2 min |
| 缺席告警（数据断流） | 摄入侧计数器 + VMAlert `absent()` | < 3 min |

- 告警状态机（触发/恢复/静默/抑制）复用 Alertmanager 语义，通知渠道自研适配；
- **告警查询走独立 Doris 计算组**，与用户即席查询物理隔离，保证告警延迟 SLO 不被分析查询挤占。

### 8.4 冷层查询：Doris Iceberg Catalog（v1.2 重写）

**决策变更**：v1.1 计划为 180 天冷查询自建一套 Apache DataFusion executor 池。v1.2 改为 **用 Doris 4.0.8 的 Iceberg Catalog + 一个独立的冷查询计算组**，零新增技术栈。

**为什么改**：

1. v1.1 方案要新建的不只是 DataFusion executor，还有 Iceberg catalog 对接、租户谓词注入、限流队列、弹性伸缩——这些在 Doris 侧已经存在且经过热路径验证，重做一遍是纯粹的重复投入；
2. Doris 的 multi-catalog 能直接查 Iceberg 外表，是其相对成熟的能力；存算分离模式下再开一个 `cold` 计算组做物理隔离，天然满足"冷查询不拖垮热路径"；
3. **开放性卖点完全不受影响**——它来自存储格式（Parquet/Iceberg，客户可用 DuckDB/Trino/Spark 自取，支持 BYO-bucket），不来自查询引擎。这一点在 v1.1 的论证里被混淆了。

**保留的 DataFusion 用法**：查询网关内嵌 `datafusion-sql` 作为 SQL 解析/改写**库**（§8.1）。把它当库用是合理的，当分布式查询系统自建则不是。

**明确不做的两件事**（v1.1 结论保留，理由依然成立）：

- **不用任何联邦引擎替换热路径**：日志检索依赖 Doris 倒排索引 MATCH 下推，联邦查询无法下推该谓词，拉数出来扫性能不可接受；PromQL 由 VM 承担；
- **不基于 DataFusion 自研数据库**：GreptimeDB/InfluxDB 的实践表明，DataFusion 只提供引擎积木，实时摄入、compaction、缓存、分布式执行均需以年计的自研投入。

**交付窗口说明**：归档从 M3 开始写入，冷查询计算组在 M3 末同步上线（因为不需要自研，不再需要推到 M4）。这消除了 v1.1 中「M3 写归档、M4 才能查」的窗口期。

## 9. 详细设计 — 多租户、配额、计量与数据治理

### 9.1 租户模型与资源隔离

```
Organization（客户）
  └── Project（环境：prod/staging）
        └── Token（摄入凭证，可吊销、可限速）
```

- **数据隔离分级**：
  - 中小租户：共享 Doris 大表 + `tenant_id` 谓词 + Row Policy；VM 侧 accountID 隔离；
  - 超大租户（Top 1% 数据量，或 attributes 基数触顶，§7.1.1）：独立 Doris 库表 + 独立计算组，双轨策略见 §9.4；
- **计算资源隔离（v1.2 升级）**：存算分离模式提供**计算组（compute group）**，是比 Workload Group 更彻底的隔离手段——不同计算组是不同的 BE 进程组，共享同一份 S3 数据但 CPU/内存/缓存完全物理隔离。一期划分四组：

  | 计算组 | 用途 | 规格 |
  |--------|------|------|
  | `hot` | 用户交互查询 + 摄入 | 4 × 16C64G + 3 × 500GB NVMe（多盘见 §4） |
  | `alert` | 告警调度 SQL + L1 物化刷新 | 2 × 8C32G（可与 hot 混部起步，量大后拆出） |
  | `cold` | Iceberg 归档查询（§8.4） | 按需弹性，0~2 节点 |
  | `dedicated-{tenant}` | 大租户专属（§9.4） | 按租户量级配置 |

  组内再用 Workload Group 做租户级 CPU/内存软限制。**这是"一期即上存算分离"的一项直接红利**：大租户隔离从"共享 BE + 软限制"升级为"独立 BE 进程组"，爆炸半径真正收敛。

### 9.2 配额体系（三道防线）

| 层 | 机制 | 超限行为 |
|----|------|----------|
| 摄入 | 网关令牌桶（bytes/s、EPS） | 429 + 客户端降采样信号 |
| 存储 | 租户写入计量 vs 合同配额 | 触发升配销售流程；硬超限强制上调采样率 |
| 查询 | 并发数 + 扫描行数上限 + 归档/回源查询独立队列 | 排队 / 拒绝并提示优化 |
| **Schema（v1.2 新增）** | per-tenant attributes 字段数配额（默认 200，§7.1.1） | 超出字段进 sparse 存储 + 治理事件推送 |

### 9.3 计量计费 Pipeline

摄入网关在 **Kafka ack 成功之后**为每批数据生成 **metering event**（tenant、signal、bytes、events、采样率、时间戳，**携带批次幂等键**，客户端重试不重复计费）→ 独立 topic `metering` → 聚合任务 → 用量表（Doris 同库小表）→ 计费系统。metrics 直连路径由 metrics-ingest 服务以同样方式计量。

计费维度：**摄入 GB（分信号定价）+ 存储 GB·月（分热/温/冷）+ 查询扫描量（超免费额度后）+ AI token（§16.2）**。

**口径统一表（v1.2 新增——v1.1 中三处丢弃口径分散在不同章节，容易对不上账）**：

| 事件 | 发生位置 | 是否计费 | 数据来源 |
|------|----------|----------|----------|
| 正常摄入 | 平台摄入网关 | 是 | metering event |
| 限流拒绝（429） | 平台摄入网关 | 否 | 网关计数器，用于容量分析 |
| tail sampling 丢弃 span | **客户集群 gateway** | 否，但计入**账单折扣项** | cluster-gateway 上报的 `otelcol_processor_tail_sampling_*`（§6.5.4） |
| 过载降级丢弃日志 | 平台 Collector | 否，计入**服务质量事件**（可能触发 SLA 赔付） | §10.2 降级动作日志 |
| 基数防护 drop label | metrics-ingest | 是（按整形后的 series 计） | 基数审计事件 |

### 9.4 大租户双轨策略

**大租户定义线（v1.2 按 1.5 TB 基线下调）**：日增 > 300 GB 或活跃 series > 200 万 **或 attributes 字段数持续触顶（§7.1.1）** → 建议独立；日增 > 1 TB → 强制独立。

**共同地基：租户分层注册表。** 控制面维护 `tenant_tier`（shared / dedicated）+ 路由元数据（目标库表、计算组、Kafka 分区键规则、vmauth accountID 段、查询并发配额），摄入网关、`otlp-loader`、metrics-ingest、查询网关统一读这张表做路由。**迁移因此退化为"搬数据 + 一次配置变更"**——两条轨道只是同一机制的两种触发方式。

**Track A：渐进型（小租户长成大租户）——在线迁移，零停机**

1. **监测**：基于 metering 的增长趋势告警——日增达大租户线 50% 时提示销售介入，80% 时启动迁移预案；
2. 建独立库表（独立分区/bucket 配置）与独立计算组；
3. **以日分区边界切流**：新一天的分区直接写新表（`otlp-loader` 路由配置变更，Kafka 回放兜底）；
4. 历史分区后台**限速**搬迁（分区级 `INSERT INTO SELECT`），限速避免挤占生产负载；
5. 追平后查询网关切读；过渡窗口内按时间范围双路由（新数据查新表、旧数据查旧表），对用户透明；
6. 旧数据清理，**保留 7 天回滚窗口**（路由配置一键回切）。

**Track B：原生大租户（接入即大）——直接独立供给**

1. **接入前定级**：销售/POC 阶段申报量级；接入向导提供"试跑一天"模式（全量 metering、只读额度），**用真实计量数据定级，不靠客户自报**；
2. **第一天落独立资源**：独立 Doris 库表（bucket 数按其量级配置）、独立计算组、Kafka 分区键含 bucket 后缀打散热点、vmauth 独立 accountID 段、独立查询并发配额；
3. **计费口径切换**：从纯用量计费叠加"专属资源占用计费"。

**降级方向**：大租户缩水**不回迁**共享表——回迁的迁移成本大于资源节省，仅在其专属计算组内缩容。

### 9.5 数据安全与合规（v1.2 新增章节）

v1.1 全文缺失本节，而对企业客户而言这些是过检项，缺一项就可能卡住合同。

**① 摄入侧 PII 脱敏**（对标 Datadog Sensitive Data Scanner）

- 在摄入网关执行（早于 Kafka，确保敏感数据不落盘）；
- 规则库：内置手机号、身份证、银行卡、邮箱、IP、JWT、常见密钥格式的正则；租户可自定义规则并选择动作（`redact` 掩码 / `hash` 保留可关联性 / `drop` 整条丢弃）；
- 规则命中数按租户暴露为指标，供合规审计；
- **性能约束**：正则扫描在 10.5 万 EPS 峰值下是实打实的 CPU 成本，M1 压测必须包含开启脱敏后的吞吐衰减实测，规则数上限按实测结果设配额。

**② 加密**

- 传输：全链路 TLS（客户集群 → 网关、网关 → 内部组件、Doris/VM 客户端）；
- 静态：S3 侧 SSE-KMS（Doris 主存储、Iceberg 归档、Kafka 分层存储若启用）；FoundationDB 备份文件同样加密；
- 凭证：租户 Token 存控制面时哈希存储，仅在创建时明文展示一次。

**③ 审计**

- **查询审计**（§8.1 已有）：谁、在什么时间、用什么条件、查了哪个租户的多少数据；
- **管理面操作审计（v1.2 补）**：租户/Token 的创建吊销、留存策略变更、配额调整、采样率下发、分区删除、大租户迁移——全部记录操作者、时间、变更前后值，独立存储且平台运维人员不可删除；
- 审计日志留存 365 天，可导出给客户。

**④ 数据删除与可携带**

- **退租删除**：合同终止后 N 天（默认 30）内彻底删除该租户的 Doris 数据、Iceberg 归档、VM series、Kafka 残留与备份副本，出具删除证明。实现方式：大租户走独立库表可直接 DROP；共享表租户需按分区执行 `DELETE WHERE tenant_id = ?` 并触发 compaction，**这在 DUPLICATE 模型上代价不低，M2 需实测单租户删除的耗时与资源占用**；
- **GDPR 单主体删除权**：从 DUPLICATE 模型的日志表中精确删除某个自然人的数据近乎不可行。**一期的诚实做法是不承诺**——在合同中声明可观测性数据为运维日志、采用短留存（180 天）与摄入侧脱敏（①）作为补偿性措施。若目标市场硬性要求，需在二期评估按 subject-key 分区或加密擦除（crypto-shredding）方案，这是一个独立的设计课题；
- **数据可携带**：归档层为开放 Iceberg 格式，支持 BYO-bucket 与客户自助导出（§8.4）。

**⑤ 数据驻留**：一期单 Region，在合同中明确数据存储地域；多 Region 驻留需求随 M5 跨 Region 能力一并评估。

## 10. 可靠性、降级与容灾

### 10.1 故障矩阵（v1.2 补入存算分离新增组件）

| 故障 | 影响 | 应对 |
|------|------|------|
| 摄入网关单点 | 无 | 无状态多副本 + LB |
| `otlp-loader` 单副本 | 无 | 无状态，consumer group rebalance，offset 在 Kafka |
| Kafka 单 broker | 无 | 3 副本，`min.insync.replicas=2` |
| Doris BE 节点 | 该 BE 缓存的数据需从 S3 重新加载，**查询延迟 spike 但数据不丢**（存算分离下数据在 S3，FE 会把 tablet 重新分配给其他 BE） | 4 台 BE（N+1），单台故障损失 25% 缓存与算力；写入由 loader 重试、查询由网关重试兜底；该窗口计入 99.9% 预算 |
| Doris FE 主 | 分钟级不可写新任务 | FE 三节点选举 |
| **Doris Meta Service 单副本** | 无 | 无状态，3 副本 + LB |
| **Doris Recycler** | S3 上过期 rowset 不被回收，存储成本缓慢上升 | 2 副本；停摆超过 24h 告警（非紧急故障，但不能长期无人管） |
| **FoundationDB 单节点** | 无（`double` 冗余） | 3 节点每 AZ 一台，自动恢复 |
| **FoundationDB 集群不可用 / 元数据损坏** | ★ **最高等级故障：整个 Doris 集群的数据不可读**（S3 上有数据但没有 rowset 元数据就无法定位） | ① `fdbbackup` 持续增量备份至独立 S3 bucket（与 Doris 数据 bucket 分离），RPO ≤ 5 分钟；② **每季度必须执行一次从备份恢复的演练**，演练结果作为 §11 的合规项；③ FDB 版本升级走灰度且必须先在演练环境验证。**这是 v1.1 完全缺失的单点，也是"一期即上存算分离"的主要风险成本** |
| VM vmstorage 节点 | 查询该分片降级 | 副本因子 2 接管；vminsert 自动 re-route |
| 查询网关 | 无 | 无状态多副本 |
| 控制面整体 | 新配置无法下发；**归档调度器停摆 → 分区堆积**（由「已过期未归档分区数」SLI 告警） | 数据面 fail-static 继续运行 |
| 客户集群 cluster-gateway 故障 | 该集群 trace 采样中断 | 2+ 副本；`file_storage` 持久队列缓冲；node-agent 的 loadbalancing exporter 自动重新路由（**注意：rebalance 期间同一 trace 可能落到不同副本，造成短时采样不一致，属可接受降级**） |
| 整 AZ | 摄入降级（容量减 1/3）；FDB 降级但可用 | 跨 AZ 部署 + 自动摘除 |

### 10.2 过载降级预案（按序执行）

1. 归档与缓存回源查询排队加深，保护热路径（本地缓存命中区）；
2. 非核心租户日志摄入限流收紧；
3. Trace 采样率全局下调（控制面一键下发到各集群 gateway 的 tail_sampling `probabilistic` 策略；**错误与慢 trace 的保留策略不下调**——它们是排障的最后依据）；
4. 低 severity（DEBUG/INFO）日志按比例丢弃（在平台 Collector 层，丢前记录丢弃计量，计入 §9.3 服务质量事件）；
5. 极端情况：只保 metrics + error 日志（"骨架模式"），事后从客户侧 agent 缓冲部分回补。

### 10.3 容灾

- 全部数据的主副本在 S3（存算分离），天然跨 AZ、可开跨 Region 复制；归档层同理；**但 FoundationDB 元数据必须与数据同等对待**（§10.1）；
- 一期不承诺跨 Region 容灾（最佳努力），RPO = Kafka 未消费窗口（分钟级）+ FDB 备份间隔（≤5 分钟），RTO = 新 Region 重建 Doris 集群、恢复 FDB 元数据、指向同一 S3 bucket + Kafka 回放追平（小时级）；
- 跨区复制、元数据备份自动化与容灾演练整体列入 M5。

## 12. 备选方案与权衡记录（Alternatives Considered）

| 方案 | 放弃原因 |
|------|----------|
| 全量统一进 Doris（含 metrics 原始数据） | 高基数时序写入放大与索引成本；PromQL 生态需自研翻译层，兼容性风险高（量化对比见 §1） |
| Victoria 全家桶（VM+VL+VT） | VictoriaTraces 未 GA；LogsQL/TraceQL 生态弱；三信号跨系统关联弱；分析型查询能力不足 |
| Elasticsearch/OpenSearch 存日志 | 同规模写入吞吐与压缩率劣势明显（Doris 写入约 5×、压缩 8:1 对 ES 1.5:1），成本否决 |
| ClickHouse 存 logs+traces | 能力上与 Doris 接近、生态同样成立；放弃点是 VARIANT 半结构化建模与倒排索引的工程成熟度需实测对比（**M1 PoC 的正式对比对象**），且团队 Doris 运维积累优先 |
| **Grafana Tempo + Mimir（v1.2 补）** | Tempo 的对象存储原生 + bloom 索引在**纯 trace 成本**上优于 Doris；否决理由是它把 trace 与 log 重新割裂到两个系统，`trace_id` 关联退回"两次查询 + 应用层拼接"，恰好放弃本设计最核心的红利（§8.2）。Mimir 相对 VM 无显著优势而运维更重 |
| **Quickwit（v1.2 补）** | 对象存储原生的日志/trace 检索引擎，设计思路与本文冷层高度重合；否决理由是它不提供 OLAP 分析能力（日志聚合分析、SQL 即席查询、物化视图全缺），且被 Datadog 收购后开源路线存在不确定性。**但其"索引直存对象存储"的思路值得在 §14 P2 结果不理想时重新评估** |
| 摄入直连 Doris 无 Kafka | 削峰/回放能力缺失，存储抖动直接传导为摄入丢失，可靠性否决 |
| Loki 存日志 | 检索能力弱（无真倒排索引）、大查询靠暴力扫，SaaS 多租户下查询成本不可控 |
| **Doris Routine Load 落库（v1.2 新增否决项）** | jsonpaths 无法展开嵌套 OTLP 数组，两条主链路都不成立；且攒批延迟 10~30s 无法承诺摄入 SLO。改为自研 `otlp-loader`（§6.4） |
| **自建 DataFusion 冷查询集群（v1.2 新增否决项）** | Doris 的 Iceberg Catalog 已覆盖该需求，自建等于重做租户隔离、限流、弹性伸缩；开放性卖点来自存储格式而非查询引擎（§8.4） |

## 15. 参考实现对标：DataBuff（AI-Native APM）

> 对象：github.com/databufflabs/databuff（AGPLv3，**仅作思路参考，禁止代码复用**——AGPL 对 SaaS 有传染性）。
> 形态：自托管单租户 APM，3 组件（Ingest + Doris + Web），OTLP/SkyWalking 双协议，Stream Load 直写 Doris（无 Kafka），49 张表全部 `replication_num=1`、`BUCKETS 3`、30 天动态分区留存。

### 15.1 对本设计的验证

- **OTLP → Doris 三信号统一存储在真实产品中可行**（其 metrics 也全量进 Doris），支持了 §1 的基线判断；
- **Stream Load 直写 Doris 的路径已被生产验证**——v1.2 §6.4 的 `otlp-loader` 采用同样的落库方式，区别在于前面加了 Kafka 削峰并做了 label 幂等；
- **反面教材**：其 metrics 全部落 AGGREGATE KEY 预聚合表（SUM/MAX/MIN），分布信息不可逆丢失，产品内 AI 自认"无法查询 P99"。实证支撑 §7.3 决策——**原始 span 全量留存 + 派生物化视图，绝不只存聚合结果**。

### 15.2 值得吸收的设计

| 项 | DataBuff 做法 | 我们的行动 |
|----|--------------|-----------|
| AI 多智能体排障 | AI Brain 编排查询/巡检/运维专家，MCP 双向，`config_ai_*` 表族 | AI 层作为独立章节，M3 设计评审、M4 MVP；表结构可参考 |
| 指标派生时机 | Ingest 写入时实时聚合 span → 分钟级 RED 表 | §14 P6：与异步物化视图做写入放大/查询延迟对比 PoC |
| SkyWalking 兼容 | 原生 11800 gRPC，改地址即迁移 | 二期摄入网关增加可插拔 SkyWalking receiver（获客通道） |
| 极简部署 | 3 组件一条 Docker 命令 | 私有化/POC 场景提供 "lite profile"（单 Doris 存算一体 + 内嵌摄入，去 Kafka/VM/FDB） |

### 15.3 其相对于本设计的结构性缺口（即我们的 SaaS 壁垒）

1. 无多租户模型（无 `tenant_id`、无配额计量计费）；
2. 无可靠性工程（无消息队列缓冲，Doris 停机 = 数据丢失 + 停写）；
3. 日志 `body` 无倒排索引、attributes 用 JSON 字符串而非 VARIANT，检索不具规模弹性；
4. Metrics 为固定 schema APM 指标，无 PromQL/Grafana 生态，非通用时序平台；
5. 30 天单级留存，无冷热分层与开放格式归档；
6. 无数据安全与合规能力（对比 §9.5）。

## 16. AI-Native 层设计

**定位**：AI 是平台的第三类产品接口（与 UI、Open API 并列），不是外挂聊天框。目标链路：自然语言提问 → 多智能体编排 → 直查实时遥测 → 携带证据的根因报告。

### 16.1 架构

```
用户自然语言 │ Cursor / Claude / 客户自有 Agent（MCP 客户端）
        │
        ▼
┌──────────────────────────────────────────────┐
│ AI 网关（控制面，多租户）                        │
│ 模型路由（BYOM：OpenAI 兼容接口）│ 租户级 token   │
│ 预算与限流 │ 会话审计                            │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ AI Brain（编排器）                              │
│ 任务拆解 → 并行派发专家 → 汇总为可转发报告        │
│ 内置专家：查询 / 巡检 / 根因 / 运维问答           │
│ 技能（Skill）可插拔：租户可注册自定义数字专家     │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│ 工具层 = MCP Server（复用 §8 统一查询网关）      │
│ search_logs │ query_metrics(PromQL) │ get_trace│
│ service_topology │ red_metrics │ list_alerts   │
│ get_neighbors │ get_blast_radius               │
│ get_golden_metrics（§7.6 Zmodel 语义工具）      │
│ get_exemplars（§7.7）                          │
│ run_sql（只读 + 行数/时间窗硬上限）              │
└──────────────────┬───────────────────────────┘
                   ▼
        §8 统一查询网关（租户注入、限流、审计）
```

### 16.2 关键设计决策

1. **工具层复用查询网关，绝不直连 Doris/VM**：AI 发起的每条查询自动继承租户谓词注入、并发配额、扫描上限与审计——这是多租户 SaaS 的 AI 与单租户 APM 的本质差异。AI 配置表族（provider/model/skill/expert/task/session/message）**全部加 `tenant_id`**，存控制面库。
2. **MCP 双向**：对外暴露 MCP Server（客户在自己惯用的 Agent 工具里直查其遥测数据，按平台 token 鉴权）；对内可挂载外部 MCP 作为虚拟数据源参与诊断。
3. **SQL 红利兑现**：底座是标准 SQL，NL→SQL 的准确率天花板显著高于 LogsQL/TraceQL 类私有语言——§1 选型决策在 AI 时代的延迟回报。工具层对 AI 暴露的是结构化工具而非裸 SQL，但 `run_sql` 兜底保留，配合表结构 + 示例查询的 schema prompt。
4. **防幻觉护栏**：AI 输出的每条结论必须携带证据链（执行的 SQL/PromQL、时间窗、命中行数），报告可点击回放到底层查询；一期**只读原则**——重启/回滚类运维动作仅生成建议，执行走人工审批。
5. **AI 计量计费**：模型 token 消耗按租户计量，进入 §9.3 计费体系；预算耗尽自动降级为规则巡检。
6. **AI 访问的合规边界（v1.2 补）**：AI 查询同样受 §9.5 的查询审计约束；送入模型的遥测内容已经过摄入侧 PII 脱敏；BYOM 场景下必须在租户配置中明确告知"数据将发送至所选模型提供方"，并支持租户禁用外部模型只用私有化部署模型。
7. **二期延伸——观测 AI 应用**：支持 OTel `gen_ai.*` 语义约定 span（LLM 调用链、token 消耗、prompt 版本、Agent 拓扑），平台既是 AI-native 的，也是 AI 应用的观测平台（与本节共用 spans 表，零额外存储成本）。

### 16.3 非目标（一期）

- 不做自动根因修复的执行闭环（只做诊断与建议）；
- 不自训模型（BYOM 路由 + prompt 工程 + RAG over 告警历史/工单）；
- 不做自然语言直接写库/改配置的通道。

### 17.2 全局决策

1. **双入口首页**：默认首页 = 服务健康矩阵（全服务 RED 概览，异常置顶）+ AI 输入框合体；
2. **全局上下文条**：时间选择器 + 项目/集群过滤器固定顶栏，跨页面保留；cluster 永远是第一维度；
3. **看板策略**：一期嵌入 Grafana（Dashboards 页 iframe + token 免密），自研力量集中在排障链路；二期评估自研拖拽看板；
4. **深色主题优先**；虚拟滚动 + 分页游标应对百万级日志列表；
5. **一切皆可跳转**：页面中任何 `trace_id`、service、时间点都是链接，承载 §8.2 关联动线的 UI 兑现。

### 17.4 关键页面：日志检索（流量最大页）

```
┌──────────────────────────────────────────────────────────────┐
│ [查询框：关键字 + 字段过滤，可切 SQL WHERE 模式]  [时间] [Live]  │
├──────────────────────────────────────────────────────────────┤
│ ▂▃▅▂▇▅▃▂ 日志量直方图（框选缩窗，按 severity 堆叠着色）          │
├───────────┬──────────────────────────────────────────────────┤
│ Facets    │ 日志列表（虚拟滚动）                                │
│ ▸ service │ 10:23:01.234 ERROR payment-svc  pod-7f8…         │
│ ▸ cluster │   ↳ 展开: body 关键字高亮 + attributes JSON 树      │
│ ▸ severity│        [上下文 ±50条] [跳转 Trace] [创建 Facet]     │
│ ▸ trace   │ 10:23:01.118 INFO  order-svc    pod-3a2…         │
│ ▸ 动态字段 │ …                                                 │
├───────────┴──────────────────────────────────────────────────┤
│ 模式: [列表] [图表分析] [SQL 编辑器]      [保存视图] [创建告警]   │
└──────────────────────────────────────────────────────────────┘
```

- **Facet 免注册（差异化）**：直接对 VARIANT 子列查 top values，动态字段即点即用——VARIANT 红利在 UI 层的兑现。**注意与 §7.1.1 的字段配额联动**：被 Top-N 取舍挤出子列化的长尾字段，Facet 聚合会变慢，UI 需对这类字段标注"低频字段，聚合较慢"；Schema Template 声明的路径（§7.1）则应在 Facet 列表中置顶，它们一定被子列化且多数带路径级索引；
- **★ v1.3 — 展开单条看完整 attributes JSON 树由 DOC 编码原生支撑**：官方在 VARIANT 「限制」一节给出的变通建议是"额外存一列原始 JSON 的 STRING"；本设计启用 DOC mode 后，原始 JSON 已由存储层维护，UI 直接 `SELECT log_attributes` 取整条即可，**无需在表里冗余一列**。这是 §7.1.1（3）为 logs 表选 DOC mode 而非稀疏列的理由之一。
  - 对应的查询纪律见 §8.1.1：**只有展开单条（返回 1 行）时才允许整条读**，列表页的 100 行必须走路径投影；
- **保存视图** = （查询语句 + 时间窗 + Facet 组合）可分享链接；
- 查询框双模式：关键字/字段语法（默认，类 KQL）与 SQL WHERE（高级）。

### 17.5 关键页面：Trace 详情

火焰图/瀑布图双视图 + 服务耗时占比图例 + span 侧滑面板，三处增强：

1. span 侧滑面板增加 **"相关日志"Tab**——同库 JOIN 零跳转加载（§8.2）；
2. **"AI 分析此 Trace"按钮**——trace 上下文直送 §16 根因专家，结果以证据卡片回显；
3. **（v1.2 新增）跨集群 trace 标注**——当一条 trace 的 span 跨越多个 `cluster_id` 时，在瀑布图顶部提示"本 trace 跨 N 个集群，部分 span 可能因跨集群采样不一致而缺失"（§6.5.4 已知缺陷的 UI 兑现）。

### 17.6 关键页面：AI 助手

- 对话流中每条结论渲染为**证据卡片**（执行的 SQL/PromQL + 图表 + 可点击回放），巡检报告可转发；
- **租户级长期记忆**：runbook、历史故障、业务术语沉淀为租户知识库，在 AI 网关侧以 RAG 注入；
- 首页 AI 输入框支持 @服务 / @集群 / @时间范围 结构化引用。

### 17.7 关键页面：接入向导（承载 §6.5）

三步流：选择集群类型（K8s/VM/Serverless）→ 生成内嵌 Token 的 `helm install` 命令 → **实时数据验收页**（"已收到 N 条日志 / M 个 span / K 个 series，最近 10 秒"，来自 metering topic 的实时反馈），验收通过自动弹出"去查看服务总览"。**（v1.2 补）验收页同时展示 tail sampling 的实时保留率**，让用户第一时间理解"为什么我发了 100 条 trace 只看到 10 条"。
